# Auth provider

Generated by `create-auth-provider` from the full template. The modules' sections are configured from two places, both outside git:

- the environment (`.env`): every key `{{application}}` reads;
- the local layer (`{{local}}`): lists, values that span sections, and the keys no module's example holds.

Each key not written keeps its module's default.

{{askedSection}}## Start

1. `pnpm install`
2. Copy `.env.example` to `.env`, uncomment each line you set and replace its placeholder; a value of several lines, such as a PEM key, goes in the local layer instead.
3. Copy `{{localExample}}` to `{{local}}`, uncomment each key and replace its placeholders, and add the keys this guide names that neither file holds.
4. `APP_CONFIG={{local}},{{application}} pnpm start`

Both examples hold every value in a comment: a copy left as it is sets nothing, and boot refuses each key still needed.
To try it on this machine over plain http, set `http.public-origin` and `issuer.url` to `http://127.0.0.1:{{port}}`, `http.insecure-origin` to `true`, and `kernel.environment` to `development`: an http public origin boots only with both, and its cookies cannot be made secure. A deployment keeps an https origin, leaves `http.insecure-origin` `false` and `kernel.environment` `production`.
A secret's placeholder begins `REPLACE-`; uncommented as it is, boot refuses it. Make one of random bytes, such as `REPLACE-32-RANDOM-BYTES-BASE64`, with `openssl rand -base64 32`. Delete the line of an optional key left unset.

{{firstLogin}}Until every key the modules need is written, the app writes each refusal on standard error, one per line, and exits 78; a refusal of a key it reads from the environment says where to write it (its variable in `.env`, or the key in `{{local}}`).
A variable 0.17 read that the environment still sets, and no configuration file reads, is named once on standard error, never its value, and boot goes on; set `APP_LEGACY_VARIABLES=refuse` to refuse boot on one instead, or `ignore` to skip the check.
SIGTERM or SIGINT stops it, draining what is under way, within `kernel.stop-deadline` (`30s` by default); give an orchestrator a grace period longer than `kernel.stop-deadline`.

## Docker

1. `docker build -t auth-provider .`
2. `docker run --env-file .env -e {{hostEnv}}=0.0.0.0 -e {{portEnv}}={{port}} -e APP_CONFIG={{local}},{{application}} -v "$PWD/{{local}}:/app/{{local}}:ro" -p {{port}}:{{port}} auth-provider`

An `-e` after `--env-file` wins over it: the container listens on every interface at {{port}}, where `-p` reaches it, whatever `.env` names for a run on the host.

Docker reads one line per variable from an env file: write a value of several lines, such as a PEM key, in the local layer instead.
The image runs as a user other than root and installs the locked production dependencies only. `tini` runs as process 1, so `docker stop` reaches the app and it stops cleanly.
Its health check asks `/_healthcheck`, which answers while the process runs; `/readyz` answers readiness, for a load balancer.
