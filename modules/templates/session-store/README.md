# session-store

Wires `session-lifecycle`'s store interfaces to `records`: session records to records, the cookie index to records under a secret, so a cookie's secret never reaches the store, and the list of closings to deferred work. Each has its own space, so a handle and a cookie's name never meet, and every space confirms its reads, the listings too: an entry decides on a raise or a close another request wrote, and a revocation reads each subject's sessions to close them, so each reads only what a failover keeps. The list of closings is spread over `closing-shards` shards (1–65536, default 1024) of up to `closings-per-shard` sessions (1–10000, default 1000); a session stays listed only while a participant keeps failing to close, so the defaults, about a million, leave room for a long outage while one shard stays near 50 KB. Each subject's listed sessions are keyed sets on `kernel`'s clock, of up to `sessions-per-subject` sessions (1–10000, default 100); a login rewrites its subject's set whole, so the default keeps it near 7 KB, far above what one person holds. Over the cap, the set pushes out the session ending first; `session-lifecycle` logs it and closes it, listing the closing first so a crash still finishes it. A need with nothing mapped to it, a guarantee or records under a secret, fails the type check, and `session-lifecycle`'s store contract, run on a store that loses what a missing guarantee allows, checks what each guarantee means. The wiring only maps, with no branches or loops. Depends on `kernel`, `session-lifecycle`, `records` and `store`.
