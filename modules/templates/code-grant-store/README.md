# code-grant-store

Wires `code-grant`'s store interfaces. Codes and each redemption record go to `subject-records` over the phase this process reads once, in `code-grant-store.codes` (keyed by secrets: created by the code, reached by the name `records` makes of it, so a code never reaches the store) and `code-grant-store.redemption-records` (keyed by the redemption's name, a digest); each `bounded` by `code-grant`'s `storedRecordMaxMs`, fenced at creation by the subject's tombstone, erased by `code-grant`, beside its index space, declaring `tombstoneFloor`, every port the builder's own. The composition is out of traffic while the phase cannot be read (probe `code-grant-store.phase`). To `records`: the codes to revoke, to deferred work. Each has its own space, which declares a guarantee for each need `code-grant` states. The codes to revoke are spread over `void-shards` shards (1–65536, default 1024) of up to `voids-per-shard` codes (1–10000, default 1000); a code is listed only when it comes again or its redemption is cut short, so the list grows no faster than codes are issued, and the defaults, about a million, leave room for a long outage of revocation while one shard stays near 50 KB. A need with nothing mapped to it, a guarantee or records keyed by secrets, fails the type check, and `code-grant`'s store contract, run on a store that loses what a missing guarantee allows, checks what each guarantee means. The wiring only maps, with no branches or loops. The void list's space holds no subject's data (`subjectData: none`): only the names of codes to void, digests of their secrets. Depends on `kernel`, `code-grant`, `records`, `subject-records` and `store`.
