# subject-revocation-store

Wires `subject-revocation`'s store interface, boundaries by subject, to `records`' records, kept without end, each write handing on the deadline `records` writes it with. Its boundaries space declares a guarantee for each need `subject-revocation` states, holds data kept through erasure (`retained`: a subject's mark of erasure among it), and is required of every process once erasure is enabled (`requiredOnceErasing`). Its fence keeps each receipt in a second space of the same guarantees that holds no subject's data (`none`: a random key and `{ id }`), in one write held by the subject's boundary as read, through `records`' `pairedRecordsAcross`, which refuses the boot where the two spaces' guarantees differ; the receipt lives the lifetime `subject-revocation` gives. It offers no fence where its store pairs none (`subject-revocation`'s `fenceWhere`), so such a store boots with erasure off; where erasure is enabled it is refused if the store gives a control record, and with neither it is the stated exclusion. Whether erasure is enabled is whether the store's control record holds `erasure-extensions`' mark, in any epoch, read when asked and never at boot. The control record is taken optionally until 0.22: where the store offers none, the boundary store does not tell, so erasure reads as off for start and readiness, every start warns, every bundle of a guarded composition is fenced where it fences, and erasure cannot be enabled. A need with nothing mapped to it fails the type check, and `subject-revocation`'s store contract, run on a store that loses what a missing guarantee allows, checks what each guarantee means. The wiring only maps, with no branches or loops. Depends on `kernel`, `subject-revocation`, `records`, `store` and `erasure-extensions`.

## Deprecated
- A store that offers no control record (`storeControl`): warned at every start, and where it pairs, every bundle of a guarded composition is fenced (+1 write) until it offers one; 0.22 requires it.
