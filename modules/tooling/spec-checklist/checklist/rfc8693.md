# RFC 8693: OAuth 2.0 Token Exchange

## 2.1 Request

- **rfc8693-2.1-a** MUST: a token exchange whose `resource` is not an absolute URI is refused.
- **rfc8693-2.1-b** MUST NOT: a token exchange goes on with a `resource` that carries a fragment.
- **rfc8693-2.1-c** MUST: a token exchange request without `subject_token` is refused.
- **rfc8693-2.1-d** MUST: a token exchange request without `subject_token_type` is refused.
- **rfc8693-2.1-e** MUST: a token exchange request with `actor_token` but no `actor_token_type` is refused.
- **rfc8693-2.1-f** MUST NOT: a token exchange goes on with an `actor_token_type` sent without an `actor_token`.
- **rfc8693-2.1-g** MUST: the subject token is validated by the procedures of the type `subject_token_type` names before anything is issued.
- **rfc8693-2.1-h** MUST: an actor token, when sent, is validated by the procedures of the type `actor_token_type` names before anything is issued.

## 2.2.1 Successful Response

- **rfc8693-2.2.1-a** MUST: a successful exchange answers the issued token in `access_token`.
- **rfc8693-2.2.1-b** MUST: a successful exchange answers `issued_token_type`, the type identifier of the token issued.
- **rfc8693-2.2.1-c** MUST: a successful exchange answers `token_type`, how the issued token is to be used.
- **rfc8693-2.2.1-d** SHOULD: a successful exchange answers `expires_in`, the issued token's lifetime in seconds.
- **rfc8693-2.2.1-e** MUST: a successful exchange answers `scope` whenever the scope issued differs from the one asked.

## 2.2.2 Error Response

- **rfc8693-2.2.2-a** MUST: an invalid exchange request, or a subject or actor token that is invalid or refused by policy, is answered with an RFC 6749 §5.2 error response.
- **rfc8693-2.2.2-b** MUST: that error response's `error` is `invalid_request`.
- **rfc8693-2.2.2-c** SHOULD: an exchange refused because no token can be issued for a `resource` or `audience` asked is answered with the error `invalid_target`.

## 4.1 "act" (Actor) Claim

- **rfc8693-4.1-a** MUST: when deciding on a token it takes, the server applies access control to the token's top-level claims and its current actor alone, never to the prior actors nested in `act`.

## 6 Privacy Considerations

- **rfc8693-6-a** MUST: a token whose content is to be hidden from the client is encrypted to its intended recipient.
  out-of-scope: no token is encrypted (`tokens`' card: signed and verified through `keys`' `accessTokenSigning` alone; `token-exchange`'s card: it issues access tokens only).
