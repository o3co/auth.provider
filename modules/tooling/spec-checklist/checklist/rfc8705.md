# RFC 8705: OAuth 2.0 Mutual-TLS Client Authentication and Certificate-Bound Access Tokens

## 2 Mutual TLS for OAuth Client Authentication

- **rfc8705-2-a** MUST: a request authenticating the client by mutual TLS without `client_id` is refused.
  out-of-scope: mutual-TLS client authentication is not offered: `mtls`'s card has authenticating clients by certificate under Not here, and `clients`' methods are `client_secret_basic`, `client_secret_post` and `none` with only `private_key_jwt` contributed (`client-assertion`), so `token_endpoint_auth_methods_supported` never names `tls_client_auth` or `self_signed_tls_client_auth`.
- **rfc8705-2-b** MUST: a client authenticating by mutual TLS is taken only when the certificate presented is the one expected for its `client_id` (by §2.1 or §2.2); none or another is `invalid_client`.
  out-of-scope: mutual-TLS client authentication is not offered: `mtls`'s card has authenticating clients by certificate under Not here, and `clients`' methods are `client_secret_basic`, `client_secret_post` and `none` with only `private_key_jwt` contributed (`client-assertion`).

## 2.1.2 Client Registration Metadata

- **rfc8705-2.1.2-a** MUST: a `tls_client_auth` client whose registration gives not exactly one expected subject parameter is refused.
  out-of-scope: the `tls_client_auth` method is not offered: `clients`' methods are `client_secret_basic`, `client_secret_post` and `none` with only `private_key_jwt` contributed (`client-assertion`), and no client metadata section holds an expected certificate subject.

## 3.1 JWT Certificate Thumbprint Confirmation Method

- **rfc8705-3.1-a** SHOULD: a JWT access token bound to a certificate holds the certificate's hash in the `cnf` member `x5t#S256`.
- **rfc8705-3.1-b** MUST: the `x5t#S256` value is base64url without trailing `=` padding.
- **rfc8705-3.1-c** MUST NOT: the `x5t#S256` value holds a line break, whitespace or any character beyond the base64url encoding.

## 4 Public Clients and Certificate-Bound Tokens

- **rfc8705-4-a** SHOULD: a refresh token issued to a public client whose access tokens are bound to a certificate is bound to that certificate too.
- **rfc8705-4-b** SHOULD: a certificate-bound refresh token is redeemed only when its binding is proved again.

## 7.4 X.509 Certificate Spoofing

- **rfc8705-7.4-a** SHOULD: under PKI client authentication, only a small set of CAs whose issuance policy meets the server's needs is taken as trust anchors.
  out-of-scope: the PKI method of client authentication (`tls_client_auth`) is not offered: `mtls`'s card has authenticating clients by certificate under Not here, and `clients`' methods are `client_secret_basic`, `client_secret_post` and `none` with only `private_key_jwt` contributed (`client-assertion`).

## 7.5 X.509 Certificate Parsing and Validation Complexity

- **rfc8705-7.5-a** SHOULD: certificate chains are validated with an established, well-tested X.509 library.
- **rfc8705-7.5-b** SHOULD NOT: certificate chains are validated by an X.509 validation procedure written for this server.
