# RFC 7521: Assertion Framework for OAuth 2.0 Client Authentication and Authorization Grants

## 3 Framework

- **rfc7521-3-a** MUST: an assertion grant whose assertion carries no signature or MAC from its issuer is refused.
- **rfc7521-3-b** MUST: a client assertion that carries no signature or MAC is refused.

## 4.1 Using Assertions as Authorization Grants

- **rfc7521-4.1-a** MUST: an assertion grant request without `assertion` is refused.
- **rfc7521-4.1-b** MUST: a token issued for an assertion grant carries no scope beyond what was granted beforehand to the subject it is for.
- **rfc7521-4.1-c** SHOULD NOT: an access token issued for an assertion grant stays valid well past the end of the assertion's validity.

## 4.1.1 Error Responses

- **rfc7521-4.1.1-a** MUST: an assertion grant refused because its assertion is invalid or expired is answered with the error `invalid_grant`.

## 4.2 Using Assertions for Client Authentication

- **rfc7521-4.2-a** MUST: a request carrying `client_assertion` without `client_assertion_type` is refused.
- **rfc7521-4.2-b** MUST: a request carrying `client_assertion_type` without `client_assertion` is refused.
- **rfc7521-4.2-c** MUST: a `client_id` sent beside a client assertion that names a client other than the assertion's is refused.

## 4.2.1 Error Responses

- **rfc7521-4.2.1-a** MUST: a client assertion refused for any reason is answered with the error `invalid_client`.
- **rfc7521-4.2.1-b** MUST: a request that uses more than one client authentication method is answered with the error `invalid_client`.

## 5.1 Assertion Metamodel

- **rfc7521-5.1-a** MUST: an assertion grant's issuer is matched to a trusted issuer by simple string comparison, without normalizing either.
- **rfc7521-5.1-b** MUST: a client assertion's issuer is matched to the client's id by simple string comparison, without normalizing either.
- **rfc7521-5.1-c** MUST: an assertion grant's audience values are matched to the server's identity by simple string comparison, without normalizing either.
- **rfc7521-5.1-d** MUST: a client assertion's audience values are matched to the server's identity by simple string comparison, without normalizing either.

## 5.2 General Assertion Format and Processing Rules

- **rfc7521-5.2-a** MUST: an assertion grant whose assertion names no issuer is refused.
- **rfc7521-5.2-b** MUST: a client assertion that names no issuer is refused.
- **rfc7521-5.2-c** MUST: a self-issued client assertion whose issuer is not the client's `client_id` is refused.
- **rfc7521-5.2-d** MUST: an assertion grant whose assertion names no subject is refused.
- **rfc7521-5.2-e** MUST: a client assertion that names no subject is refused.
- **rfc7521-5.2-f** MUST: a client assertion whose subject is not the client's `client_id` is refused.
- **rfc7521-5.2-g** MUST: an assertion grant whose assertion does not name this server among its audiences is refused.
- **rfc7521-5.2-h** MUST: a client assertion that does not name this server among its audiences is refused.
- **rfc7521-5.2-i** MUST: an assertion grant whose assertion has no expiry is refused.
- **rfc7521-5.2-j** MUST: a client assertion that has no expiry is refused.
- **rfc7521-5.2-k** MUST: an assertion grant whose assertion expired longer ago than the clock-skew allowance is refused.
- **rfc7521-5.2-l** MUST: a client assertion that expired longer ago than the clock-skew allowance is refused.
- **rfc7521-5.2-m** MUST: an assertion grant whose signature does not verify under its trusted issuer's key is refused.
- **rfc7521-5.2-n** MUST: a client assertion whose signature does not verify under one of the client's registered keys is refused.
- **rfc7521-5.2-o** MUST: an assertion grant protected by a MAC under a secret shared with its issuer is refused when the MAC does not verify.
  out-of-scope: assertion grants are taken only signed with an issuer's public key (`jwt-bearer` issuers' `keys` are public keys or a key set); `external-jwt` never takes shared-secret algorithms.
- **rfc7521-5.2-p** MUST: a client assertion protected by a MAC under the client's secret is refused when the MAC does not verify.
  out-of-scope: `client_secret_jwt` is not offered; `client-assertion` contributes `private_key_jwt` alone, with asymmetric algorithms, and `external-jwt` never takes shared-secret algorithms.
