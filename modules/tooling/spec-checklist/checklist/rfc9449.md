# RFC 9449: OAuth 2.0 Demonstrating Proof of Possession (DPoP)

## 4.2 DPoP Proof JWT Syntax

- **rfc9449-4.2-a** MUST: a proof whose JOSE header lacks `typ`, `alg` or `jwk` is refused.
- **rfc9449-4.2-b** MUST NOT: a proof whose `alg` is `none` or a symmetric (MAC) algorithm is accepted.
- **rfc9449-4.2-c** MUST NOT: a proof whose `jwk` carries a private key is accepted.
- **rfc9449-4.2-d** MUST: a proof whose payload lacks `jti`, `htm`, `htu` or `iat` is refused.
- **rfc9449-4.2-e** MUST: once the server has supplied a nonce, a proof without the `nonce` claim is refused, at the token endpoint with `use_dpop_nonce` and a fresh nonce in `DPoP-Nonce`.
- **rfc9449-4.2-f** MUST: a DPoP proof sent with an access token is refused when the proof carries no `ath`.
  role: rs
- **rfc9449-4.2-g** MUST: each DPoP proof o3co's client makes carries a `jti` that another proof in the same context takes only with negligible probability.
  role: client
  out-of-scope: o3co's client sends no DPoP proof: its requests to upstreams go through `upstream-client` and the upstream-login IdP types, and no upstream-login or delegation module builds a proof.
- **rfc9449-4.2-h** MUST: a proof whose JOSE header lacks `typ`, `alg` or `jwk` is refused.
  role: rs
- **rfc9449-4.2-i** MUST NOT: a proof whose `alg` is `none` or a symmetric (MAC) algorithm is accepted.
  role: rs
- **rfc9449-4.2-j** MUST NOT: a proof whose `jwk` carries a private key is accepted.
  role: rs
- **rfc9449-4.2-k** MUST: a proof whose payload lacks `jti`, `htm`, `htu` or `iat` is refused.
  role: rs
- **rfc9449-4.2-l** MUST: once the server has supplied a nonce, a proof without the `nonce` claim is refused, at a resource with a `DPoP` challenge whose error is `use_dpop_nonce` and a fresh nonce in `DPoP-Nonce`.
  role: rs

## 4.3 Checking DPoP Proofs

- **rfc9449-4.3-a** MUST: a request carrying more than one DPoP header field is refused.
- **rfc9449-4.3-b** MUST: a DPoP header whose value is not exactly one well-formed JWT is refused.
- **rfc9449-4.3-c** MUST: a proof whose `typ` header is anything but `dpop+jwt` is refused.
- **rfc9449-4.3-d** MUST: a proof whose `alg` is not a registered asymmetric signature algorithm that the server supports and its policy allows is refused.
- **rfc9449-4.3-e** MUST: a proof whose signature does not verify with the key in its own `jwk` header is refused.
- **rfc9449-4.3-f** MUST: a proof whose `htm` differs from the request's HTTP method is refused.
- **rfc9449-4.3-g** MUST: a proof whose `htu` differs from the request's URI, query and fragment left aside, is refused.
- **rfc9449-4.3-h** MUST: where the server supplied the client a nonce, a proof whose `nonce` is not exactly a nonce it recently supplied is refused.
- **rfc9449-4.3-i** MUST: a proof whose creation time, read from `iat` or from the server's time a nonce carries, lies outside a window of limited length is refused.
- **rfc9449-4.3-j** SHOULD: `htu` and the request's URI are compared after RFC 3986 syntax-based and scheme-based normalization.
- **rfc9449-4.3-k** MUST: a proof whose `ath` is not the base64url SHA-256 of the access token presented is refused.
  role: rs
- **rfc9449-4.3-l** MUST: a proof whose public key is not the one the presented access token is bound to is refused.
  role: rs
- **rfc9449-4.3-m** MUST: a request carrying more than one DPoP header field is refused.
  role: rs
- **rfc9449-4.3-n** MUST: a DPoP header whose value is not exactly one well-formed JWT is refused.
  role: rs
- **rfc9449-4.3-o** MUST: a proof whose `typ` header is anything but `dpop+jwt` is refused.
  role: rs
- **rfc9449-4.3-p** MUST: a proof whose `alg` is not a registered asymmetric signature algorithm that the server supports and its policy allows is refused.
  role: rs
- **rfc9449-4.3-q** MUST: a proof whose signature does not verify with the key in its own `jwk` header is refused.
  role: rs
- **rfc9449-4.3-r** MUST: a proof whose `htm` differs from the request's HTTP method is refused.
  role: rs
- **rfc9449-4.3-s** MUST: a proof whose `htu` differs from the request's URI, query and fragment left aside, is refused.
  role: rs
- **rfc9449-4.3-t** MUST: where the server supplied the client a nonce, a proof whose `nonce` is not exactly a nonce it recently supplied is refused.
  role: rs
- **rfc9449-4.3-u** MUST: a proof whose creation time, read from `iat` or from the server's time a nonce carries, lies outside a window of limited length is refused.
  role: rs
- **rfc9449-4.3-v** SHOULD: `htu` and the request's URI are compared after RFC 3986 syntax-based and scheme-based normalization.
  role: rs

## 5 DPoP Access Token Request

- **rfc9449-5-a** MUST: a token request whose DPoP header carries an invalid proof is answered with the RFC 6749 §5.2 error `invalid_dpop_proof`.
- **rfc9449-5-b** MUST: a token response issuing an access token bound to the proof's key gives `token_type` as `DPoP`.
- **rfc9449-5-c** MUST: a refresh token issued to a public client that presented a valid proof is bound to that proof's key.
- **rfc9449-5-d** MUST: a refresh request presenting a DPoP-bound refresh token is refused unless its proof is for the key the refresh token is bound to.
- **rfc9449-5-e** MUST: o3co's client asking for a DPoP-bound access token sends a valid DPoP proof in a `DPoP` header with each token request, whatever its grant type.
  role: client
  out-of-scope: o3co's client sends no DPoP proof: its requests to upstreams go through `upstream-client` and the upstream-login IdP types, and no upstream-login or delegation module builds a proof.
- **rfc9449-5-f** MUST: o3co's client discards a token response whose `token_type` is not `DPoP` where the binding's protection is deemed important.
  role: client
  out-of-scope: o3co's client sends no DPoP proof: its requests to upstreams go through `upstream-client` and the upstream-login IdP types, and no upstream-login or delegation module builds a proof.

## 5.2 Client Registration Metadata

- **rfc9449-5.2-a** MUST: a token request without a DPoP header, from a client registered as always binding by DPoP, is refused (the RFC's `dpop_bound_access_tokens`; here the client's `sender-binding` section with `required` and `kinds` naming `dpop`).

## 6 Public Key Confirmation

- **rfc9449-6-a** MUST: whether an access token is DPoP-bound, and to which key, is read from the token itself.
  role: rs

## 6.1 JWK Thumbprint Confirmation Method

- **rfc9449-6.1-a** MUST: a DPoP-bound JWT access token carries in `cnf.jkt` the base64url-encoded RFC 7638 SHA-256 thumbprint of the proof's public key.

## 6.2 JWK Thumbprint Confirmation Method in Token Introspection

- **rfc9449-6.2-a** MUST: an introspection response for a DPoP-bound token that names its `token_type` names it `DPoP`.

## 7.1 The DPoP Authentication Scheme

- **rfc9449-7.1-a** MUST: a DPoP-bound access token presented under the `DPoP` scheme without a DPoP proof is refused.
  role: rs
- **rfc9449-7.1-b** MUST NOT: access is granted before every check of the access token and its proof has passed.
  role: rs
- **rfc9449-7.1-c** SHOULD: a `DPoP` challenge to a request that carried an access token and failed authentication names the reason in `error`.
  role: rs
- **rfc9449-7.1-d** SHOULD: a `DPoP` challenge names, in `algs`, the JWS algorithms taken for proofs.
  role: rs
- **rfc9449-7.1-e** MUST NOT: this provider uses the `DPoP` scheme in `Proxy-Authenticate`, or takes it from `Proxy-Authorization`.
  role: rs
- **rfc9449-7.1-f** MUST: o3co's client ignores the parameters it does not know in a `DPoP` challenge.
  role: client
  out-of-scope: o3co's client sends no DPoP proof: its requests to upstreams go through `upstream-client` and the upstream-login IdP types, and no upstream-login or delegation module builds a proof.

## 7.2 Compatibility with the Bearer Authentication Scheme

- **rfc9449-7.2-a** MUST: a DPoP-bound access token presented as a bearer token is refused.
  role: rs
- **rfc9449-7.2-b** SHOULD NOT: a challenge to a request that carried no authentication holds an error code or other error information.
  role: rs
- **rfc9449-7.2-c** SHOULD: where the scheme a request tried can be told, its error is told in that scheme's challenge.
  role: rs

## 7.3 Client Considerations

- **rfc9449-7.3-a** SHOULD: o3co's client makes a new DPoP proof for each request, a retry of an idempotent one included.
  role: client
  out-of-scope: o3co's client sends no DPoP proof: its requests to upstreams go through `upstream-client` and the upstream-login IdP types, and no upstream-login or delegation module builds a proof.

## 8 Authorization Server-Provided Nonce

- **rfc9449-8-a** MUST: the nonces the server supplies in `DPoP-Nonce` cannot be predicted.
- **rfc9449-8-b** MUST NOT: an error response carries more than one `DPoP-Nonce` header field.

## 8.2 Providing a New Nonce Value

- **rfc9449-8.2-a** MUST: o3co's client puts the nonce a `DPoP-Nonce` header last supplied in its next token request and every one after, until the server supplies another.
  role: client
  out-of-scope: o3co's client sends no DPoP proof: its requests to upstreams go through `upstream-client` and the upstream-login IdP types, and no upstream-login or delegation module builds a proof.

## 10 Authorization Code Binding to a DPoP Key

- **rfc9449-10-a** MUST: a token request redeeming a code asked for with `dpop_jkt` is refused when the thumbprint of its proof's key differs from that value.
  out-of-scope: the `dpop_jkt` authorization request parameter is not offered (`authorize`'s card decides on the redirect URI, PKCE, scope, prompt and `max_age` alone; no module reads `dpop_jkt`).

## 10.1 DPoP with Pushed Authorization Requests

- **rfc9449-10.1-a** MUST: a DPoP proof sent with a pushed authorization request is checked as §4.3 says.
  out-of-scope: pushed authorization requests are not offered (no module contributes `pushed_authorization_request_endpoint` to `issuer`'s metadata).
- **rfc9449-10.1-b** MUST: a code from a pushed authorization request that carried a DPoP proof is redeemed only with a proof for the same key.
  out-of-scope: pushed authorization requests are not offered (no module contributes `pushed_authorization_request_endpoint` to `issuer`'s metadata).
- **rfc9449-10.1-c** MUST: a pushed authorization request may bind its code by `dpop_jkt` or by a DPoP header, and both are taken.
  out-of-scope: pushed authorization requests are not offered (no module contributes `pushed_authorization_request_endpoint` to `issuer`'s metadata).
- **rfc9449-10.1-d** MUST: a pushed authorization request whose `dpop_jkt` differs from the thumbprint of its DPoP proof's key is refused.
  out-of-scope: pushed authorization requests are not offered (no module contributes `pushed_authorization_request_endpoint` to `issuer`'s metadata).
- **rfc9449-10.1-e** MUST: o3co's client binding a pushed request's code by `dpop_jkt` sends it among the request's parameters in the POST body.
  role: client
  out-of-scope: o3co's client sends no DPoP proof: its requests to upstreams go through `upstream-client` and the upstream-login IdP types, and no upstream-login or delegation module builds a proof.
