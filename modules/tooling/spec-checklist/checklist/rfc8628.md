# RFC 8628: OAuth 2.0 Device Authorization Grant

## 3.1 Device Authorization Request

- **rfc8628-3.1-a** MUST: a device authorization request from a client that does not authenticate and names no `client_id` is refused.
- **rfc8628-3.1-b** MUST: a parameter sent with an empty value at the device authorization endpoint is handled as though it had not been sent.
- **rfc8628-3.1-c** MUST: a parameter the device authorization endpoint does not know is passed over, never a cause to refuse the request.
- **rfc8628-3.1-d** MUST: a device authorization request that sends a parameter more than once is refused.
- **rfc8628-3.1-e** MUST NOT: a device authorization response carries one of its parameters twice.

## 3.2 Device Authorization Response

- **rfc8628-3.2-a** MUST: a successful device authorization response carries `device_code`.
- **rfc8628-3.2-b** MUST: a successful device authorization response carries `user_code`.
- **rfc8628-3.2-c** MUST: a successful device authorization response carries `verification_uri`, the page on the server where the user goes.
- **rfc8628-3.2-d** MUST: a successful device authorization response carries `expires_in`, the lifetime in seconds of both codes.

## 3.3 User Interaction

- **rfc8628-3.3-a** MUST: the server offers a user interaction that begins with the user opening `verification_uri` and, at some step of it, has the user give the `user_code`.
- **rfc8628-3.3-b** SHOULD NOT: the user code is written into the `verification_uri` the server answers.

## 3.4 Device Access Token Request

- **rfc8628-3.4-a** MUST: the device grant is taken at the token endpoint only under the grant type `urn:ietf:params:oauth:grant-type:device_code`.
- **rfc8628-3.4-b** MUST: a device access token request without `device_code` is refused.
- **rfc8628-3.4-c** MUST: a device access token request from a client that does not authenticate and names no `client_id` is refused.
- **rfc8628-3.4-d** MUST: a device access token request from a client that holds credentials, or must authenticate otherwise, is refused unless it authenticates as RFC 6749 §3.2.1 says.

## 5.1 User Code Brute Forcing

- **rfc8628-5.1-a** SHOULD: user codes carry enough entropy that, with the attempt limit and their short life, guessing one is not feasible.

## 5.2 Device Code Brute Forcing

- **rfc8628-5.2-a** SHOULD: device codes carry very high entropy.

## 6.1 User Code Recommendations

- **rfc8628-6.1-a** SHOULD: the user code is drawn from a character set with no two characters easily taken for one another.
