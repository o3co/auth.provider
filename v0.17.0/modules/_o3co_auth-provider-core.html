    Module @o3co/auth-provider-core

    @o3co/auth-provider-core

    Last updated: 2026-10-08

    Responsibility

    @o3co/auth-provider-core is the package every other auth.provider package builds on: the module system and the boot planner (createApp), the grant-handler contract and the token helpers every grant mints with, the repository and store ports with in-process adapters for a single replica, the key store, and the configuration schema. It sits under every other package and imports none of them. That is why it is a package of its own: a contract several packages share lives here, because those packages do not all depend on one another — session and oauth are independent, and oauth-token-exchange and webauthn implement grants without depending on oauth — so core is the one place they all depend on.

    It owns no grant type and no /oauth/* endpoint (@o3co/auth-provider-oauth and the grant packages): the only route core mounts itself is the discovery document, and its JWKS, health and readiness routers are installed by a composition root. It owns no durable adapter (@o3co/auth-provider-redis), no federation adapter (the @o3co/auth-provider-federation-* packages), no login or browser session (@o3co/auth-provider-session) and no Store client (@o3co/auth-provider-foundation). Which directory inside owns what, and why each is separate, is src/README.md.

    Vocabulary: the Store is auth.provider's term for the consumer's upstream user service — the system of record for identity, credentials, and email-verification state. Defined on the User doc in src/repositories/types.mts; auth.provider reads Store-published state, and causes a write there only through the two optional relays its own flows need (linkFederatedIdentity, and markMfaEnrolled, the MFA enrollment witness).

    Install

    npm install @o3co/auth-provider-core
    # and, for createApp:
    npm install express@^5.0.0

    Optional peer dependency: express@^5.0.0, needed only for createApp. The package depends on bcrypt, jose, js-yaml and zod.

    Public API

    Configuration

    A composition root resolves its configuration — its own files over the reference.conf of every package it loads, in the order moduleReferences(modules) answers them, core's last — and hands createApp what it resolved, unparsed. Boot parses it once:

    1. with core's base, CoreConfigSchema: core's own section, core, with its coercions and checks (an environment variable's string read as a number or a boolean). No other section is core's: each is validated by the schema of the module that reads it when that module is loaded, and by nothing when it is not;
    2. laid over what was written, so a section no schema declares is kept;
    3. then with each module's own section, at the module's name, over the base's output, written back there: a loaded module's section is never stripped.

    A value any of them refuses refuses boot (config-validation-failed), naming each path the operator wrote. So does a key named after an Object.prototype member (__proto__, constructor, toString, …) or prototype, at any depth, whatever the schemas make of it: a schema would drop __proto__ unread, and a lookup by any of the others may find the inherited member. The check covers the configuration's own data properties, which is everything a parsed HOCON file holds; a getter in a configuration built in code is read by the schemas' parse, not by this check. A top-level section nothing loaded owns is kept, and named once in the log, at warn, with the names and never a value, to the logger bootstrapped beside the configuration. A package's reference.conf is layered whenever any of its modules is, so it sets the sections of siblings that are not loaded; a composition root that also hands boot the configuration's defaults — bootstrapComponents.configDefaults, the same references resolved with no file of its own and no environment, to plain data the same way as the configuration, since a section is compared with its default whole (ReservedBootstrapInputs) — lets boot tell them apart: a section the defaults hold and the configuration leaves equal to them is not named; one the operator's files or the environment changed is config_sections_not_loaded, a setting for a module the composition does not load; one the defaults do not hold is config_sections_ignored, which is where a misspelt section name shows. Without the defaults, every such section is config_sections_ignored. A section that sets nothing — empty, or holding only empty sections — is not named, as core's own reference.conf leaves jwks when JWKS_PATH and JWKS_CACHE_MAX_AGE are unset. Likewise, a variable a package's reference.conf captures in renamed-variables that the resolution saw set and no loaded module — nor core — declares renamed is named once as environment_variables_not_applied, at warn, with the names: RATE_LIMIT_FAIL_MODE set with the Redis package loaded but not its rate limiter, for one. What boot parsed is the config slot; read it from the handle. It is one object core and its own modules share — no other module reads it (below) — and its plain data — objects and arrays — is a copy frozen all the way down: a write to it throws a TypeError in strict-mode code. A value that is not plain data — a Map, a Date, a class instance an open schema passed through or a transform built — is handed over as is, not frozen.

    import { fileURLToPath } from "node:url";
    import { type AppConfig, createApp, moduleReferences } from "@o3co/auth-provider-core";
    import { type Config, empty, parseFile } from "@o3co/ts.hocon";

    // `own` over every loaded package's reference.conf, core's last.
    const layered = (own: Config, options?: { env: Record<string, string> }) =>
      moduleReferences(modules)
        .reduce(
          (config, reference) => config.withFallback(parseFile(fileURLToPath(reference), options)),
          own,
        )
        .toObject();

    const resolved = layered(parseFile("config/application.conf"));
    // The same references with no file of the composition's and no environment.
    const configDefaults = layered(empty(), { env: {} });

    const handle = await createApp({
      modules,
      // Unparsed: createApp parses it once, with every loaded module's schema.
      bootstrapComponents: {
        config: resolved as unknown as AppConfig,
        configDefaults,
        pathResolver: import.meta.resolve,
      },
    });
    const config = handle.components.config; // what boot parsed

    A section core's schema does not declare — a module's, or a path one moved from — is the module's to validate. With the module loaded, its own schema reads it, environment strings included; without it, nothing reads it: it is kept as written in the config slot and named as above, never refused by core. A path a section moved from is refused (config-path-relocated) only while a loaded module declares the move, or core does for its own section (CORE_RELOCATIONS); cors is the exception: core reads a composition's CORS origins from the httpSettings slot alone, so a cors section that sets anything refuses boot (config-validation-failed, naming the slot) unless a loaded module's own section is cors, which reads it. A loaded module that relocates it refuses it first, naming its own path (the standalone template's http does, config-path-relocated); an empty cors {} sets nothing and boots. Core's own section a composition root reads before boot with readCoreSection(resolved) (src/config/core-section.mts): core {} alone, by the strict schema boot parses it with, refused in the same words, and no other section.

    AppConfig, the type of the config slot, is CoreConfig & Readonly<Record<string, unknown>>: core's sections typed, every other section unknown. A module reads its own section as deps.section, typed by its schema. The config slot itself is core's: only the modules core ships read it, known by the manifest objects themselves, not by their names. Any other module that lists config in its requires or its optional refuses boot, switched on or not and before any factory runs (reserved-component-key, details { componentKey: "config", source, module }), the message naming the module and the slot and pointing at its own section — a module named as one of core's, or a copy of one, is refused the same way. Read the module's own settings as deps.section, and what another module owns through a slot (federationSettings, outboundPolicy, oauthTokenSettings, …).

    Defaults live in a reference.conf, never in the schema: core's own sections' in config/reference.conf, a module's in the reference.conf its manifest declares (the standalone template's http, logging and key-store settings in the template's).     Core reads a few keys of the oauth module's section by path, beside its own: the issuer (oauth.jwt.issuer) its stage-1 grant-policy check and its discovery document, CORS table and session requirements' pages are built on, the token lifetimes (oauth.accessToken.* through resolveAccessTokenLifetime, oauth.refreshToken.expiresIn through resolveRefreshTokenLifetime) its revoking records are sized by, and oauth.revocation.*, which two absence policies are keyed in. With the oauth module loaded it reads the module's parsed section; with no oauth-package module loaded nothing layers that package's reference.conf, so no OAUTH_* variable binds any of it, and core reads what was written, failing closed:

    • every key written under oauth {} but those, while no loaded module's section is oauth (oauthEndpointsModule not loaded), refuses boot (config-validation-failed, one issue per path, naming the module and never the value): a retired key, a misspelt one, or one only that module reads; and so does a configured oauth.jwt.issuer that is not a canonical issuer (checkCanonicalIssuer), at the key, so every reader sees a canonical issuer or none;
    • a grantPolicy wired with no issuer refuses boot (grant-policy-without-issuer); with no issuer there is no discovery document, the CORS table guards no discovery path, and a requirement's page is held to no issuer's origin;
    • an absence policy keyed in oauth.revocation.* is satisfied only by "unsupported" written there: OAUTH_REVOCATION_SUBJECT and OAUTH_REVOCATION_ACCESS_TOKEN declare nothing, and the unfilled slot refuses boot (component-absence-undeclared);
    • a lifetime that is absent, or an environment string no section schema read, is refused: an oauthTokenSettings a host fills as config-validation-failed at stage 1, one a module provides, and the default refresh-token family modules, as provides-factory-failed. With no token settings at all nothing in the composition mints a refresh token, and the session lifecycle keeps a closing record for no time.

    Grant System

    The grant system is the extension point for OAuth 2.0 grant types. Each grant type is implemented as a GrantHandler and declared on a module via contributes.grants; the boot planner instantiates and registers handlers internally.

    Interfaces and types

    The definitions are in src/grants/types.mts: GrantHandler, GrantContext, SessionData, AuthenticatedClient, GrantHandlerResult, GrantDependencies, GrantFactory. What a handler may trust (authenticatedClient, never body.client_id) and what it must not do is documented on the fields themselves; the directory's responsibility map is src/grants/README.md.

    Grant registration

    A module declares its grants in contributes.grants, keyed by grant type. Whether a grant is contributed at all is the module's decision: the oauth package's modules contribute each of their grants only when its switch is on — oauth-session.enabled for the session grant, oauth-authorization.grants.<grant>.enabled for the others — while token exchange and WebAuthn contribute theirs whenever their module is installed, and the device-grant module registers the device grant only when its own device-grant.enabled is true. A factory may answer null instead, switching its grant off: the grant type is then absent from the token endpoint's dispatch and from discovery's grant_types_supported, as one no module contributes is, yet still claimed, and an override of it refuses boot. Boot runs each factory, registers the handler under its grant type — two modules contributing the same grant type refuse boot — and freezes the registry at stage 5, so a registration after boot throws. Consumer code never imports or builds the registry: GrantRegistry is internal and not exported from the package root.

    A GrantHandler has no teardown hook. AppHandle.dispose() runs each provided component's lifecycle[K].cleanup in reverse-topological order, then Symbol.asyncDispose on module-provided values that declared none, then the LifecycleRegistrar drain — and never touches the registry. A module that holds a resource on a handler's behalf releases it through its own lifecycle[K].cleanup; see src/grants/README.md.

    Resource indicators (RFC 8707)

    A grant that honours resource reads it with extractResourceParam, derives the audience it names with deriveAudienceFromResources, and refuses an issued aud that does not represent it with unrepresentedResources — src/grants/resourceIndicator.mts. Each value is kept whole (a URI may contain a comma), the empty entries of a repeated parameter are dropped, and an all-empty parameter means none was requested. The oauth grants, /authorize and the WebAuthn grant all read it there, so a custom grant that does the same gives the same answer.

    Underneath is readTargetParameter, the strict reading of a target parameter — resource, or RFC 8693's audience — from a form or JSON body: the values it names ([] when none), or null when it is malformed, that is neither a string nor an array of strings. A malformed value is never converted to a string, since String([["https://x"]]) names https://x. extractResourceParam reads a malformed resource as none requested. The token-exchange grant reads resource and audience with readTargetParameter and refuses a malformed one with invalid_target: RFC 8707 §2's answer to a resource the server "fails to parse", given to audience by symmetry.

    Outbound fetch

    createOutboundFetch({ config, source }) returns a fetch for URLs a client registration (source: "registration") or a request (source: "request") supplies, under core.outbound — src/net/outbound-fetch.mts. A module that does not read config passes the outboundPolicy slot instead, createOutboundFetch({ policy, source }), and gets the same fetch: exactly one of config and policy is given, and both or neither is a TypeError. The fetch:

    • https only. Plain http is admitted only to a loopback host internalHosts lists, for a registration's URL, and only when every address it resolves to is loopback.
    • A URL with credentials is refused, and so is a port on the Fetch standard's bad-port list.
    • deniedHosts refuses a host whatever the other lists say; a non-empty allowedHosts refuses any host it does not list. A non-empty allowedHosts also narrows internalHosts: an internal host must be listed in both. An entry is a host name (letters, digits and hyphens once IDNA has run; no wildcard) or an IP address (an exact match), or a .suffix (the domain and every subdomain), and both the entries and the URL's host are read as the URL parser reads a host: case, IDNA, a trailing dot and IP spellings do not change what matches, and an IPv4 address and its IPv4-mapped IPv6 literal match each other.
    • The host is resolved once, and every address must be outside the special-use ranges (isSpecialUseAddress). An answer with any special-use address is refused. internalHosts lifts this for a host it lists, for a registration's URL only; a request's URL never has it.
    • The connection goes to the addresses that were checked and nowhere else; the TLS server name and certificate identity stay the URL's host.
    • No redirect is followed: any 3xx but 304 is refused. A status that is not 2xx, and 204, 205 and 304, comes back with a null body. A 2xx body is read whole: in the identity encoding only (the request asks for it), and up to maxResponseBytes.
    • One deadline, timeoutMs, covers resolution, connection, TLS, headers and body. timeoutMs and maxResponseBytes in core.outbound are ceilings: a caller's own (createOutboundFetch's options) applies only when smaller. A caller's signal still applies, and its abort rejects with its own reason.
    • Host-name resolutions are bounded for the whole process, across every fetch createOutboundFetch builds: at most two fewer than the libuv threadpool size, and at least one (lookupCeilingOf in the source). The size is UV_THREADPOOL_SIZE read as libuv reads it: absent, 4; present, its leading digits (atoi), with 0 read as 1 and anything past 1024 as 1024, except that a value too large for an int (2^31 or more, either sign) reads as 0, as atoi answers it, and so as one thread. It is read once, when the module loads, so the default bound is 2. Set it before the process starts, as Node's documentation says: the threadpool is sized at its first use. The system resolver runs on that threadpool, which bcrypt and the file system share, and it cannot be cancelled: a resolution the deadline gave up on keeps its thread, and counts, until it settles. libuv runs host-name resolution on at most (n + 1) / 2 of its n threads. This bound keeps the outbound fetch's own resolutions finite, those nobody waits for any more included, and keeps a URL a client supplies from holding more than one of them. With a very small pool (1 or 2 threads) that limit is every thread or all but one, so resolutions that hang can still occupy the threads libuv gives such work: a deployment that enables Client ID Metadata Documents should keep UV_THREADPOOL_SIZE at its default, 4, or higher. Of the bound, URLs a request names (source: "request") may hold one resolution at a time, and none when the bound is 1, where such a call fails with timeout at once; the rest is left to client registrations' URLs, so request URLs whose resolver never answers cannot hold up a registration's jwks_uri or a back-channel delivery. A call that needs a resolution its source may not start yet waits for one, within its own deadline, and fails with timeout without starting one; a freed place goes to the longest-waiting call that may take it, so a registration's goes ahead of a request's whose share is full. An IP-literal host, and a URL refused before resolution, do not count. At most 64 calls wait across the process (MAX_WAITING_LOOKUPS), at most 48 of them for a request's URL; a call that finds its queue full fails with timeout at once, without waiting or resolving. None of these bounds is configured. A fetch from createOutboundFetchForTesting resolves under a pool of its own, bounded the same way.
    • It takes a string or a URL, GET or POST, and a string, URLSearchParams or Uint8Array body.

    outboundLimitsOf(config) answers the timeoutMs and maxResponseBytes the section sets (the defaults when it is absent), the ceilings the fetch applies, for a caller to compare its own with; it refuses a malformed section as building the fetch does.

    matchesHostList and readHostEntry (src/net/outbound-policy.mts) are the host-list grammar's public readers, for a list of the same form kept elsewhere. matchesHostList reads its input as an entry is read (any URL's hostname; case, a trailing dot and IP spellings alike), and throws a TypeError for a host it cannot read, such as one with an empty label, which the caller refuses. isOutboundRefusal(err) tells the policy refusing from the exchange failing (resolution, network, deadline); the reason is a code that loggableError keeps as reason. A proxy or dispatcher installed in code is not consulted: outbound client-metadata fetches connect directly. Building the fetch refuses while HTTPS_PROXY or HTTP_PROXY is set, unless core.outbound.egress is "direct". IPv6-only networks that reach IPv4 through NAT64 (64:ff9b::/96) are not supported, as those addresses are special-use. Tests use createOutboundFetchForTesting and withOutbound from @o3co/auth-provider-core/testing, with a resolver and a transport of their own below the policy.

    Error text (RFC 6749)

    RFC 6749 Appendix A.7 and A.8 limit error and error_description to 1*NQSCHAR: printable ASCII without " and \. The rule is in src/errors/envelope.mts:

    • errorEnvelope(error, description?, uri?) builds the RFC 6749 §5.2 error body and applies the rule itself, so every writer that goes through it conforms whatever it was handed: core's token-binding middleware (a mechanism's retryInstruction or unavailable text, the kinds a dispatch conflict names), the protected-resource binding, the rate limiter (a limiter adapter's reason), the session routes and a contributed module's own routes. A description character outside the set is sent as ?; a description that is not a string is dropped like an empty one. A malformed error code is sent as server_error and logged as error_envelope_code_malformed through consoleLogger: the code came from server-side code, and the envelope does not know the status its caller answers with. error_uri is sent only when it is an http: or https: URI — §5.2's human-readable web page — or a relative reference, parsed component by component against RFC 3986's grammar (no userinfo — https://example.com@evil.example/ goes to evil.example — brackets only around an IP-literal host, no colon in a relative path's first segment, one fragment) and resolved by the WHATWG URL parser. Every character that grammar admits is in RFC 6749's error_uri set (Appendix A.9). Any other error_uri is dropped, not altered, and logged as error_envelope_uri_malformed.
    • sanitizeErrorText replaces every character outside the set with ?, and answers undefined for a value that is not a string, so the caller falls back to its own default. A writer that builds its body itself — a redirect's query, a literal { error, error_description } — sends what it echoes through it.
    • auditErrorText does the same and caps the text at 200 characters, for a log line or an audit event.
    • auditErrorList(values, maxItems = 10) records a list a client chose (the scopes it asked for, the resources it named) for a log line or an audit event: still an array, each entry through auditErrorText, the first maxItems kept. A small, well-formed list comes back as it was; the caller adds a count of the entries sent when the list was cut (requestedScopeCount, missingResourceCount). A maxItems that is not a positive integer is a RangeError.
    • isWellFormedErrorCode checks an error code before it goes out. A caller that builds a code from something it does not control and knows its answer is a refusal of the client's request falls back to a client-error code itself: the token-binding middleware answers a refusal whose invalid_<kind>_proof would be malformed as invalid_request, and core's policyDenied and /oauth/authorize do the same for a grant policy's deny (below).

    Text written in this repository's own words is held to the set where it is written by __tests__/errorText.drift.test.mts: quote a value with ', write "section" for the section sign, and use no em dash.

    Token Utilities

    generateToken(data, options), generateTokenResponse(tokens) and formatObject are in src/grants/token.mts, with Token, TokenResponse and GenerateTokenOptions beside them.

    generateToken signs a JWT with the current signing key of options.keyStore; alg and kid are the key store's, typ is options.tokenType, cnf is emitted only when options.confirmation is given, and jti / issuedAt are minted unless the caller reserved them first (#449). exp is iat + options.expiresIn, so expiresIn must be a positive whole number of seconds: a fraction, NaN, Infinity, zero or less is a RangeError before anything is signed, and so is a lifetime that would put exp past Number.MAX_SAFE_INTEGER (the configuration schema refuses the same values for oauth.accessToken.* and oauth.refreshToken.expiresIn). generateTokenResponse formats an access token, an optional refresh token and an optional id_token into the OAuth 2.0 token endpoint response shape, with the token_type read off the access token's own confirmation (the confirmation generateToken echoes on the Token): DPoP for cnf.jkt (RFC 9449 §5), Bearer for cnf.x5t#S256 (RFC 8705 §3) and for an unbound token — so the envelope cannot disagree with the claim. A grant stamps ownedConfirmation(ctx.tokenBinding), the member the binding's mechanism owns, never ctx.tokenBinding.confirmation as a mechanism returned it. generateToken also returns the exp it signed as Token.expiresAt (epoch seconds), and generateTokenResponse answers expires_in as the access token's time left when the response is built: max(0, min(expiresIn, expiresAt − floor(now))). It is never above the lifetime and within a second of the real remaining life; a token without expiresAt answers expiresIn as given. The 0 floor is core's rule; a route may refuse instead (token exchange and the federation token route answer 503). formatObject strips undefined and null values from an object.

    Key Store

    The KeyStore interface abstracts over symmetric (HS256) and asymmetric (RS256, ES256, EdDSA) signing keys, including key rotation. Rotation is shape-specific: asymmetric algorithms use previousKeys (kid + public key + expiry), and HS256 uses previousSecrets (kid + secret + expiry). getVerificationKey(kid) resolves the key by kid — the keystore returns the matching key directly, never trial-verifies across keys — and throws UnknownKidError for a kid it does not hold and ExpiredKidError for one whose expiresAt has passed, so a caller can tell a fabricated kid from a retired one. Anything else it throws — a remote key service that timed out — is the keystore failing to answer, not a finding about the token: verifyJwt reports it as verification_key_unavailable, never kid_unknown, and every route answers it 503 temporarily_unavailable (see Token verification). So a custom keystore must answer a kid it does not hold with UnknownKidError, never with another error. The kid is untrusted — the token's own header, read before any signature is checked; verifyJwt passes only a well-formed key id (isWellFormedKid: a string of 1 to MAX_KID_LENGTH (256) characters with no control character), but any other character may be in it — so an adapter that looks keys up remotely (a KMS, an HSM, a JWKS endpoint) checks it against its own key naming before it reaches that system, and answers one that fails with UnknownKidError. The contract is written on getVerificationKey in src/keys/KeyStore.mts. The same rule holds where a kid is chosen: key-store and all three bundled keystores refuse a current or previous kid that is not a well-formed key id when they are built (src/keys/kid.mts). Otherwise the server would sign tokens its own verifier refuses as kid_unknown. A previous key's expiresAt follows the same pattern (src/keys/retirement.mts): all three stores refuse, when they are built, one that is not a Date holding a valid time — an Invalid Date, an ISO string, a number — naming the entry (previousKeys[0].expiresAt, previousSecrets[0].expiresAt), and read each date once, so changing the Date object afterwards moves no deadline. A previous key verifies only strictly before its expiresAt, and a deadline that cannot be compared counts as passed: the key no longer verifies. sign(options) returns a compact JWT; the KeyStore self-injects the alg and kid protected header fields, so callers cannot override them. This contract lets remote-sign adapters (KMS/HSM) implement sign() without exposing private key material. getSigningKidFallback() is a cheap accessor returning the current signing kid for verifying legacy/malformed tokens that lack a kid header. Do not use it for rotation-safe lookup.

    The definitions — KeyStore, SignJwtOptions, JWTPayload, ManagedKey, KeyLike, the two errors, AsymmetricKeyStoreOptions, SymmetricPreviousSecret, createAsymmetricKeyStore and createSymmetricKeyStore — are in src/keys/KeyStore.mts.

    Signing without holding the private key (KMS / HSM / Vault)

    createRemoteSigningKeyStore is a KeyStore whose private key never enters this process. The whole seam is one method, RemoteSigner.sign(kid, data), which answers the signature in JWS form (RFC 7515 §3.3), not the provider's native encoding. Its options carry public key material only, and verifyOnConstruction defaults to true; the definitions are in src/keys/remoteSigning.mts.

    Everything else a KeyStore owes — building the protected header, base64url encoding, assembling the compact JWT, rotation bookkeeping, publishing JWKS — is done for you, so an integrator writes the provider call and nothing else.

    No vendor is bundled. Wire AWS KMS, PKCS#11, or a Vault transit key by supplying signer; core stays free of any of their SDKs. There is no remote entry in the key-store factory for the same reason a RemoteSigner is a function: build the store in your composition root and supply it as the keyStore component.

    ES256 returns DER from almost every provider, and JWS does not accept it. AWS KMS, PKCS#11 and OpenSSL all return an ASN.1 SEQUENCE; JWS wants the raw R || S concatenation. derToJoseEcdsaSignature(der) converts it. Getting this wrong produces signatures that fail at the relying party while the signer reports success, which is why the store signs one token at construction and verifies it against the public key — a signer returning the wrong form fails boot with a message naming both likely causes. Pass verifyOnConstruction: false only where a provider call at boot is itself the problem.

    There is no HS256 variant, deliberately. A shared secret has no public half, so "the key never leaves the boundary" cannot be true of it — every verifier needs the same bytes the signer has. Offering it here would let a deployment believe it had moved key material out of reach when it had not.

    // Sketch: AWS KMS, ES256
    const store = await createRemoteSigningKeyStore({
      algorithm: "ES256",
      kid: "v1",
      publicKeyPem: await fetchPublicKeyPem(),
      signer: {
        async sign(_kid, data) {
          const { Signature } = await kms.send(new SignCommand({
            KeyId: KMS_KEY_ID,
            Message: data,
            MessageType: "RAW",
            SigningAlgorithm: "ECDSA_SHA_256",
          }));
          return derToJoseEcdsaSignature(Signature!);  // KMS returns DER
        },
      },
    });

    createKeyStoreFactory() creates a new factory with no registered types. registerBuiltinKeyStores(factory) registers the built-in "local" provider, which dispatches to createAsymmetricKeyStore or createSymmetricKeyStore based on algorithm. Both are in src/keys/factory.mts. The factory follows the same AdapterFactory<T> contract as the ClientRepository, UserRepository, and CodeRepository factories.

    Algorithm default and key requirements

    reference.conf ships algorithm = "EdDSA" (DEFAULT_SIGNING_ALGORITHM). Asymmetric by default because HS256 leaves a relying party with two bad options: verify nothing (there is no public key to publish) or hold the shared secret — which also lets it mint tokens.

    The "local" builder has no fallbacks:

    • An absent algorithm is an error, not an implicit HS256.
    • An asymmetric algorithm with no privateKey/privateKeyPath (or no public half) throws a message naming the exact config keys, the exact environment variables, and the openssl genpkey -algorithm ed25519 command that produces them.
    • HS256 requires secret to carry at least MIN_SECRET_ENTROPY_BYTES (32) of key material, and so does every previousSecrets[].secret.

    Entropy is measured on the decoded value, taking the smallest plausible reading (measureSecretEntropyBytes): a 64-character hex string is 32 bytes and passes; a 32-character hex string is 16 bytes and does not. The same floor applies to session-store.secret, enforced by the session store's section schema. assertSecretEntropy / describeWeakSecret are exported so a composition root that accepts its own operator secrets can apply the identical check.

    Note that the floor lives in the builder and the schema — the config boundaries. createSymmetricKeyStore is the low-level primitive and does not enforce it, so a composition root calling it directly owns the check.

    HS256 key rotation

    To rotate an HS256 signing key without a maintenance window:

    1. Record the current kid and secret values.

    2. Generate a new secret: openssl rand -hex 32.

    3. Update application.conf to set the new kid + secret and move the old pair into previousSecrets:

      key-store.local {
  algorithm = "HS256"
  kid = "v1"           # new kid
  secret = ""
  previousSecrets = [{
    kid = "v0"          # old kid
    secret = ""
    expiresAt = "2026-06-05T00:00:00Z"  # access-token TTL + buffer
  }]
}

    4. Restart the server. Tokens signed by v0 continue to verify (resolved by kid from the JWT header) until expiresAt.

    5. After the overlap window passes (all v0 tokens have expired), remove v0 from previousSecrets and restart again.

    Both the new secret and every previousSecrets[].secret must clear the 32-byte floor — a retired secret is still a live verification key for the whole overlap window, so it carries the same forgery risk the current one does.

    The schema rejects mixing the asymmetric previousKeys shape with HS256, and the builder rejects the reverse (previousSecrets under RS256/ES256/EdDSA) — operators on an asymmetric algorithm use the previousKeys field instead.

    Token verification

    verifyJwt (src/jwt/verify.mts) verifies the tokens this provider issued and throws a JwtVerificationError whose reason is either a finding about the token — a bad signature, a kid nobody holds (kid_unknown), a retired one (kid_expired), expiry, a revocation (revoked) — or an outage: verification_key_unavailable (the keystore could not answer) or revocation_unavailable (the jti denylist or the subject watermark could not be read). isVerificationUnavailable(err) tells the two apart, and VERIFICATION_UNAVAILABLE_DESCRIPTION names the dependency for the wire. Every surface in this repository answers an outage 503 temporarily_unavailable and never with a verdict — not 401 invalid_token, 400 invalid_grant, active: false or a revocation's 200 — because each of those describes the token and sends the client to replace a credential that may be perfectly good. The token is refused either way.

    A subject's revocation boundary (SubjectRevocation.revokedBefore) revokes a token whose iat, or whose auth_time when it carries one, is at or before the boundary: second-truncated, inclusive, and widened by subjectRevocationSkewMs (one second by default). A token without auth_time is judged by iat alone. While a boundary is in force, a token with no iat, or with an auth_time that is not whole, non-negative epoch seconds, is revoked; with none in force, neither is checked. A boundary that is not a valid date is an outage (revocation_unavailable). claimCoveredByRevocationBoundary(claimSeconds, boundary, skewMs) is that rule on one claim, for a grant that checks the boundary before signing, so it never mints a token the verifier would refuse. subjectBoundaryCovers(subjectRevocation, subject, claimSeconds) is that check whole: it reads the subject's boundary once and answers covered, clear or unavailable (with the cause). A claim that is absent or not a finite number is covered while a boundary is in force. A read that throws, or a boundary that is not a valid date, is unavailable, which a grant answers as an outage. A grant calls it as its last read before signing.

    REVOCATION_RETENTION_ALLOWANCE_MS is how long past a token's exp a record that revokes it must be kept: the verifier's clock tolerance, a replica allowance and a second of rounding. /oauth/revoke keeps a denylisted jti that much past exp, and a revoked refresh-token family is kept by the same rule (Refresh-token families).

    A JWT's exp, iat and nbf are NumericDates (RFC 7519 §2) only when finite and within the Date range: isNumericDate and malformedNumericDateClaim (src/jwt/numericDate.mts) state the rule, and the jwt-bearer registry verifier, private_key_jwt and DPoP refuse an assertion or proof that breaks it before computing any expiry from it. jose checks only that such a claim is a number, and JSON's 1e400 parses to Infinity. A fraction is allowed. An assertion whose jti is recorded for single use — a private_key_jwt client assertion, an ID-JAG — may also run at most MAX_ASSERTION_LIFETIME_SECONDS (an hour) past now, and have been issued at most that long ago (src/assertions/lifetime.mts): its replay record lives until exp, so an unbounded exp would be an unbounded record. Both verifiers allow their clock tolerance on top, as for every other time check, and compare exp through the same assertionLifetime, so a client or IdP whose clock runs a little ahead is not refused on one path and admitted on the other.

    Sealing values at rest

    A store that keeps a secret at rest seals it in the v2 key-ring envelope (src/sealing/envelope.mts). sealWithKeyRing(plaintext, ring, { purpose, record }) returns v2.<key id>.<iv>.<ciphertext>.<tag>, AES-256-GCM under the ring's first key. openWithKeyRing(envelope, ring, { purpose, record }) answers an OpenedSeal: ok with the value and the keyId that opened it, so a caller can re-seal a value opened under a key that is no longer first; key_unavailable with the keyId the envelope names when the ring no longer holds it, which an operator undoes by putting that key back; or unreadable for anything else, a value bound to another purpose or record and a tag or IV of any length but 16 and 12 bytes included. It never throws for the envelope. The purpose label (1 to 64 printable ASCII characters, no space) and the record's bytes are authenticated and not stored, so a value copied into another record, or read by another caller sealing under the same ring, does not open.

    A ring (SealingKeyRing: SealingKey entries { id, key }, in src/sealing/keyRing.mts) seals with its first key and opens with any. An ID is 1 to 64 characters of A-Za-z0-9_- (isSealingKeyId) and a key is a Buffer of SEALING_KEY_BYTES (32) bytes. checkSealingKeyRing(ring, setting) refuses a ring that breaks the rule with a RangeError whose message starts with setting: a store calls it when it is built, under the configuration key or option it read the ring from (redis-federation-grant-store.encryptionKeys), so a bad ring is refused at boot and names where it was written. Every refusal names the entry by its index and none quotes an ID: a 32-byte key spelled in hex or unpadded base64url passes the ID rule, so an operator who swapped an ID and its key would otherwise see the key. Sealing and opening check the ring again, as the "sealing key ring", and throw a RangeError on a purpose outside its rule, and sealing on an empty ring. decodeSealingKey reads a configured key: canonical base64 of exactly 32 bytes with no whitespace, or undefined for the caller to refuse, naming its configuration key. @o3co/auth-provider-redis's federation grant store seals its credentials this way, and so does the MFA package a factor's data and a ceremony's state, under the ring configured as mfa.encryptionKeys.

    Plain JSON values

    copyPlainJson(value) (src/json/plainJson.mts) is the one rule for a value JSON gives back as it is, and the copy taken by it. It answers { ok: true, copy } — the copy frozen at every depth, each field read once, an own getter's included, so what acts on the copy acts on what was checked — or { ok: false, at }, naming where the value is not one ("" for the value itself, .name for a field, [index] for a list entry). It takes null, booleans, strings, finite numbers other than -0, plain lists whose own keys are exactly their indices with no undefined entry, and objects of prototype Object.prototype or none whose every own key is an enumerable string; a field read as undefined is left out, as JSON leaves it out. It refuses anything else — a class's instance, a built-in, a function, a symbol's or a hidden field, a cycle, a read that throws, nesting past the stack — and never throws. The MFA coordinator takes a factor's state, data and response by it, and the test kit's mfaFactorContract holds a factor to it. The path's keys are not escaped: it is for a reader.

    Repositories

    Repository interfaces define the data access contract. Built-in in-memory implementations are provided for development and testing.

    Interfaces and types

    Module System

    Modules extend the app with routes, grant handlers and DI-graph components. A module is a declarative manifest written with defineModule({...}): it declares requires / optional (typed ProviderDeps keys), provides components, and contributes to ContributesMap kinds such as grants, routes and federationTypes. The boot planner injects the typed deps into every factory; a module never mutates shared state. The vocabulary is src/modules/manifest/, also published as the @o3co/auth-provider-core/modules/manifest subpath.

    Each mechanism is one axis of the extension surface: a routes, grants or federationTypes contribution adds behaviour (a plugin), a provides fills a port's slot (an adapter), an optional method detected by a supportsX guard is an adapter's extra (a capability), and a contribution kind core composes changes what a core decision means (an extension). AGENTS.md says which one a new policy takes.

    A module that reads configuration declares its own section in the manifest: section.schema is the Zod schema of the one section it owns, and boot parses that section before any factory runs and hands it to every factory as deps.section, typed as the schema's output. A value the schema refuses refuses boot (config-validation-failed), naming the path the operator wrote. The section is read at the module's name — the top-level key named exactly as the module, never split on its dots — and nowhere else: a manifest whose section carries at, or that carries configSchema, is refused (module-section-path-invalid), so no module parses or rewrites any key outside its own section. section.relocatedFrom names the paths the section moved from: a configuration that still sets a key there refuses boot (config-path-relocated), naming the key's new path and the environment variable that binds it, or that the key was removed — a bridge for the 0.x line, removed at the first major release (the relocated-paths drift test fails the cut that forgets). section.renamedVariables names the environment variables whose names changed, each old name mapped to the old path it was bound to (the new name is the one the new path is bound to; a removed key's has none), and the package's reference.conf captures each name in the reserved renamed-variables section: while the resolution captured an old name set, boot refuses (environment-variable-renamed), whether or not it captured the new name set and whatever either holds, as it does for a removed key's variable set or a name not captured. section.reference names the package's config/reference.conf: boot does not read it, and moduleReferences(modules) (src/config/references.mts) answers the references of the modules a composition loads, each once, with core's own (coreReference()) at the bottom, for the composition root to layer beneath its own files; a package checks its reference in its own tests with packageReferenceProblems from @o3co/auth-provider-core/testing. A section's schema is to refuse a key it does not declare, at every object level, so a typo or a key an earlier version read refuses boot (config-validation-failed) naming where it is, instead of being ignored; sectionStrictnessProblems, on the same entry, names each level of a module's section that keeps an unknown key — a level open by design (a record keyed by names the deployment chooses) exempted with its reason — and each level the schema declares that the samples it is given do not reach. Boot writes each module's parsed section back into the configuration at the module's name, so core, reading config, sees what the section's schema made of it; module names are unique (duplicate-module-name), so a section has one owner.

    A module with an enabled key of its own declares it as its switch, section.isEnabled, which boot calls with the parsed section. Answering false, the module registers nothing — no slot, contribution, route, admission action, rate-limit budget, requirement on another slot, absence policy or lifecycle — and none of its factories runs, as if it were not installed; its section is still parsed and its old paths still refused, and a module that requires a slot only it would provide is refused as when it is not installed.

    A module whose state lives in this process's memory says so on its manifest, replicaSafety: { unsafe: true, reason } (ReplicaSafetyDeclaration, src/modules/manifest/module-spec.mts), where reason names what diverges per replica and what that costs: with core.deployment.mode = "multi" boot refuses it (replica-unsafe-adapter), unset warns, and "single" is silent. When the section decides what the module holds — a storage type — replicaSafety is a function of the parsed section, typed as the schema's output, answering the declaration or undefined; boot calls it once, after the parse and only when the module is switched on, and a throw or an answer of any other shape refuses boot (config-validation-failed, naming the module and its section's path). replicaUnsafeReason(module, section) reads a declaration the same way for a module and its parsed section, and checkReplicaSafety takes the parsed sections by module name (sections) for a composition root that runs the guard itself; either throws a TypeError naming the module rather than call a declaration made from the section without the section.

    A section's leaf that an environment variable can set reads the string HOCON substitutes for ${?VAR}. Core exports the readers for those strings, all defined in src/config/application.schema.mts, so every package reads a variable the same way:

    • wholeNumberFromEnv(bounds) reads a whole number. It accepts a number as written, or a string of decimal digits (a whole number), whitespace around the digits allowed. Anything else reaches bounds unchanged and is refused there, with the message bounds gives. That includes an empty or blank string, a string with a sign, a fraction, an exponent ("8e3") or hexadecimal ("0x50"), and null, true or a list. z.coerce.number() would read "", null and [] as 0 and "1e3" as 1000. bounds is a z.number() schema that decides every other rule: an integer check for a number written as one, the minimum, the maximum and the message. The standalone template reads http.port with it, so an exported-but-empty HTTP_PORT fails boot instead of listening on a port the OS picks.
    • wholeNumberInRangeFromEnv(min, max?) is the same reader held to min, and to max when given, refusing every other value with one message that names the range and the form (must be a whole number from 1 to 31536000, in decimal digits). Core reads its token lifetimes (oauth.accessToken.*, oauth.refreshToken.expiresIn), oauth.nonce.maxLength, webauthn.challengeTtlMs, jwks.cacheMaxAge, the core-rate-limiter-memory section, the memory code repository's defaultExpiresIn and the memory federation grant store's tombstoneRetention with it. A number setting that needs a message of its own passes its own bounds to wholeNumberFromEnv.
    • coerceBooleanFromEnv reads a boolean: "true" / "1" and "false" / "0" / "", trimmed and case-insensitive. Anything else fails boot.

    A key several modules read has one owner, and the others receive it through a slot whose contract is core's: the owner parses its own section and provides the value, and in code a package imports only core. Core declares these slots; the session package's modules provide loginCompletion, loginEntry, csrfGuard, sessionCookiePolicy and csrfTokenSigner, the oauth module provides oauthTokenSettings, core fills deploymentMode, tokenBindingSettings, federationSettings and outboundPolicy itself, and the others are declared ahead of their providers:

    • oauthTokenSettings, what other modules read of the oauth module's token settings — src/token-settings/types.mts.
    • loginCompletion, the tail of a login (establishSession, answerInterruption) a requirement's completion finishes with instead of importing the session package, and the renewal of a signed-in session's id after an escalation (renewSession; SessionRenewalCall, SessionRenewalReporter, SessionRenewalResult, SessionRenewalStep) — src/session-admission/login-completion.mts.
    • loginEntry, csrfGuard, csrfTokenSigner and sessionCookiePolicy: the login page with its redirect_to protocol, the one policy for whether a browser may change state — a request's, and a navigation's that starts a flow — the CSRF token's signature, which the owner of the session secret provides to the guard's provider and the session routes (its length bounds are CSRF_SIGNATURE_MIN_LENGTH and CSRF_SIGNATURE_MAX_LENGTH), and the session cookie's attributes — src/browser-session/types.mts. Boot holds csrfGuard to its contract where the slot is filled, by a module or a host map — middleware a function of at most three parameters, check a function, a member whose read throws refused, naming it — and hands every reader one frozen copy of the guard, each member read once, so a reader mounts or asks the guard as it is handed, checking nothing itself.
    • httpSettings (trustProxy, the CORS origins) and deploymentMode (single, multi or unset) — src/deployment/types.mts. Boot fills deploymentMode from the configuration's core.deployment.mode for every composition, before any provider runs, with its one reading of the key (src/deployment/mode.mts), which the replica-safety guard decides by too. It is a synthetic key: a module that provides it, and a bootstrapComponents or overrideComponents entry for it, refuse boot (synthetic-key-collision). A module that refuses or warns by the mode requires the slot, reads nothing of deployment itself, and holds the value it is handed to checkDeploymentMode, which throws a TypeError naming its source for anything but the three values, absence included. deploymentModeOf, the reading itself, is exported for a composition root that builds such a module by hand. Beside it, the one reading of an environment's name (src/deployment/environment.mts): readEnvironmentName trims and lower-cases one, and productionEnvironmentIn answers which of several names — the one a configuration was selected by, CONFIG_ENV, NODE_ENV — says production or staging, for a module refused there; isDevelopmentEnvironment answers whether every one of them that is set says development or test, with at least one set, for a thing let in only there.
    • tokenBindingSettings (dispatchPolicy, bindConfidentialClientRefreshTokens), core's token-binding settings — src/middleware/tokenBinding.mts. Boot fills it from the configuration's core.tokenBinding for every composition, with or without the oauth module, before any provider runs, with its one reader of the section, resolveTokenBindingSettings, frozen; boot mounts the token endpoint's dispatch policy from it. It is in GrantDependencies, so a grant whose module requires it reads the confidential-client binding rule without config.
    • federationSettings (FederationSettings, each entry a ConfiguredFederation), core's view of core.federations — src/federations/settings.mts. Nothing else of an entry, and no secret: the rest is its type's module's. Deeply frozen, and the map inherits nothing, so a name no entry has reads as absent.     • outboundPolicy (OutboundPolicy), the outbound destination policy core.outbound states — src/net/outbound-policy.mts. Not core's grantPolicy, the gate token-minting paths consult (allow or deny, optionally narrowing the scope and audience): this is the federation grants' switch and keep policy. The federation-grants module provides it from its section while it is on, eagerly, and names it authoritative. Boot does not check it.
    • RateLimiter.failMode, the limiter's own outage policy, which the guard applies (closed when it declares none) — src/ratelimit/types.mts.

    App Factory

    createApp(options): Promise<AppHandle> is the boot planner in src/boot/. CreateAppOptions and AppHandle are defined in src/boot/types.mts.

    createApp validates the manifests, composes and parses the configuration, materialises the component graph, applies every contribution, freezes the world and mounts the routes. A refused boot is a BootError (src/boot/types.mts): its message names the error behind it by loggableError's rules — never quoting what a parser quoted, a Redis reply's arguments or a thrown value that is not an Error — and printed (util.inspect, console.error, Node's unhandled-rejection printer) it shows every error it carries as its projection. cause and details.originalError still hold the thrown value, for code that reads them. The returned router is ready to mount (app.use(handle.router)) or to serve through handle.listen(port); handle.dispose() runs every cleanup in reverse-topological order, waits for each, and rejects with an AggregateError carrying every failure; handle.cleanupAllowanceMs is the longest tailMs a cleanup was registered with: the least a host that bounds dispose() allows the whole of it. A tail covers the cleanups around it too, so tails do not add. There is no separate init() step.

    What core mounts on its own, in this order: corsMw when there are origins to let read (CORS), the single tokenBindingMw composed from the contributed mechanisms when at least one was contributed, the protected-resource sender-constraint check (always, on every request but the token endpoint's POST), the grantMiddleware contributions ahead of grant dispatch, the OIDC discovery route when an issuer is configured and a module declares providerRoot, and, after every route, a terminal error handler (src/middleware/terminalError.mts). That handler answers what a route it assembled let through, so none of those errors reaches the host's own handlers (a route a host adds to handle.router after boot sits after it, and is not covered): a body parser's refusal — read by body-parser's own type — is 400 malformed_body, 413 body_too_large or 415 unsupported_encoding (a path Express could not decode, 400 malformed_path) in the RFC 6749 envelope, logged nowhere, and any other exposed http-errors 4xx keeps its status as invalid_request / request_refused, with a 401's WWW-Authenticate or a 405's Allow (up to 1 KiB) when it carries one; anything else is 500 server_error, logged once at error as unhandled_request_error with endpoint and the error's projection; every answer is Cache-Control: no-store and Pragma: no-cache. An error after a response's headers went out is logged the same way, and the connection closed unless the response had already ended. A request no route answered still passes on to the host. The handler is exported as terminalErrorHandler(logger), for a host that mounts routes of its own beside the router and wants the same answer after them. Everything else — JWKS (jwksModule), liveness and readiness (createHealthcheckRouter, createReadinessRouter), the OAuth and session routes — is a module or a router the composition root installs.

    express is an optional peer dependency, loaded lazily: createApp imports it (await import("express")) to build the router, and boot also requires it (createRequire) for the express() factory handle.listen() wraps the router in — and for the router, if the import failed.

    CORS

    The origins corsMw (src/middleware/cors.mts) lets read are the httpSettings slot's cors.allowedOrigins — the standalone template's http module provides it, from http.cors.allowedOrigins. A composition that holds no httpSettings mounts no CORS. A configuration's cors section is read by nothing, and one that sets anything refuses boot (above). assembleApp mounts the middleware first — ahead of every other middleware and every route contribution. An empty list (the default) mounts nothing: no CORS headers and no Vary. A slot whose origins break its contract (an entry checkSerializedOrigin refuses, or no list of strings) refuses the boot with a RangeError naming the member and the index.

    Surface

    browserFacingCorsRoutes(config, { issuer, jwksPath }) is the table, and it is an allowlist — the opposite polarity to the sender-constraint mount beside it. That one guards a credential and must therefore cover routes core has never heard of; this one grants a cross-origin read, so a route core has never heard of is exactly the one that must not silently acquire it.

The /oauth/* paths are coupled to the bundled oauthEndpointsModule's mountPath, like the /oauth/token mounts in boot/assemble-app.mts — a downstream that re-mounts the OAuth router elsewhere builds its own table and passes it to corsMw.

    Headers

    • Access-Control-Allow-Origin carries the matched entry, echoed exactly. An arbitrary origin is never reflected and * is never emitted — not even for the unauthenticated documents, because one code path that can emit * is one code path away from emitting it on a response carrying a token.
    • No Access-Control-Allow-Credentials, ever. A cross-origin SPA here is a public client using PKCE and holds no cookie of ours. Allowing credentials would reach the cookie-backed session grant, which exchanges an authenticated browser session for tokens — a much larger grant than "may read the response to a request it authenticated itself", and CORS delivers the two together.
    • A preflight (OPTIONS carrying Access-Control-Request-Method) is answered 204 with the route's methods, Access-Control-Allow-Headers: content-type, authorization, dpop, and Access-Control-Max-Age: 600.
    • Access-Control-Expose-Headers: WWW-Authenticate, Retry-After — both are diagnostics the caller cannot act on otherwise (an opaque 429 with nothing to back off by; a 401 that will not say which scheme it wanted).
    • Vary: Origin on every response from these routes, including the ones with no CORS headers, so a shared cache cannot serve one origin's response to another.

    Origins

    Entries are validated at boot by checkSerializedOrigin (src/net/origin.mts) and refused by index, because matching is exact string equality: a trailing slash, an explicit :443, an uppercase host, a path, or a wildcard is an allowlist that admits nobody with nothing anywhere to say so. https is required except for a loopback host, through the shared isLoopbackHostname home. corsMw re-applies the same check and warns on anything it drops, so a hand-built AppConfig that never passed the schema cannot install an entry the schema would have refused.

    The list takes two spellings. The comma-separated string an environment variable carries (HTTP_CORS_ALLOWED_ORIGINS) is split on commas, each entry trimmed and empty entries dropped, so an empty variable is no list. An array keeps its string entries, trimmed, and an empty one is refused by the check above; a non-string entry is dropped. null is no list. Any other shape — a number, an object, a boolean, which only a configuration file can write — is refused by the module that provides the slot (the standalone template's http module names http.cors.allowedOrigins). Core reads no cors section: a configuration that still writes one refuses boot, naming it, unless a loaded module relocates it first in its own words. normalizeAllowedOrigins in the same file reads both and is exported; the WebAuthn package reads WEBAUTHN_ORIGIN / WEBAUTHN_TOP_ORIGIN with it, so every origin list set from the environment is spelled alike.

    Usage Example

    import express from "express";
    import {
      type AppConfig,
      createApp,
      createRepositoryFactories,
      createKeyStoreFactory,
      defineModule,
      registerBuiltinKeyStores,
    } from "@o3co/auth-provider-core";

    // The signing key, the repositories and the port are this composition's own
    // sections: core declares none of them and ships no default, so rawConfig
    // carries them as written (the standalone template keeps them in its
    // `config/reference.conf`, each parsed by its own module's schema). Parse them
    // with a schema of your own; createApp parses rawConfig itself (#728).
    type Selected = { type?: string; provider?: string } & Record<string, unknown>;
    const own = rawConfig as {
      "key-store"?: Selected;
      repositories?: { client: Selected; user: Selected; code: Selected };
      http?: { port?: number };
    };
    const signingKey = own["key-store"];
    const repositories = own.repositories;
    const port = own.http?.port;
    if (signingKey === undefined || repositories === undefined || port === undefined) {
      throw new Error("key-store, repositories and http.port are required");
    }

    // Both repositories.* (uses 'type') and key-store (uses 'provider') follow
    // the same nested adapter sub-section pattern. flatten() normalises either selector
    // to { type, ...subSectionFields } before forwarding to the factory:
    const flatten = (section: Selected) => {
      const selector =
        (section as { type?: string; provider?: string }).type
        ?? (section as { provider?: string }).provider;
      if (typeof selector !== "string") {
        throw new TypeError("flatten: section requires 'type' or 'provider' string");
      }
      const sub = section[selector];
      const flattenedSub =
        typeof sub === "object" && sub !== null && !Array.isArray(sub)
          ? (sub as Record<string, unknown>)
          : {};
      return { type: selector, ...flattenedSub };
    };

    const keyStoreFactory = createKeyStoreFactory();
    registerBuiltinKeyStores(keyStoreFactory);
    const keyStore = await keyStoreFactory.create(flatten(signingKey));

    const { clientFactory, userFactory, codeFactory } = createRepositoryFactories();

    const clientRepository = await clientFactory.create(flatten(repositories.client));
    const userRepository = await userFactory.create(flatten(repositories.user));
    const codeRepository = await codeFactory.create(flatten(repositories.code));

    const localComponentsModule = defineModule({
      name: "local-components",
      provides: {
        keyStore: () => keyStore,
        clientRepository: () => clientRepository,
        userRepository: () => userRepository,
        codeRepository: () => codeRepository,
      },
    });

    const handle = await createApp({
      modules: [
        localComponentsModule,
        // additional modules go here
      ],
      bootstrapComponents: { config: rawConfig as AppConfig, pathResolver: import.meta.resolve },
    });

    const server = express();
    server.use(handle.router);
    server.listen(port);

    Extension points

    Five optional extension points: a slot or contribution kind a composition root fills, or leaves empty.

    MFA

    The ports of multi-factor authentication, as the MFA ADR designs them, which the MFA package and its adapters share. The package is @o3co/auth-provider-mfa. It contributes its mfa requirement, which declares the second-factor authority, to session admission (below) and the TOTP factor, and it interrupts a password login with a first binding's or a second factor's transaction (mfa_enrollment_required, mfa_required). The routes that verify a factor and complete the login come with step 8's third part (the MFA ADR's build order).

    • MfaFactor, the contract a second factor implements, and what it is handed — src/mfa/factor.mts. A factor never sees a key, a store or a transaction: it is handed its records' data opened, the state it keeps between two requests of one ceremony, the transaction's id, and keyed digests under the key ring made for it (MfaDigests, for a code it compares and never recovers). A verification takes the pending challenge unless the factor opts in to reuse (reusableChallenge, the email factor); a digest whose key has left the ring answers key_unavailable, an outage, never a wrong code (MfaDigestMatch); a factor says whether a user can enroll it (enrollable), and may answer the identity of the authenticator a record's data holds (identity), a duplicate key: two of a subject's records of one kind with equal identities hold one authenticator enrolled twice. It depends on the data alone — the same whichever factor instance reads it, in whatever order, after later enrollments, and for a verification's next data. It is not an assurance signal: distinct identities do not show distinct devices or mailboxes. undefined is none it can read, and a record with no identity is a duplicate of none, never a distinct authenticator, so a consumer that counts distinct authenticators does not count it. A challenge or an enrollment's start may answer a code for the coordinator to mail (MfaFactorMail): its purpose, never account_email_proof, the code, never in the response, and its expiry. A login code also carries the keyed digest of the address the factor was enrolled with (MfaLoginCodeMail), or null when its data holds none it can read; the coordinator mails it to the account's current address only when that address, normalised, matches it, and otherwise refuses the factor until it is enrolled again. The digest a factor records is the one it is handed: of the address its code went to, kept with the pending state when it was sent, never from a later read of the Store (MfaEnrollmentCompletionContext.addressDigest, MfaVerifyContext.addressDigest). Every call runs under a transaction — outside a login or step-up, an enroll transaction the MFA package opens. A package contributes one as contributes.mfaFactors, keyed by its kind (MfaFactorFactory); a factory answers null when its configuration switches the factor off. Boot projects the contributions through the synthetic key mfaFactorResolver, which leaves out a kind that answered null; that kind stays claimed, so a second contribution of it is a duplicate, and it is no override target: an override of it refuses boot (override-target-missing), so an override never switches on a factor its owner's settings switched off. An override may answer null, which switches off the factor it replaces. The resolver is in place before the provides factories run and fills as boot registers the contributions, so a factory that runs earlier may hold it and read it later — the MFA package's requirement reads it for its reach, which core reads once every factor has registered; a read while the provides factories run refuses the boot. A factor whose kind is not the key it is contributed under refuses boot. mfaFactorContract in @o3co/auth-provider-test-kit is the suite a factor's tests run; @o3co/auth-provider-core/testing has the doubles they use: createTestMfaFactor (a factor with a trivial protocol, with or without a challenge, its proofs in testMfaFactorProofs) and createTestMfaDigests (keyed digests under a fixed test key; { rotated: true }, a ring whose first key is a second one, as after a rotation).
    • MailSender, the port a one-time code the provider issued leaves through, filling the mailSender slot, with MailSend, MailSendResult and the closed list MAIL_PURPOSES (login_code, account_email_proof, email_factor_enrollment) — src/mail/types.mts. send takes what a mail means — its purpose, the account's subject, the address on the user record at that moment, the code and its expiry — and answers { outcome: "delivered" } once the relay holds it or { outcome: "refused_at_limit" }, which the provider answers 429; a rejection, or any other answer, is an outage the provider answers 503. mailSendOutcome is the one reading of that answer, delivered and refused_at_limit only from a plain record whose one data property is outcome (src/mail/outcome.mts); normaliseMailAddress is the one spelling of an address the provider digests, compares and delivers to — trimmed, NFC, the domain in its ASCII form and in lower case, the local part in the case it is written — or undefined for a value that is not one addr-spec: a list, an angle address, a comment, a format character, or a domain a URL parser would cut short, decode or map to ASCII among them (src/mail/address.mts). Rendering, delivery and send limits are the sender's: @o3co/auth-provider-standard holds standard ones. Tests use createRecordingMailSender() from @o3co/auth-provider-core/testing, which keeps what it delivered and can stand in for a sender at a limit (refuseAtLimit) or a relay that is down (failWith, recover); a sender's conformance suite is mailSenderContract, on @o3co/auth-provider-test-kit.
    • The enrollment witness, which keeps a lost factor store from reading as "never enrolled" (D12): User.mfaEnrolled, which the Store answers on authenticate and on authenticateByToken and which is read only through readMfaEnrollmentWitness() — enrolled, not_enrolled (false or absent), or malformed (any other value, answered 503 and never read as "not enrolled") — and the optional UserRepository.markMfaEnrolled(subject, enrolled), detected by supportsMfaEnrollmentWitness() — src/repositories/UserRepository.mts. InMemoryUserRepository has no markMfaEnrolled.
    • MfaFactorStore, where a subject's enrolled factors are kept, and MfaFactorRecord — src/mfa/factorStore.mts. A record's data is sealed before it reaches the store, which keeps it byte for byte; update is a compare-and-set on version, and one at Number.MAX_SAFE_INTEGER, whose next version would be no safe integer, is a RangeError that writes nothing (checkMfaVersionAdvances, src/mfa/version.mts); a store that cannot answer throws rather than answering "no factors". A subject's records are one set with a store generation, which follows core's conditional-write convention for a set (docs/adapter-surface.md, "Conditional writes"): listVersioned reads it with the records, and createIf / removeIf write only at the generation the writer read (readMfaFactorSet, readConditionalCreateAnswer, readConditionalSetRemoveAnswer read the answers); every membership write, the unconditional removeAllForSubject included, issues a fresh one, and update keeps it. How the factor set keeps the write-lifetime bound is stated once, on MfaFactorStore in src/mfa/factorStore.mts. The three are required members of the port, as list and update are; the port has no unconditional create or single-record removal. The in-process adapter createMemoryMfaFactorStore() (its now option is the clock an emptied set's tombstone expires by) and its module memoryMfaFactorStoreModule are for development and a single replica: a restart empties them, which the module warns about once (mfa_factor_store_in_memory), and core.deployment.mode = "multi" refuses the module. createMfaFactorStoreFactory() / registerBuiltinMfaFactorStores() build it by name. Every adapter runs mfaFactorStoreContract, the suite in @o3co/auth-provider-test-kit, and mfaFactorStoreConditionalContract beside it; the kit's own tests run both over the in-process adapter.
    • The wire format of the Store's MFA endpoints — src/mfa/storeWire.mts: the JSON bodies of list, create, update, delete and markMfaEnrolled (MfaStoreFactor, MfaStoreFactorChanges, MfaStoreUpdateRequest, …), and their codec (toMfaStoreFactor, readMfaStoreFactor, fromMfaStoreFactor, readMfaStoreListAnswer, toMfaStoreFactorChanges, readMfaStoreFactorChanges, toMfaStoreUpdateRequest, and for the factor set's generation readMfaStoreVersionedListAnswer, toMfaStoreCreateIfRequest, readMfaStoreCreateIfAnswer, toMfaStoreRemoveIfRequest, readMfaStoreRemoveIfAnswer), read by the Store adapter and by a Store's own implementation or a fake of one. Times are epoch milliseconds named …Ms; an optional field with no value is left out, and a record carrying null is one readMfaStoreFactor does not read; nor is one whose id, kind or label — the fields a page shows — is outside the record's shape: isMfaFactorId (22 base64url characters), isMfaFactorKind (a hint token), isMfaFactorLabel (1 to MFA_FACTOR_LABEL_MAX_LENGTH, 64, characters, none that breaks or reorders a line), in src/mfa/factorStore.mts. A list is read whole: one unreadable record, one naming another subject, or two with one id make it unreadable. What a writer makes, the reader reads back whole, and what the reader refuses, the writer refuses with a RangeError; an update names the record by subject and id and carries the expected version and, as its changes, only data, label and lastUsedAtMs, and changes carrying any other field are not read. The factor set's generation travels under core's conditional-write HTTP wire (docs/adapter-surface.md, "Conditional writes"): readMfaStoreVersionedListAnswer reads a list's 200, factors with the set's generation (required, and null only for an absent set, which holds no factors), as the port's VersionedSet of records; toMfaStoreCreateIfRequest and toMfaStoreRemoveIfRequest carry expectedGeneration (null only on a create, for a set read as absent) and a required deadlineMs, an instant in epoch milliseconds on the provider's clock, the send time plus the adapter's request timeout: the Store checks deadlineMs against its own clock in the same atomic step as the conditional write; at or after it, the write is not applied and the answer is 408. This assumes the provider's and the Store's clocks agree within the clock skew assumed between the two; under that assumption a conditional write commits or fails within W, the request timeout plus that skew. The builders refuse, with a RangeError, a generation that is no store generation and a deadline that is not a whole instant above 0 within the Date range; readMfaStoreCreateIfAnswer and readMfaStoreRemoveIfAnswer read a status with its outcome body (200, 404 for a removal only, 409) as the port's answer, through the convention's readers. Each of these readers throws a TypeError for any other answer, a 404 or 409 without its body, a 408, and a generation holding " included. readMfaStoreListAnswer is unchanged, and ignores a generation. What each answer means is @o3co/auth-provider-foundation's.
    • MfaTransactionStore, where MFA transactions and the subject lock state are kept, with MfaTransaction, MfaTransactionPatch and MfaLockoutPolicy — src/mfa/transactionStore.mts. A transaction is the single-use record of one second-factor ceremony, bound to what started it through binding — MfaTransactionBinding, a union discriminated by kind, { kind: "session", id } (MfaSessionBinding) alone today (#742) — which a store keeps whole; every use compares the whole binding, kind included (isMfaTransactionBoundTo), and reads a transaction through it (getBoundMfaTransaction, which answers one bound to anything else as an unknown id). reserveAttempt, takeChallenge and consume are atomic, so attempts in flight are each spent, a challenge is answered once and one verification consumes the transaction. A binding holds at most MFA_MAX_TRANSACTIONS_PER_BINDING (5) live transactions: create past it ends the one that expires first — the oldest — never the one it creates, and never another binding's; consumed, attempt-ended and expired transactions do not count. An adapter whose create and count are not one atomic step (Redis) may hold more while creates are in flight; only a step that failed leaves an excess, until it expires. create refuses a field its type does not admit — a binding of a kind it does not know, or with an empty id, among them — and a record that does not start from a fresh count, and keeps only the fields a transaction has (newMfaTransactionRecord); update writes only its patch keys — a value sets, null clears a field that may be empty, undefined is absent, anything else is a RangeError (mfaTransactionPatchWrites) — and refuses a transition that would undo a requirement: a required email proof other than met, a met one undone, enrollment lowered (checkMfaTransactionTransitions) — and refuses an update at Number.MAX_SAFE_INTEGER, whose next version would be no safe integer, with a RangeError, before anything is read or written (checkMfaVersionAdvances, which the factor stores call too). Every adapter calls the four. Every operation answers a transaction at or past its expiresAtMs on the store's own clock as absent — reserveAttempt and takeChallenge too, spending and taking nothing — whatever a shared backend's clock says. The subject state is the lock on guessable proofs, judged on the time each caller passes, so the callers' clocks must agree: the consecutive run (a short backoff from threshold failures, doubling to maxSeconds and forgotten memorySeconds after the last lock ends — or, before any lock, after the previous failure; a hold fixed when the run, reservations in flight counted, reaches hardLimit, which no time, no settle, no exempt success and no higher hardLimit lifts; a success ends the run up to its own reservation), and the weekly budget of failures in any rolling seven days (MFA_WEEKLY_WINDOW_MS) that no success refunds and no attempt bypasses; a refused reservation says whether it is the first refusal since an attempt was let through (first), so a hold is told apart from the refusals that repeat it; an exempt success (noteExemptSuccess(subject, nowMs, policy)) ends the run up to its time until the hard hold is fixed — a run it finds at hardLimit fixes the hold instead, and an attempt after its time always stays — and answers nothing. readMfaSubjectAttemptReservation(answer) is the one reading of what reserveSubjectAttempt answers: a pass with its reservation, a non-empty string, or a hold the port names with a boolean first and a time to come back — null for the hard hold, else a finite number of milliseconds above 0 — anything else being an outage, never a pass or a hold. A store forgets a failure only MFA_CLOCK_SKEW_ALLOWANCE_MS (a day) after it stops counting, judged no later than its own clock, so a caller ahead by less than that erases nothing another still counts, and a caller far ahead, on any subject, erases nothing. An applied recovery is the one way the lock state ends early and the one way a hard hold lifts; no revocation and no credential change applies one. A recovery is authorized once (authorizeSubjectRecovery: a recover minted at an exempt proof in one session, or the operator's reset; one slot per operation and session, which a new authorization replaces, pending or applied) and applied once under the subject's lease (applySubjectRecovery): a recover gives the week back only when the earliest failure it counts up to the caller's time comes before the subject's sessions boundary by more than DEFAULT_CLOCK_SKEW_MS (a boundary further ahead of the caller's time than that is refused), and lifts the hard hold on a rebind — no record of an installed guessable kind created before the hold, named by the earliest such record's time or null when none remains (a recover naming neither is refused) — ending the run the hold counted; a reset ends the lock state whole and every other authorization. Every answer says whether the hard hold still stands and, while it does, from when a rebind counts (rebindAfterMs: the hold's time plus DEFAULT_CLOCK_SKEW_MS, whole epoch milliseconds, an exclusive bound — a guessable record created after it is a rebind, one created at or before it is not — and the bound the apply judges a rebind by; null while no hold stands); readMfaSubjectRecoveryAnswer refuses one an apply cannot give, a missing or inconsistent rebindAfterMs included. Each applied recovery moves the subject's generation (subjectGeneration) by one, and the generation moves only under the subject's lease (acquireSubjectLease, releaseSubjectLease): a writer of the subject's factor set captures it before it begins and acquires the lease under it (the generation is required), so a write begun before a recovery or a reset is refused stale when it acquires the lease to commit, and a release answering false tells a write that outlived its lease. The lease is logical, on the store's clock, from MFA_SUBJECT_LEASE_MIN_MS to MFA_SUBJECT_LEASE_MAX_MS (DEFAULT_MFA_SUBJECT_LEASE_MS, a minute). The store also keeps the subject's recovery-set floor (recoverySetFloor), below which no recovery-code set verifies, raised under the subject's lease to a recovery-code set's generation — a set's, not the subject's (raiseRecoverySetFloor(subject, { setGeneration, leaseToken }), lease_not_held without the lease); nothing lowers it, a reset included. Beside the lock, the store keeps the operator reset's email-proof requirement until the subject's next first binding consumes it (requireEmailProofAtNextBinding, emailProofRequiredAtNextBinding), under the subject's lease: the lease checked and the requirement cleared in one atomic step, so a consume that lands after its lease ended clears nothing a later reset set (consumeEmailProofRequirement(subject, { leaseToken }), answering consumed, absent, or lease_not_held without the lease; readMfaEmailProofRequirementConsumeAnswer is the one reading of the answer, and checkEmailProofRequirementConsume the check every adapter runs first); an applied recovery leaves it. It also keeps the account-email proof (D24) given in one session of a subject (recordSessionEmailProof(subject, sid, provedAtMs, untilMs), which replaces an earlier one for that session), and answers when it was given, no later than the time asked about, while its untilMs is after both that time and the store's clock (sessionEmailProofAt(subject, sid, nowMs)); another session, or the same sid under another subject, is never answered. checkSessionEmailProof — on the store's clock: an untilMs after it, a provedAtMs no further ahead of it than MFA_CLOCK_SKEW_ALLOWANCE_MS — checkSessionEmailProofQuestion (a time from the epoch) and sessionEmailProofAnswer are the rules every adapter records, is asked and answers by, and readSessionEmailProof(answer, nowMs) the one reading of the answer, anything but null or an instant up to nowMs being an outage. A lost proof fails closed: the user proves again. It also keeps a subject's first-binding mark — when a first counting factor was last bound for the subject, or its witness marked (noteFirstBinding(subject, atMs, untilMs)) — keeping, of the mark held and the one noted, the later time and the later end (laterFirstBindingMark), so no note moves it back or shortens it; a note answers the mark that stood before it, its atMs or null, read and replaced in one atomic step, so a caller learns of a mark that landed after its own read. The store answers atMs, never moved earlier, while its untilMs is after the store's clock (firstBindingAt(subject, nowMs)): the store's clock alone ends a mark, never the time asked about. checkFirstBindingNote (the shape, then, on the store's clock, an untilMs after it and an atMs at most DEFAULT_CLOCK_SKEW_MS either side of it), checkFirstBindingQuestion and firstBindingAnswer are the rules every adapter notes, is asked and answers by, and readFirstBindingAt(answer, nowMs) the one reading of the answer, anything but null or a whole instant up to nowMs plus DEFAULT_CLOCK_SKEW_MS being an outage. An applied recovery leaves the mark: it is not lock state, and clearing it would trust a stale session. The mark does not stand in for the enrollment witness: it covers only the window in which a session's recorded witness can be stale. The stretch between a mark's note and the witness's mark is a documented residual (the MFA ADR's D12): the mark is noted once, so a sign-in past it can make a first binding only when all three hold — a request stalled past DEFAULT_CLOCK_SKEW_MS between its note and its witness's mark; another sign-in of the same subject in that stretch; and a lost factor-store record, the one that request wrote. A mark a store cannot read is an outage, never absent: an absent mark trusts the session. checkMfaLockoutPolicy(), the store's port check, refuses a policy a store cannot apply with a RangeError, among them a threshold above hardLimit and a hardLimit above NIST's 100 (MFA_LOCKOUT_MAX_HARD_LIMIT), and answers the copy it checked, each field read once, for the store to apply. checkConfiguredMfaLockoutPolicy() checks a policy a deployment configures: the port check, then hardLimit at least MFA_LOCKOUT_MIN_HARD_LIMIT (10) and above threshold, and maxSeconds at most MFA_LOCKOUT_MAX_BACKOFF_SECONDS (a week). The in-process adapter createMemoryMfaTransactionStore() and memoryMfaTransactionStoreModule are for development and a single replica: a restart forgets the lock state, the first-binding marks and the email-proof requirement, which the module and the memory builder warn about once per store built (mfa_transaction_store_in_memory), and core.deployment.mode = "multi" refuses the module; the adapter holds at most core-mfa-transaction-store-memory.maxEntries entries, transactions, session proofs, first-binding marks, subject leases and recovery authorizations together (not subjects' generations or floors, which a restart forgets) (DEFAULT_MEMORY_MFA_TRANSACTION_STORE_MAX_ENTRIES, a hundred thousand), and at the cap refuses a new one with MfaTransactionStoreFullError, a store fault, rather than evict a live one; createMfaTransactionStoreFactory() / registerBuiltinMfaTransactionStores() build it by name. Every adapter runs src/mfa/__tests__/transactionStore.contract.mts and, for the consume of the email-proof requirement, src/mfa/__tests__/emailProofRequirement.contract.mts, and, for what a note of the first-binding mark answers, src/mfa/__tests__/firstBindingNote.contract.mts.
    • The one reading of a session (sessionAuthentication, vouchedAmr, SessionAuthentication), which splits a session written before UserSession.authentication existed as it reads it, and what a session requirement is asked about it (requirementSession(session)) or about a token with no live session (requirementSessionFromAmr); the same file holds what each login path records (passwordSessionAuthentication, federatedSessionAuthentication), whether a federation's upstream IdP's amr counts (federationTrustsUpstreamAmr, core.federations.<name>.trustUpstreamAmr) what a verified second factor makes of a session (sessionAfterSecondFactor, checkSecondFactorEvent), what a store may record as authentication (recordableSessionAuthentication) and as authTime (recordableAuthTime), and how fresh a session's authentication is (authenticationFreshness, sessionFreshness: the earlier of authTime and the upstream's authentication.upstreamAuthTime, never fresh when that is null, authTime when it is absent) — src/user-sessions/authentication.mts.     Session admission

    The one decision every consumer of an authenticated browser session calls, and the contract of the requirements that extend it, as the session-admission ADR designs them. What the decision guarantees — the order of its checks, what fails closed, what is branded and refused — is kept in src/session-admission/README.md. This section says what each public name is for and where it is defined: the admission functions and the claim builders in src/session-admission/admit.mts, the types and the requirement contract in src/session-admission/requirement.mts, the grades and what a consumer registers for an action in src/session-admission/actions.mts.

    • A consumer calls admitSession(deps, request) and maps the Admission it answers to its own protocol. An admitted admission carries view, admission's SessionView of the record (null without one), and a step_up its view: the session's facts are read there, never off the record. An admitted admission also carries renewalNonce, the record's renewal nonce as admission read it, absent when the record holds none or a value that is not a nonce: what a consumer that writes the record next (recordSecondFactor's expectedRenewalNonce) expects of it, never the cookie session's nonce over a record without one. The view's secondFactorRecordable says whether a second factor can be recorded on the session — the store's step-up capability and canRecordSecondFactor over the record, decided once per admission — and every requirement is handed the same answer in its copy of the view. A session whose lifecycle record is closing or closed is not_live (closing), where the consumer hands its sessionLifecycleStore (AdmissionDeps.sessionLifecycleStore); a cookie session that does not hold the renewal nonce an escalated record carries is not_live (renewed); the nonce's one spelling is newRenewalNonce, isRenewalNonce and RENEWAL_NONCE_BYTES (src/user-sessions/renewalNonce.mts); a store reads an event's nonces with readRenewalNonces and compares them with expectsRenewalNonce. A step_up carries the requirement's page as registered (RegisteredStepUpPage): resolved once, at registration, on the issuer (oauth.jwt.issuer) to page.href — one absolute URL with the page's params on its query and no return parameter — which a consumer answers or navigates to; none resolves a page itself. The request carries a SessionClaim from one of core's builders — cookieClaim, codeClaimFirstRead and codeClaimRevalidation, linkClaim, tokenClaim — never one the consumer made, and the name of an action the consumer's module registers under contributes.admissionActions — an AdmissionActionDeclaration, { grade }, one of ADMISSION_GRADES but remediation (ActionGrade). Admission hands the requirements the grade the action registered and refuses a name nothing registers; a deployment's own route registers its actions as a bundled consumer does. grants_nothing exempts an admission a record carries (a cookie, a code, a link) from the MFA requirement's baseline — a token is judged on its own amr whatever the grade; boot says each registered action with its grade and module (admission_actions_registered). A package whose handler a composition may mount by hand exports what it admits (DEVICE_GRANT_ADMISSION_ACTIONS, OAUTH_ROUTER_ADMISSION_ACTIONS); the handler refuses to be built on a resolver that does not register them. deps (AdmissionDeps) is the consumer's own slots and sessionRequirementResolver, the synthetic key the consumer lists in its requires. A consumer factory built by hand takes the resolver as a required option and checks it at construction with checkResolver(requirements, factoryName, admits), which refuses a missing or forged resolver, and one on which an action in admits is not registered, by the factory's name. A test builds one with resolverForTests from @o3co/auth-provider-core/testing, registering the actions its consumer admits ({ actions }). For an unavailable answer, describeAdmissionOutage(store) is the text every consumer gives its client.
    • A login builds a password login's primary with passwordPrimary(facts) and asks admitPrimary(deps, primary), which answers an Establishment to write the session with or an interruption to answer (isEstablishment, isInterruptAdmission). The federation callback builds its establishment with establishWithoutAsking(login), without asking. Each primary carries enrollmentFacts, derived from its user and never from a caller's object, which establishSession records on the session and admission hands a requirement a copy of in its view (SessionView.enrollmentFacts). A route that admitted a subject over the cookie's claim reads the cookie session's user through cookieSessionUser(req, subject), read back as a login reads one and answered only for that subject. A login reads its User into a plain snapshot — exactly the fields User declares, each by name, once, however the object holds it (a class instance's getter, an ORM entity's), arrays and plain objects inside copied the same way, nothing else of it — and derives the primary's user, which req.session.user holds, and its facts from that snapshot alone. It refuses a User that is not an object, an id that is not a non-empty string or not the subject, and a declared field holding what JSON does not hold as it is, which left out would read the witness as not enrolled; a getter that throws is let through as it threw. A requirement that completes its interruption calls resumePrimary(deps, continuation, completed) with the PrimaryContinuation it kept in its own record; checkPrimaryContinuation (src/session-admission/primary.mts) is the shape such a record is held to — the MFA transaction store's create holds a login's continuation to it; it does not know the registration, and resumePrimary holds each entry to its requirement's declaration. @o3co/auth-provider-session's establishSession and answerInterruption take what these answer; a requirement's completion — the MFA package's — reaches them through the loginCompletion slot, whose contract — LoginCompletion and its call, reporter and result types — is src/session-admission/login-completion.mts.
    • A requirement is a SessionRequirement, contributed under contributes.sessionRequirements by its name, and a composition names what it expects in core.sessionRequirements.expected. Its own route admits with the remediation actions issuedRemediationActions(requirement) gives the object its factory returned (IssuedRemediationAction). It decides by the action's grade, over every one of ADMISSION_GRADES, never by an action's name. checkStepUpPage is the rule its stepUpPage is held to, and isHintToken the grammar of an interruption's hint values. A requirement that declares secondFactorAuthority is the one that may vouch for a second factor (SECOND_FACTOR_AMR, mfaAt), whatever its name, and boot binds it to the MFA ports; at most one may declare it, and a second refuses the boot (duplicate-second-factor-authority). A composition names the requirement it holds to the authority in core.sessionRequirements.secondFactorAuthority; once that is written, boot refuses a name the list does not expect, or a requirement registered under it that does not declare the authority (second-factor-authority-not-declared). Core reads neither mfa.mode nor a requirement's name for this. sessionRequirementContract in @o3co/auth-provider-test-kit is the suite every requirement runs.
    • The acr vocabulary — readAcrTable, stepUpReach, producibleAmr, vouchableAcrTable and SECOND_FACTOR_AMR, which oauth's drop of unsatisfiable entries and its discovery read — is src/session-admission/acr.mts. What a key of the table may be, and the one wording of the refusal of any other — checkAcrValueName, which every schema declaring the table uses — is src/config/acr-values.mts.

    Audit

    • AuditSink.record(event) fire-and-forget
    • Factory: createAuditSinkFactory(), built-in "console" via registerBuiltinAuditSinks()
    • Errors swallowed by core — audit failure never blocks auth flow
    • Several sinks: a module contributes auditHooks, each an AuditSink, and the auditSink slot then holds core's fan-out (createAuditFanOut, src/audit/factory.mts) over the slot's own sink and every hook. Each is called at once, in registration order (the slot's sink first), and handed one deeply frozen copy of the event (a date's setters refused; an object that is not plain data is shared as it is); a rejection, a synchronous throw or an answer that is not a promise is that sink's failure alone, logged at error as audit_sink_failed with sink — 0 the slot's own sink, n the nth hook, as boot's audit_hooks_registered line names each with its module — and the event's type, nothing else of the event. record resolves once every sink has settled and never rejects, so behind it the subject-revocation auditor's federation_grant_audit_failed no longer fires; core neither retries nor times a sink out. The slot's own sink is handed the frozen copy too, so a sink that mutates its event fails there (audit_sink_failed). The slot's readers change nothing, and hooks alone fill it, for a module's requires and for its absence policy. The fan-out is frozen: a write to it (deps.auditSink.record = ...) throws a TypeError in strict-mode code. The slot's own sink and the hooks are not frozen, and without a hook the slot holds the sink as it was given. An event recorded while a hook's record runs, in its async context (a promise chain or a timer it starts, a detached emitAuditEvent), reaches the slot's own sink alone, or nowhere without one, logged at warn as audit_sink_reentered; a lost event is never silent: the line is logged even when no sink is left. The guard is best effort. It covers an awaited record, a detached emitAuditEvent, a timer and a promise chain started inside a hook's record, and the indirect loop through another module's component that captured auditSink. It does not see work a hook hands to a queue consumer, a setInterval, a MessagePort or worker, or a promise continuation created outside the hook, nor work run through AsyncLocalStorage.snapshot() or AsyncResource.runInAsyncScope: those are the hook author's to avoid, and a hook must not emit from record. A long-lived resource a hook creates inside record (a timer, a pool) carries its context, so that resource's later events skip every hook and are reported audit_sink_reentered: create such resources at factory time. The slot's own sink must not record into the auditSink slot, and a logger that turns audit_sink_* lines into audit events loops without bound; neither is guarded. A hook's record must be a function, and the collector is core's: a host collector for auditHooks refuses boot (contribution-kind-guarded). Tests use createRecordingAuditSink() and auditHooksModule(name, ...sinks) from @o3co/auth-provider-core/testing
    • Every built-in event reaches its sink through recordAuditEvent(sink, event) (src/audit/factory.mts) — emitAuditEvent calls it and detaches; an emitter that waits on its sink (federation grants) calls it directly and gets the sink's promise. It hands the sink the event with ip an IPv4 or IPv6 address (net.isIP, an IPv6 %zone stripped) or left out — an SIEM that maps the field as an IP type rejects a whole event over X-Forwarded-For: x — and userAgent sanitised and capped as auditErrorText does (RFC 6749 NQSCHAR, ? for anything else, at most 200 characters); either is dropped when it is not a string. Behind trust proxy, req.ip is what the caller wrote in X-Forwarded-For, and a user agent is the caller's own header. An ordinary address or user agent is carried unchanged, the event keeps its own key order, and a sink that throws synchronously or answers something that is not a promise never throws into the route. Besides emitAuditEvent, two emitters call it directly: the federation-grants routes' bridge, which returns the sink's promise for core to bound and a shutdown to drain, and oauth's subject-revocation auditor, which logs a rejection (federation_grant_audit_failed) rather than waiting on the sink. logErrorProjection.drift.test.mts pins that nothing else in the workspace writes a sink
    • An event carries an error it reports as details.cause, auditedError(err) (src/audit/auditedError.mts): { name, code?, cause?: { name, code? } } — the name and code loggableError reads, and one level of its cause, sanitised and capped, and never a message. A sink is a record other systems read, and a store's or an IdP's message is theirs: the arguments a Redis reply quotes, the input a JSON parse error quotes, an upstream's description. rate_limit.unavailable, introspect.store_unavailable and federation.logout.idp_unreachable carry it
    • Each details key keeps one type in every event, because a sink that fixes a field's type on first sight (Elasticsearch dynamic mapping, a BigQuery schema, a Datadog facet) drops the events that disagree: details.error is a string wherever it appears (an OAuth code, a reason), and a code in details.cause is a string. AuditEventDetails types both keys, and auditEventInventory.drift.test.mts reads every emission for them
    The details contract: AuditEventDetails and AuditedError

    AuditEvent.details is AuditEventDetails: an open record, with two keys typed so that no event can give them a second type:

    Key Type What it holds
    details.error string An OAuth error code or a refusal's reason — never an error object and never an error's message
    details.cause AuditedError The error the event reports: { name: string, code?: string, cause?: { name: string, code?: string } }

    Every other key is open, and is still expected to keep one type across the events that carry it.

    • A custom emitter (a module calling emitAuditEvent or recordAuditEvent, or a sink wrapper that builds events) — one that calls sink.record itself skips the bound on ip and userAgent:

      • puts an error it reports under details.cause, built with auditedError(err) and nothing else;
      • never writes an error object, its message or its stack anywhere in details;
      • writes details.error only as a string.

      An event written as an object literal is held to the two keys by the compiler. A details built first as a Record<string, unknown> is not, so an emitter that assembles one owns the rule itself.

    • A custom sink (an AuditSink implementation, or a wrapper that relays events):

      • may rely on details.error being a string and details.cause an AuditedError wherever they appear;
      • if it transforms or redacts details, keeps those types: a cause it will not carry is replaced with an AuditedError ({ name: "[redacted]" }, say), never with a string or a message;
      • may drop a key, but should not change its type.

      Every name and code in an AuditedError is already held to printable ASCII without " and `` and capped at 200 characters.

    • The rateLimiter slot is the deployment's abuse control: optional to wire, not optional to decide. Wherever a module reads the slot, core attaches RATE_LIMITER_ABSENCE_POLICY, so a composition that wires no limiter must list it in core.declaredAbsent (core.declaredAbsent = ["rateLimiter"]) or boot refuses (component-absence-undeclared).     Attempt counter

    A verifier's own attempt limit — what a module that checks a secret allows per key — runs on its own port, apart from the rate limiter, whose budgets and outage policy are the deployment's.

    • The port is AttemptCounter in src/ratelimit/attempts.mts, the attemptCounter slot's value: consume(key, spec) counts one attempt in a fixed window and answers allowed, remaining and resetAt. The spec (AttemptSpec, { limit, windowSeconds }, the window at most a day, MAX_ATTEMPT_WINDOW_SECONDS) is handed in on every call by the module that owns the limit, so no deployment configuration loosens it; a counter takes no limit of its own. A refused attempt counts nothing, and a key is at most 512 characters (MAX_ATTEMPT_KEY_LENGTH). A counter's answer is read only through readAttemptCount, which refuses one that is not a count under the spec, a window's end more than ATTEMPT_COUNT_CLOCK_ALLOWANCE_MS (5 s) before now or after now plus a day included: the bound is the longest window any spec allows, so a window started under an earlier, longer spec on a shared store is a count, not an outage
    • createAttemptGuard (src/ratelimit/attemptGuard.mts) is the one way a route counts: perIp() keys <tag>:ip:<ip> and takes an onRefused(req, count) hook for the owning module's audit; attempt(req, res, id) keys <tag>:<id>. An id past 128 characters, or one starting h:, is keyed as h:<sha256 hex>, so no long key or raw value reaches a store. Use one key kind per guard — build a guard for per-IP keys and another for per-user keys — so cheap keys of one kind never push out the other's windows. A hook that throws or rejects is logged attempt_refused_hook_failed and changes nothing. It owns the per-process fallback when no counter is wired (refused under core.deployment.mode = "multi", warned attempt_counter_not_shared when unset, silent under "single", sized by maxEntries); failing closed — a counter that throws, does not answer within timeoutMs (default DEFAULT_ATTEMPT_COUNTER_TIMEOUT_MS, 2 s) or answers a malformed count is an outage, answered 503 (attemptCounterUnavailableEnvelope) whatever the counter declares, logged attempt_counter_unavailable and audited rate_limit.unavailable; and what a response tells: a refusal is a 429 with Retry-After alone, and every answer it writes carries Cache-Control: no-store. It never sends RateLimit-*, which would tell whoever guesses a secret how many guesses are left and when more come
    • The in-process counter is createMemoryAttemptCounter (src/ratelimit/attemptsMemory.mts), per process and lost on a restart. It holds at most maxEntries keys (DEFAULT_MEMORY_ATTEMPT_COUNTER_MAX_ENTRIES, a hundred thousand). Full, it drops the windows that have ended and then evicts, in one scan, a batch of one in a hundred of maxEntries (at least one): the live windows with the fewest attempts, the ones that end first among equals, so a key that has spent its limit outlives a flood of fresh keys. It warns attempt_counter_evicted with counts and its tag only, at most once a minute. Refusing instead would let a flood of fresh keys lock out every new client
    • Suite: attemptCounterContract on @o3co/auth-provider-test-kit

    Refresh-token families (RFC 6819 §5.2.2.3 replay detection)

    • The port is RefreshTokenFamilyRotation / RefreshTokenFamilyRevocation in src/refresh-token-family/types.mts
    • Every rt+jwt carries a family_id claim
    • Provide the refreshTokenFamilyRotation / refreshTokenFamilyRevocation slots (a family store — memoryRefreshTokenFamilyStoreModule or the Redis adapter — with defaultRefreshTokenFamilyRotationModule and defaultRefreshTokenFamilyRevocationModule) for replay detection and family revocation. oauthAuthorizationGrantsModule refuses to boot with the refresh_token grant on unless both are wired (the oauth package)
    • A revoked family is remembered until the last access token it could have minted stops being accepted: the revoking write — a revocation, or the replay that revokes the family — keeps the record until the later of the family's own expiry and now plus oauth.accessToken.maxExpiresIn, plus REVOCATION_RETENTION_ALLOWANCE_MS (src/refresh-token-family/retention.mts). A family whose record has already run out is recorded as revoked all the same. createRefreshTokenFamilyRevocation and createRefreshTokenFamilyRotation take that horizon as accessTokenHorizonMs (resolveFamilyAccessTokenHorizonMs(config)), and the default modules read it from config
    • The memory store forgets every family on a restart, revoked ones included, so an access token of a family revoked before the restart passes the family check afterwards until it expires; it is single-replica and development only

    GrantPolicyHook (scope / audience / token exchange policy)

    • GrantPolicyHook.evaluate(request, ctx) returns allow (with optional narrowing) or deny
    • Only an outcome that is exactly "allow" allows and only one that is exactly "deny" refuses. Anything else — another string or case, no outcome, a value that is not an object, a field that throws when read, an element of grantedScope or grantedAudience that is not a string — is an invalid decision, never allow: 500 server_error with the description policy_decision_invalid at /oauth/token, error=server_error on the /oauth/authorize redirect, logged as grant_policy_decision_invalid (error) with the policy's kind and never the decision, and audited as a failure with reason policy_decision_invalid. Every grant that consults the policy, and /oauth/authorize, reads a decision with readGrantPolicyDecision, which writes the line on core's console logger when it is handed no logger (grants/grantPolicy.mts). It hands back a plain copy of the decision, each field read once and an array copied, so a getter or a proxy cannot answer a check one value and its use another; the caller acts on the copy alone
    • A policy that throws is never allow: core's answer is policyUnavailable(), 503 temporarily_unavailable with the description policy evaluation unavailable, which evaluateGrantPolicy gives every grant that consults the policy through it
    • At the token endpoint a deny is answered by policyDenied (grants/grantPolicy.mts), which evaluateGrantPolicy applies for every grant: 400 with the deny's error when it is a token-endpoint code — RFC 6749 §5.2's invalid_request, invalid_grant, unauthorized_client, unsupported_grant_type or invalid_scope, or invalid_target (RFC 8707 §2, RFC 8693 §2.2.2) — and invalid_request for any other code — invalid_client (§5.2 answers it 401 with a WWW-Authenticate challenge to a client that authenticated by header, which a refusal's fixed 400 cannot), access_denied, RFC 8628's polling codes (authorization_pending, slow_down, expired_token), another extension code, a malformed one. Not invalid_grant, which clients read as a dead grant (an SDK discards its refresh token on it); a grant whose refusal really ends the grant names its own code as evaluateGrantPolicy's denyFallback, and the codes its own specification registers as denyAllowed — the device grant, whose poll has spent the approval, passes RFC 8628 §3.5's terminal access_denied and expired_token and answers anything else invalid_grant. authorization_pending and slow_down, which tell a device to keep polling, never pass. policyDenied takes the deny readGrantPolicyDecision read, never a raw decision. The errorDescription is repaired to RFC 6749 §5.2's characters and capped at 200 characters (auditErrorText); one that is empty or not a string is not sent. The refusal carries policyDenial (the policy's own code, sanitised and capped), which /oauth/token audits as token.issued.failure with reason policy_denied and policy_error, so a policy's refusal reads apart from a malformed request; it is never sent. A rewritten code is logged as grant_policy_refusal_rewritten (warn) once per policy instance, code, grant type, site and answer, with the policy's code sanitised and capped and the code answered; a logger with no warn sends it to core's console logger every time
    • At /oauth/authorize a deny's error must be an RFC 6749 error code, 1*NQSCHAR: non-empty printable ASCII without " and \ (isWellFormedErrorCode, errors/envelope.mts); any other code is answered access_denied, logging the policy's code sanitised
    • /oauth/authorize evaluates once; /oauth/token re-uses grantedScope / grantedAudience persisted on the Code record (no re-evaluation for authorization_code)
    • Every other bundled grant that mints a token consults a wired grantPolicy at the token endpoint: client_credentials, session, refresh_token, jwt-bearer, token exchange, the WebAuthn grant and the device-code grant (at the poll that redeems the approval). A grant handler a deployment contributes consults it only by calling evaluateGrantPolicy itself

    All five are optional. The audit sink carries an absence policy (AUDIT_SINK_ABSENCE_POLICY): when nothing fills the slot — no sink and no auditHooks contribution — the config must declare it absent (core.declaredAbsent = ["auditSink"]) or boot refuses. The other four are simply off when absent.

    Token-binding mechanisms

    Sender-constrained token binding is a first-class extension surface. The tokenBindingMechanisms contribution slot lets a module ship a custom TokenBindingMechanism without forking core. See ADR 2026-05-20-token-binding-first-class-abstraction.md for the design rationale.

    Public types

    • TokenBinding (src/grants/tokenBinding.mts) — the cross-cutting binding shape: a kind, the confirmation, and the optional responseHeaders a mechanism asks the response to carry (DPoP-Nonce). kind is open so downstream mechanisms can extend additively.
    • Confirmation (src/grants/confirmation.mts) — the RFC 7800 cnf claim payload, a closed union of jkt and x5t#S256; adding a variant is a core semver-minor change.
    • TokenBindingMechanism (src/middleware/tokenBinding.mts) — the verb-side abstraction: a kind, intentExplicit (true for header-driven mechanisms such as DPoP, false for ambient ones such as mTLS) and extract(req).
    • TokenBindingRefusal (same file) — what extract throws to refuse, read by duck type, and the mechanism's word on which of three answers it is. A verdict on the material is 400 <code> at the token endpoint and 401 invalid_token with a challenge at a protected resource. A retryInstruction (DPoP's use_dpop_nonce) is 400 <code> at the token endpoint and 401 challenging with that code at a protected resource. An unavailable outage — the mechanism could not reach a verdict, such as a replay store that cannot be read — is 503 <code> at both, with no challenge, because the credential is not at fault. The dispatcher that answers the 503 owns its one error-level line — token_binding_unavailable or protected_resource_binding_unavailable, with the mechanism and code — so a mechanism need not, and should not, log the outage itself. An outage refusal may add a reason (its own name for it — logged when it is a code, as on the verdict line below, never sent) and the failure that stopped the verdict as the standard cause, whose loggableError projection the line carries. A verdict is one warn line — token_binding_proof_invalid or protected_resource_binding_proof_invalid — with the mechanism, the code, the refusal's reason when it is a code, and the refusal's loggableError projection as err, whose own cause is the error that made the mechanism refuse (a parser's, a library's); so a verdict refusal, too, states its reason and carries a parser's or a library's error as cause, never in its message. Every 401 invalid_token refusal at a protected resource is also one sender_constraint_rejected warn line (the 503 outage and the retry instruction's 401 — DPoP's use_dpop_nonce — are not), with rejection naming the sender-constraint rule that refused the request — compound_cnf, scheme_mismatch, proof_invalid, no_matching_binding — beside scheme and site; it was reason, the name the verdict line uses for the mechanism's own. The dispatchers never learn a mechanism's codes.
    • TokenBindingMechanismFactory<Deps> (src/modules/manifest/contributes-map.mts) — the contribution-slot entry: it answers a mechanism, or null when the module is disabled by config (secure-default opt-in).

    Built-in mechanism packages

    • @o3co/auth-provider-dpop — RFC 9449 DPoP (explicit-intent).
    • @o3co/auth-provider-mtls — RFC 8705 mTLS certificate-bound tokens (ambient).

    Both packages contribute via tokenBindingMechanisms. Core's assembleApp collects all contributions, filters nulls, and composes ONE tokenBindingMw mounted on /oauth/token. It and the grantMiddleware contributions run for the token endpoint alone — a POST to /oauth/token, with or without a trailing slash, in any letter case — and not for another method or a longer path beneath it; inside them the request is what a use mount on /oauth/token shows (req.path /, req.baseUrl ending in /oauth/token). The sender-constraint check exempts exactly the same requests.

    Dispatch policy

    When multiple mechanisms are installed, core.tokenBinding.dispatchPolicy (in core's own section — single source of truth) arbitrates:

    • intent-explicit (default) — prefer explicit-intent mechanisms over ambient. Two or more explicit successes, or two or more ambient successes with no explicit one, are rejected with invalid_request and logged once at warn, token_binding_ambiguous, with the tier and the mechanisms that succeeded.
    • strict-mutual-exclusion — reject invalid_request if more than one mechanism's extract returns a binding.

    Env override: CORE_TOKEN_BINDING_DISPATCH_POLICY.

    Grant-side allowlist

    The grants in @o3co/auth-provider-oauth emit cnf-bound RTs only for mechanisms in an explicit allowlist (bindingIsDpop || bindingIsMtls). Adding a new mechanism to bound-RT issuance MUST land its refresh-time enforcement matrix in the same PR — see packages/oauth for the §9.2 matrix pattern.

    Session stores and federation tokens

    Two groups of optional slots for federation and OIDC support, provided by a module (memorySessionStoresModule, memoryFederationTokenStoreModule) or by the Redis adapters:

    • userSessionStore and its sid- and subject-keyed siblings: session metadata (auth_time, how the session was established — authentication — active RPs, family IDs, OIDC claims), the logout fan-out indexes, and subject-wide revocation — src/user-sessions/README.md. SupportsSecondFactorUpdate — optional capability on UserSessionStore that records a second factor verified in a live session (recordSecondFactor), which a step-up needs. Both bundled stores implement it; detect it with the supportsSecondFactorUpdate(store) guard.
    • federationTokenStore: (sid, federationName)-keyed upstream IdP tokens, deleted at logout. The Redis adapter encrypts refresh_token with AES-256-GCM; allow-plaintext is opt-in and emits a warning. A store must round-trip every field of FederationTokens — expiresAt: null included, and undefined, never null, for a field with nothing recorded (obtainedAt included, with the key named). The port contract, field by field, is in src/README.md, and what a store implementer changes for the required keys is docs/upgrading-required-record-keys.md.

    @o3co/auth-provider-oauth consumes both: logout and cascading revocation, id_token and /userinfo, and POST /oauth/federation/:name/token. When any core.federations.<name>.enabled is true, boot refuses a composition missing any of userSessionStore, sessionLifecycle, federationTokenStore and refreshTokenFamilyRevocation (federation-stores-incomplete). Once the stores are wired, boot refuses an enabled federation that no installed module handles (federation-type-unhandled): one whose type no module registers under federationTypes, whatever module contributes its name under federations. Without the refusal it would boot, and its routes would answer 404. A test boots the entries of a type without the package that owns it by installing federationTypeForTests(type) from @o3co/auth-provider-core/testing: each enabled entry of the type gets a provider named after it and a redirect policy that accepts every redirect, or what the test's provider and redirectPolicy callbacks build from the entry.

    • SupportsLock — optional capability on FederationTokenStore for per-(sid, federationName) advisory locks, which keep concurrent refreshes from stampeding the upstream. Both bundled stores implement it; detect it with the supportsLock(store) guard. The lock implementations behind them — core's createInProcessLock (src/federation-tokens/lock/memory.mts) and @o3co/auth-provider-redis's createRedisLock — are internal and not exported; a custom store that needs locking exposes SupportsLock instead.
    • Client.allowedAzpForFederationToken — opt-in flag on the Client record; absent means false. A client that consumes POST /oauth/federation/:name/token must set it to true.

    Session lifecycle

    One record per session that fences joining it against closing it, so no join lands once a close has committed, and the service that is its one caller. The standalone template installs the service's module (templates/standalone/src/buildModules.mts); the design is the ADR 2026-10-05-session-lifecycle.md.

    • The port is SessionLifecycleStore in src/user-sessions/lifecycle/types.mts, the sessionLifecycleStore slot's value. A record's state only moves forward, active → closing → closed (SESSION_LIFECYCLE_STATES). open writes it active and never writes over another record; join adds a participant (rp, family or federation, unique by kind and id) only while the record is active and the session's expiresAt has not passed on the store's clock; beginClose moves it to closing in one commit that keeps the participants as the snapshot and saves the close work — one item per step the caller names and one per participant of the kinds it names (sessionCloseItemOf) — and answers a record already closing or closed as it is, so it is idempotent and resumable; completeIf marks one item done at the generation the caller read, under the conditional-write convention, and the record is closed once nothing is pending; listClosing(limit, after) names the closing sids in ascending order of their UTF-8 bytes after the cursor, so paging from the last sid answered reaches every closing record.
    • The whole record lapses at one retention on the store's clock: expiresAt plus DEFAULT_CLOCK_SKEW_MS while active, and from the closing commit the later of that and the commit plus the request's retainMs. An outage rejects, never missing, null, closed or refused. Every answer is read through the readers in src/user-sessions/lifecycle/readers.mts — readSessionOpenAnswer, readSessionJoinAnswer, readSessionCloseAnswer, readVersionedSessionLifecycle, readSessionLifecycleListing and, for completeIf, readConditionalReplaceAnswer — which refuse anything outside the types with a TypeError; checkSessionParticipant and checkSessionCloseRequest refuse a caller's input outside the port's rules with a RangeError.
    • The in-process store is createInMemorySessionLifecycleStore (src/user-sessions/lifecycle/memory.mts), per process: at most maxEntries records (DEFAULT_MEMORY_SESSION_LIFECYCLE_MAX_ENTRIES, a hundred thousand) and maxParticipants per record (DEFAULT_MEMORY_SESSION_LIFECYCLE_MAX_PARTICIPANTS, a thousand), its clock injectable. Full, it drops lapsed records and, if that makes no room, evicts the closed record whose retention ends first, so a full store may drop a closed record before its retention; it rejects when there is none. A record that left the store reads as closed, as one that lapsed does: nothing joins it, and a repeated close or federations answers no snapshot. An active or closing record is never evicted: that would drop a live session's fence, or leave its close work undone
    • Suite: sessionLifecycleStoreContract on @o3co/auth-provider-test-kit
    • The service is SessionLifecycle (src/session-lifecycle/service.mts), built by createSessionLifecycle and filled in the sessionLifecycle slot by sessionLifecycleModule (core-session-lifecycle), which memorySessionStoresModule's sessionLifecycleStore serves in one process. open(sid, { sub, expiresAt }) writes the session's record active as it is established, and answers opened (a repeat for the same subject and end too) or refused (the sid holds another session's record, or the end has passed: establish nothing on it); a store that cannot answer rejects with its own error, and the service logs nothing for it: the caller logs the outage once. The same holds for join, close, federations and liveness. join(sid, { rp?, familyId?, federation? }) answers joined or refused — the session is closing, closed, gone or has no record; the service has revoked the family and deleted that federation's tokens, and the caller hands out nothing. close(sid, cause) answers done, or pending once its closing commit has landed while work is outstanding, which a later close of the session or the sweep resumes, with the snapshot's relying parties and federations. A sid with no record — never opened, as a session established before the lifecycle, or lapsed at its end on the store's clock, before the closing commit too — reads as closed: liveness answers not_live, join answers refused and writes nothing, and close answers done with no relying party or federation and nothing to run. liveness(sid) answers live with the user session while the record is active and the user session stands as admission's live read judges a record — a subject, an authTime, and an expiresAt later than a clock reading taken after both reads — and not_live from the closing commit on, or for a user session at or past its end, or missing its subject or authTime, even while its store still answers it (a store that keeps a row until a sweep); join refuses such a session as gone; federations(sid) answers the federations the record holds, in the order they joined, as the close that makes the closing commit answers them — which a logout reads before the close removes their tokens; resumePending() runs the work of every closing record. A sid the port cannot hold (empty, past 512 characters, or with a lone surrogate) names no session: liveness answers it not_live and federations lists none, while open, join and close refuse it with a RangeError. A record's participants are in the order each first joined; a repeat join does not move one.
    • The close work runs in phases, each only once the earlier ones are recorded: revoke each family and remove the federation tokens; tell each relying party; delete the user session; remove the subject's index entry, last: where subject revocation closes through the lifecycle (#1455), a close still pending keeps the sid listed, so a retried subject-wide revocation finds it and resumes the close. The items of a phase run together, and a close makes at most eight notices and family revocations at once: relying parties that do not answer hold a close for about one notifier timeout per eight, not one each. Every cause runs it; every cause but expiry also tells the relying parties. A failed item keeps the record closing. The service reads none of the per-session stores (SessionRPRegistry, SessionFamilyIndex, SessionFederationIndex). Where the session package is wired to the lifecycle (@o3co/auth-provider-session's sessionModule and loginCompletionModule take the sessionLifecycle slot), every login opens its session's record before it creates the user session.
    • SessionCloseNotifier (src/session-lifecycle/notifier.mts) is how a close tells a relying party: notify({ sid, sub, clientId, cause }) resolves once the notice is settled and rejects only to be tried again. A module contributes it under the sessionCloseNotifiers contribution kind (SessionCloseNotifierFactory), at most one per composition and never overridden, and the service reads it through the synthetic sessionCloseNotifierResolver when a close runs, never while modules are built: the contributing module is not ordered before sessionLifecycleModule, and may read slots of a module that requires sessionLifecycle. Where the lifecycle module built the sessionLifecycle slot and the clientRepository slot is filled, boot refuses a composition that contributes no notifier, at the end of the contributions. The sweep runs every core.sessionLifecycle.sweepIntervalSeconds (60 unwritten), and not at all at 0

    Federation grants

    The federation grant domain — the grant record, its stores, lodging, retrieval and revocation — is described in src/federation-grants/README.md. A package that writes a grant's credential from an upstream token answer reads the answer with readFederationGrantUpstreamAnswer(answer, context) (src/federation-grants/upstream-answer.mts), the rule the retrieval uses: it reads each field once, and answers the refresh token beside either the access token to store, built by federationGrantAccessToken, or the ineligibility reason. It stores a token only from a readUpstreamTokenLifetime reading with verdict: "finite" and stated: "both", and refuses any other reading — an expiresIn-only one included — as no_finite_lifetime. The token built from such a reading has obtainedAt the call's start, issuedLifetime the expiresIn as issued, and effectiveExpiresAt the reading's end, min(expiresAt, calledAt + expiresIn). When the context names the token the grant held and the answer carries the same access token, effectiveExpiresAt is no later than the held token's end: a re-answer never lengthens a token's life, and one whose held end has passed by the time it arrives is refused as no_finite_lifetime.

    OIDC id_token and claim filter

    Two low-level helpers used by the authorization_code grant and the /oauth/userinfo endpoint.

    generateIdToken

    generateIdToken(opts) is in src/grants/idToken.mts, with its options, GenerateIdTokenOptions, beside it; expiresIn defaults to 3600 s. issuedAt (optional, whole epoch seconds) is the issuance instant: it sets iat, exp is measured from it, and auth_time is read against it. Without it, the clock is used. One that is not whole, non-negative epoch seconds is refused, as generateToken refuses it.

    Signs and returns an OIDC id_token JWT (OIDC Core §2). Claim composition:

    • iss, sub, aud, exp, iat, jti — standard JWT claims
    • auth_time — whole seconds since the epoch, from opts.authTime read against the instant that sets iat (issuedAt, else the clock) through authTimeAt, so never later than iat: an instant up to DEFAULT_CLOCK_SKEW_MS ahead is stamped as iat; one it cannot read (an invalid Date, one before the epoch, one further ahead) is a RangeError, and nothing is signed
    • sid — session identifier for back-channel logout
    • azp — authorized party, included when provided
    • nonce — reflected verbatim from the authorization request when provided
    • amr, acr — as the caller passes them (the authorization_code grant: the code's amr — what the session vouched for at /authorize, vouchedAmr — and its acr); an empty amr is omitted, not emitted as []
    • scope-filtered user claims via filterClaimsByScope

    Header uses typ: "JWT" — the standard spelling, kept deliberately disjoint from RFC 9068's at+jwt so an id_token can never pass an access-token surface. An id_token carrying id+jwt is refused as an ordinary typ mismatch.

    filterClaimsByScope

    filterClaimsByScope(claims, scopes) (src/grants/claimFilter.mts) maps UserSessionClaims to the JWT-shaped claim subset that the granted scopes authorize. Strict whitelist — only the mappings in the table below are emitted; any other UserSessionClaims fields (e.g. provider-specific fields like hd) are never forwarded.

    Scope Emitted claims
    openid (no claims — governs id_token issuance; sub is added by generateIdToken)
    profile name, picture
    email email, email_verified
    groups groups

    /.well-known/openid-configuration

    OIDC Discovery 1.0 metadata endpoint. Synthesized and mounted by core when config.oauth.jwt.issuer is configured AND a module declares the provider surface (oauthEndpointsModule sets providerRoot: true on its discoveryMetadata contribution). Core aggregates every module's discoveryMetadata slice into one document. issuer and id_token_signing_alg_values_supported are core's own, and a module may not set them; a document missing a required field refuses boot (discovery-document-invalid), and so does one that lists a response type without naming authorization_endpoint, or names it with no response type listed: a client asks for a response type there (RFC 8414 §2). A composition with no authorization_code grant is an OAuth authorization server and not an OpenID Provider: its document follows RFC 8414 and names no authorization endpoint, which OpenID Connect Discovery §3 would require; the same document is served at both paths, so a resource server that discovers the issuer's keys through either finds them, and a relying party looking for an OpenID Provider finds none. The slices the bundled modules contribute are below — oauthEndpointsModule's is defined in packages/oauth/src/module.mts, jwksModule contributes jwks_uri:

    • issuer, token_endpoint, userinfo_endpoint, introspection_endpoint
    • authorization_endpoint — only with the authorization_code grant registered, read off the same registry as grant_types_supported; oauthEndpointsModule mounts /authorize on the same condition
    • jwks_uri — always advertised (contributed by jwksModule); an issuer-configured composition MUST install jwksModule or boot fails fast with DiscoveryDocumentError. The route never publishes an empty key set: an HS256 deployment answers 404 jwks_not_published, and an asymmetric keystore that yields no exportable public key answers 503 jwks_unavailable, both with Cache-Control: no-store. A keystore that cannot answer at all — a remote key service timing out — is the same 503, not the terminal handler's 500: a relying party retries a 503. The 503 is logged at error level as jwks_unavailable when the router has a logger (jwksModule passes the composition's), with the error's projection when the keystore threw. The symmetric secret is never published either way. A 200 from this route always carries at least one key. jwksModule reads its own section, jwks: path, where the key set is published under the issuer (default /.well-known/jwks.json, JWKS_PATH), and cacheMaxAge, the success's Cache-Control: public, max-age in seconds (default 300, JWKS_CACHE_MAX_AGE); core's own reference.conf binds both variables, and oauth.jwt.jwksPath and oauth.jwt.jwksCacheMaxAge refuse boot naming these paths wherever the module is installed.
    • revocation_endpoint — advertised when POST /oauth/revoke can revoke anything at all. Two arms, resolved the way the route resolves them: the refresh arm is a wired refreshTokenFamilyRevocation; the access arm is a wired accessTokenDenylist and oauth.revocation.accessToken not being "unsupported" (an explicit "unsupported" disables that path however the composition is wired). Either arm suffices: RFC 7009 §2.2.1 defines unsupported_token_type precisely so an AS may revoke one token type and not the other, so a refresh-only endpoint is a revocation endpoint, and withholding the URL would leave a client that wants to revoke a refresh token at logout unable to revoke anything. With neither arm the route still answers RFC 7009's mandatory 200 and revokes nothing, so advertising it would promise a revocation that does not happen. Which token types it revokes is still not derivable from discovery — RFC 7009 / RFC 8414 define no per-type metadata field, and the access-token answer surfaces at the endpoint itself as unsupported_token_type.
    • response_types_supported — ["code"] with the authorization_code grant; [] without it (RFC 8414 §2 requires the field)
    • request_uri_parameter_supported: false — with the authorization_code grant: OIDC Discovery reads an omitted field as true, and /authorize refuses request_uri
    • client_id_metadata_document_supported: true — only when oauth.clientIdMetadataDocuments.enabled is true, a consent store is wired and the authorization_code grant is registered; see the oauth package README
    • subject_types_supported: ["public"]
    • id_token_signing_alg_values_supported — derived from the configured KeyStore.algorithm
    • scopes_supported: ["openid", "profile", "email", "groups"]
    • grant_types_supported — read off the grant-handler registry /oauth/token dispatches against, so it lists exactly the grants this composition registered and nothing else. Emitted even when empty: RFC 8414 §2 reads an omitted grant_types_supported as ["authorization_code", "implicit"], which would advertise an implicit flow this AS does not implement.
    • token_endpoint_auth_methods_supported: ["client_secret_basic", "client_secret_post", "none"], plus private_key_jwt when a replaySeenSet is wired. A client registered with jwks / jwksUri presents a JWT it signed (RFC 7523 §2.2), verified under those keys, with iss = sub = client_id, aud the issuer or the token endpoint, exp at most an hour out and a single-use jti recorded in the replaySeenSet. That store is the condition: without it the verifier answers 500 server_error rather than accepting an unchecked jti, so the method is advertised only where it can be honoured — the same "on and completable" rule as revocation_endpoint above. See the oauth package README.
    • token_endpoint_auth_signing_alg_values_supported — the assertion algorithms, asymmetric only (RS*, PS*, ES*, EdDSA); the same list is emitted for the introspection and revocation endpoints as *_endpoint_auth_signing_alg_values_supported. All three travel with the method: when no replaySeenSet is wired they are omitted along with it, because algorithms for a method that is not offered say nothing a client can act on.
    • introspection_endpoint_auth_methods_supported: ["client_secret_basic", "client_secret_post"], plus private_key_jwt on the same condition — no none: /oauth/introspect refuses public clients per RFC 7662 §2.1. Two things the metadata cannot say, and an operator needs: (a) RFC 6749 §2.3.1 requires the client_id and secret to be form-urlencoded before base64 for client_secret_basic, so a client_id holding reserved characters — a resource URI, whose : would otherwise read as the Basic field separator — must be percent-encoded (https%3A%2F%2Fapi.example.com); (b) an authenticated caller may introspect tokens whose aud is in that client's allowedAudiences ∪ {client_id}, which is what lets a resource server introspect the tokens issued for its resource URI under RFC 8707. Both are stated in full in the oauth package README.
    • revocation_endpoint_auth_methods_supported: ["client_secret_basic", "client_secret_post", "none"], plus private_key_jwt on the same condition — alongside revocation_endpoint; none is present because RFC 7009 §2.1 lets a public client revoke its own tokens
    • acr_values_supported — with the authorization_code grant, the keys of oauth.authorize.acrValues, when the table is non-empty: the Authentication Context Class References /authorize can satisfy from the amr a session vouches for, less every entry nothing installed can satisfy (dropped at boot, the MFA ADR's D15; see the oauth package README). Each key is one value an acr_values request can name: /authorize reads the parameter as space-delimited RFC 6749 §3.3 scope-tokens, so a key is one or more printable ASCII characters other than the space, " and \. Any other key — one holding whitespace, say — would be advertised and never requested, and refuses boot (config-validation-failed at oauth.authorize.acrValues.<key>, naming the key). Omitted when no entry is left, and acr_values is then unmet_authentication_requirements.
    • code_challenge_methods_supported: ["S256"] — with the authorization_code grant; S256 only, and deliberately fixed: PKCE takes no configuration. This array is server-wide metadata: every client that reads it concludes "I may use any of these". plain never satisfies that (/authorize refuses it outright for public clients per RFC 9700 §2.1.1), so it stays out — a per-client exception does not belong in a server-wide array in either direction.
    • dpop_signing_alg_values_supported — contributed by @o3co/auth-provider-dpop when dpop.enabled = true, carrying that module's algWhitelist verbatim (RFC 9449 §5.1)
    • tls_client_certificate_bound_access_tokens: true — contributed by @o3co/auth-provider-mtls when mtls.enabled = true (RFC 8705 §3.3). Omitted otherwise, which the RFC already defines as false. Independent of mtls.source: both the TLS-layer and the trusted-proxy header path produce the same cnf["x5t#S256"] on the token, and this flag describes the token.
    • end_session_endpoint, and backchannel_logout_supported, backchannel_logout_session_supported, frontchannel_logout_supported, frontchannel_logout_session_supported (all true) — advertised when userSessionStore, sessionLifecycle, federationTokenStore and refreshTokenFamilyRevocation are wired (the same check that mounts the logout routes)

    Logout helpers

    Low-level helpers used by POST /oauth/logout in @o3co/auth-provider-oauth, in src/grants/logoutToken.mts.

    generateLogoutToken

    generateLogoutToken(opts) takes GenerateLogoutTokenOptions, defined beside it; includeSid defaults to true and expiresIn to 300 s. It generates a signed logout_token JWT (OIDC Back-Channel Logout 1.0 §2.4). Header typ: logout+jwt. Claim composition: iss, sub, aud, iat, exp, jti, and events carrying { [BACKCHANNEL_LOGOUT_EVENT_URI]: {} }. The sid claim is included by default; set includeSid: false for RPs registered with backchannel_logout_session_required: false. The nonce claim is never included (spec §2.4 requirement).

    BACKCHANNEL_LOGOUT_EVENT_URI

    The canonical event URI every logout_token's events claim carries, http://schemas.openid.net/event/backchannel-logout. Exported so downstream code and tests can reference it without re-literalizing.

    Logger

    The structural, pino-compatible logger in src/logging/Logger.mts: trace / debug / info / warn / error / fatal, each accepting an object-first or a string-first call, plus child(bindings). A pino instance satisfies it without an adapter, and consoleLogger is the default. It is also the optional logger component slot.

    loggableError(err) is what a call site hands the logger instead of an error that came out of a library or a store talking to another system. Every logger call that reports a caught error goes through it — in every workspace package's src and in the standalone template's — and src/__tests__/logErrorProjection.drift.test.mts keeps it so: its SOURCE_ROOTS lists the trees it reads, and a package added to the workspace fails it until it is listed. A file that hands a caught error to another projection at least as strict instead is named there, with the reason (core's token-binding dispatchers, whose unavailableLogFields is a refusal's reason and loggableError of its cause).

    Why: an error built from a parsed upstream response carries whatever that response said — an OAuth library puts the token answer it refused on the cause chain, a JSON parser quotes the text it could not parse, a Redis reply echoes the command it refused, and ioredis puts that command's arguments (a token record, for a store write under allow-plaintext) on the error. What the projection does:

    • The projection is plain data, and the line is the projection. It has no message: a serializer takes a value with a string message for an Error and rewrites it — pino's err serializer folds each cause into one message and stack, writes none of the cause's fields, and writes the name over type. pino's err and errWithCause serializers, like any that follow the same convention, hand anything else through untouched. So under pino's defaults, the standalone template's logger or consoleLogger, every field below reaches the line at every level, with no serializer to configure. Every level carries name; pino adds no type of its own.
    • detail is the error's message — detail (RFC 7807's name for an occurrence's human-readable explanation) rather than message, for the reason above — with the known quoting shapes removed: a SyntaxError's message is dropped — V8's JSON.parse and body-parser quote the input — keeping only at position N (at most ten digits) as position; a YAMLException's is dropped whole — js-yaml quotes the lines around the fault; and Redis's , with args beginning with: … is cut from every message, whichever client's class carries it. Other text a peer wrote into a message is kept — the projection cannot tell it from this process's own — but on one line: every character that breaks a line or reorders it on screen (C0, DEL, C1, U+2028/U+2029, the directional marks U+200E, U+200F and U+061C, and the bidi embedding, override and isolate controls U+202A–U+202E and U+2066–U+2069) is replaced by ?, while ", \ and every other character, a non-ASCII letter included, stay. The same filter is exported as lineSafeText(text, maxLength = 256), for a package that logs peer text that is not an error's (an mTLS certificate's subject, a URL it names); it caps with the cut marked ..., never inside a surrogate pair, and a maxLength that is not an integer of at least 4 is a RangeError.
    • error_description is the one peer-written string kept on purpose, because it tells a revoked grant from a broken client: its first line only (Azure AD's AADSTS line, not its Trace ID lines), when that line is within RFC 6749 §5.2's character set, cut at the start of the word that holds its first run of twenty or more token characters ([A-Za-z0-9._~+/=-]) and trimmed, so that no part of the token and no fragment of its word is left — legacy Spring's "Invalid refresh token: " keeps "Invalid refresh token:", Azure AD's AADSTS700016 keeps "AADSTS700016: Application with identifier", a redirect URI Azure AD or Okta names goes whole with its https: — and omitted when nothing is left.
    • stack keeps the frames and never the header that carries the message: at most ten frames, 2048 characters, at every cause. It is kept only when the stack starts with the whole header its name, code and message give — name: message, Node's name [code]: message, and for an empty message also name or name [code] — ending its line; a message rewritten after the stack was formatted, or one that is not a string, leaves no stack.
    • Also kept: name, a string or numeric code, an integer status, a string type (body-parser's entity.too.large), an error within §5.2's set, response: { status, contentType } for a Response on the cause or on response (a gateway's 503 page), and the Error causes the same way, three deep.
    • Closed-set fields a store's or a client's error records, kept because their shape cannot hold free text: an own reason that is a code — lowercase words joined by _ or -, at most 64 characters (a Store transport failure's unreachable, a challenge store's expired-at-issue) — and up to four own <word>Status fields holding an HTTP status, 100–599 (a Store refusal's storeStatus). A field of that kind records an upstream's answer beside the error's own status, which Express reads as this server's, so it is kept under its own name rather than any package's being named here.
    • An AggregateError's members (any error's errors array), as aggregateErrors: of the first five (LOGGED_AGGREGATE_MAX_ERRORS), the Errors, each projected as a cause is and within the same three levels; aggregateErrorsOmitted counts the members not among them. aggregateErrors is the name pino writes a raw AggregateError's members under, so one query finds both. A handle.dispose() failure is logged with the name and code of every cleanup that failed.
    • The command a store's error answered, by name alone: command: { name } from ioredis's command: { name, args }, when the name is a token of at most 32 letters, digits and _, or two joined by one . — which Redis command failed (set, evalsha, hello, a module's JSON.SET), never its arguments. It stays at ioredis's own path, so a query on err.command.name reads a raw and a projected line alike; a command that is a string (execa's shell line) is not kept.
    • A budget for one line: at most sixteen projections (LOGGED_MAX_PROJECTIONS) — the error, its causes and its members together — taken nearest first, so the error's own cause and members come before any of theirs. Every cut shows, whether the budget or the depth limit made it: a member left out counts in aggregateErrorsOmitted, and a cause left out leaves causeOmitted: true. With every string capped, a line stays under about 64 KB.
    • Never kept: a cause or a member that is not an Error (where openid-client puts the answer it refused), any other field (a command's args, body, buffer), and anything of a thrown non-Error but its typeof, as thrown.
    • Every string — name, code, type and a response's contentType as well as detail — is on one line (the filter above) and capped at 256 characters, the stack at 2048; no cut falls inside a surrogate pair. It never throws. consoleLogger prints a projected error eight levels deep (LOGGED_PRINT_DEPTH); other objects print as before. The depth is past the deepest level a projection nests to, so its causes and members print whole rather than as [Object]. Each projection carries its own non-enumerable util.inspect.custom that does this, and consoleLogger hands the console its arguments unchanged. Any other object a caller logs, such as a request or a config, keeps Node's default two levels. JSON, pino and a spy never see the hook.
