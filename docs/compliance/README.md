# Specification checklist

Generated by `pnpm --filter @mod/spec-checklist run report` from the checklist and the tests that name its items. Do not edit.

Each specification has a page here, `<spec>.md`, with a row for each of its items.

A status here is read from the checklist and the tests alone: `mapped` (a test names the item), `hole` (no test does), `noncompliant` (a MUST known not met), `deviates` (a SHOULD not followed, by a decision), `out-of-scope` (a feature not offered, or what the deployment provides, as its reason says). Whether a mapped item's tests ran and passed is told by each CI run's compliance report. An item that asks the server for a document (its scope requirements, the size of its codes and tokens) is met by the cards and the guides, which no test can name, so it counts as a hole.

An item's role is the role of the server's it binds: `as` the authorization server, `op` the OpenID Provider, `rs` the resource server at its own protected routes, `rp` the relying party to an upstream IdP, `client` the client sending tokens or assertions out.

The checklist binds a production deployment (`kernel.environment = production`, the default). What only a development deployment allows, such as a plain-http public origin by `http.insecure-origin`, is outside it: a production deployment refuses a plain-http origin or issuer at boot, as the security model's Boot section (`docs/security-model.md`) tells. What an operator loosens explicitly, an `accept-*` setting or a `plain-*` pair, or an algorithm it writes explicitly (`oidc.id-token-alg`), is the deployment's declared exception: an item keeps the status its tests give the default, and the security model's "Left to you" names the setting.

The summary over every specification, by specification and by role, is not kept here: `pnpm --filter @mod/spec-checklist run summary` prints it from the checklist as it stands.

## Notes

Notes several items point to, from their Note cell:

- <a id="n-https"></a>**N-https**: Held for a production deployment (`kernel.environment = production`, the default), which refuses a plain-http public origin and issuer at boot: there the URL is https. Outside production, a deployment that declares `http.insecure-origin = true` may serve it over plain http, for trying the provider on one machine.
- <a id="n-least-privilege"></a>**N-least-privilege**: Held for what the provider issues: a token's scope stays within what the client is allowed (`client-allowance`), and its audience is narrowed by a resource indicator (`resource-indicators`). What a resource server takes a token for is its own.
- <a id="n-response-types"></a>**N-response-types**: Held where the authorization endpoint is composed (`authorize`), which publishes `code`. A deployment without it supports no response type, so the member would hold no value, and a member with no values is left out (RFC 8414 §3.2, OpenID Connect Discovery §4.2): the two MUSTs meet there, and the metadata keeps the second. v0.17.0 published `[]`, a declared difference (`response-types-without-authorization-endpoint`).
