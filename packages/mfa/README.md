# @o3co/auth-provider-mfa

Last updated: 2026-10-06

Multi-factor authentication for [`auth.provider`](../../README.md): a second factor after a password login, and a step-up when a relying party asks for one at `/authorize` — the package [the MFA ADR](../core/docs/adr/2026-09-25-multi-factor-authentication.md) designs (its D1).

> No revocation and no password change clears the subject lock (D21): it is given back early only through the authorized-recovery entry — the subject's own release after a recent exempt proof (`POST /session/mfa/lock/release`, [The lock's release](#the-routes)), or the operator reset (`resetMfaForSubject`, from `mfaResetModule`).

## Responsibility

**Role.** Everything MFA needs that is not a shared port: the `mfa` session requirement it contributes to core's session admission — what the MFA ADR called the coordinator — the browser API under `/session/mfa/*`, the factors that are not another package's, the key ring and what is sealed under it, lockout and audit. Core holds the ports the factors and the stores share; a factor from another package (WebAuthn's) reaches the requirement as an `mfaFactors` contribution.

**Owns:**

- the `mfa` session requirement — what MFA is to every consumer of a session, through core's admission — and `mfaModule`, which registers it as `sessionRequirements.mfa` and refuses the compositions that could not honour it;
- the login's MFA transaction: opened when the requirement interrupts a password login, and the `403` the login is answered with;
- the routes under `/session/mfa` — reading a transaction, a factor's challenge, a verification, a login's first binding, an enrollment from a signed-in session, the step-up — of a first binding, or of a counting factor — the account page's list, rename and removal of factors, the subject's release of its lock, and the account-email proof — and the login a verified second factor, or a factor bound at a login, completes, with the audit events they emit;
- the subject lock in the verify path (D21, [`src/lock.mts`](src/lock.mts)) over core's `MfaTransactionStore`, and the authorized-recovery entry, the one way it is given back early ([`src/lockRecovery.mts`](src/lockRecovery.mts)): the subject's own release, and the operator reset ([`src/reset.mts`](src/reset.mts), `mfaResetModule`);
- the enrollment witness's reads at login and its writes (the MFA ADR's D12, [`src/witness.mts`](src/witness.mts));
- the one first-binding gate (D24, D25, [`src/firstBinding.mts`](src/firstBinding.mts)) and the account-email proof ([`src/proof.mts`](src/proof.mts));
- MFA mail — the one place a code the provider issued is handed to the mail sender, and the masked address a page may show ([`src/mail.mts`](src/mail.mts)) — and the codes it issues: the long code every 80-bit code is, and the six-digit login code ([`src/codes.mts`](src/codes.mts));
- the TOTP factor (RFC 6238 on `node:crypto`), contributed as `mfaFactors.totp` by `mfaTotpFactorModule`, the recovery-code factor, contributed as `mfaFactors.recovery_code` by `mfaRecoveryCodeFactorModule`, and the email factor, contributed as `mfaFactors.email` by `mfaEmailFactorModule`;
- the sections its modules read — `mfa`, the MFA module's (the mode, the MFA page, the key ring, a transaction's life and attempts, the subject lock, recent MFA's window, the first binding's proof), `mfa-totp-factor`, the TOTP factor's module's, `mfa-recovery-code-factor`, the recovery-code factor's module's, and `mfa-email-factor`, the email factor's module's — their defaults ([`config/reference.conf`](config/reference.conf), exported as `@o3co/auth-provider-mfa/reference.conf`) and their refusals, the development sample key among them;
- sealing a factor's data and a ceremony's state under the key ring, and keyed digests for codes that are compared and never recovered — so that no factor holds a key. Factor data, state and a challenge's or an enrollment's `response` must be plain JSON-shaped values; a class instance is refused. Each is taken once, as a plain copy (plain objects and arrays, strings, finite numbers, booleans, `null`; an own getter read once), and that copy is what the factor's `amrFor` is handed, what is sealed and what the page is answered; anything else is the factor's failure (`503`), its stored data left as it was. A verification or an enrollment's completion counts only when its `ok` is `true` or `false`, a refusal only with a `reason` its type names, and `amrFor`'s list is taken once as a copy; anything else is the factor's failure too;
- its testing entry, `@o3co/auth-provider-mfa/testing` ([`src/testing/index.mts`](src/testing/index.mts)): what another package's tests use of this one.

**Does not own:**

- the `MfaFactor` contract, the `MfaFactorStore` and `MfaTransactionStore` ports and their adapters, the `mfaFactors` kind and `mfaFactorResolver` — core's (`packages/core/src/mfa/`), with Redis adapters in `@o3co/auth-provider-redis`;
- the WebAuthn factor — `@o3co/auth-provider-webauthn`'s `webauthnMfaFactorModule`, contributed as `mfaFactors.webauthn` and verified through these routes like any factor (the ADR's D4, F7);
- the pages: the login page's second step, the MFA page and the account page are the deployment's (D6), and keep [The MFA page's contract](#the-mfa-pages-contract).

**Why a separate package.** Core mounts no route but discovery and imports no sibling, and the MFA routes are browser routes that need the session package's CSRF guard and its login tail. A package also lets a deployment that opts out install none of it, and lets the factor code move on its own review cadence (D1).

## Configuration

Four sections, each its module's and named after it: `mfa`, the MFA module's; `mfa-totp-factor`, the TOTP factor's module's; `mfa-recovery-code-factor`, the recovery-code factor's; `mfa-email-factor`, the email factor's. Boot parses each with its module's schema before any factory runs, and hands it to the module's factories. Each is strict at every level: a key it does not declare — a typo, or a key an older version read — refuses the boot (`config-validation-failed`), naming its path. Layer [`config/reference.conf`](config/reference.conf) between your `application.conf` and core's `reference.conf`, as for the WebAuthn package; it carries the defaults and the environment variables that override them. `mfaModule`, `mfaTotpFactorModule`, `mfaRecoveryCodeFactorModule` and `mfaEmailFactorModule` declare it as their sections' reference, so core's `moduleReferences(modules)` names it among the files to layer.

A key your `application.conf` sets shadows the substitution `reference.conf` makes for it; repeat the `${?VAR}` line after your value to let the environment override it again. Every number in these sections is a whole number, or its decimal digits as an environment variable carries them.

**The TOTP factor's old path.** `mfa.factors.totp` refuses the boot wherever `mfaTotpFactorModule` is installed (`config-path-relocated`), naming each key's path under `mfa-totp-factor` and the variable `reference.conf` binds it to (a value written at `mfa.factors.totp` itself names the section alone). Its variables, `MFA_TOTP_ENABLED` and `MFA_TOTP_ISSUER`, are bound to no setting and declared renamed on the factor's module (`section.renamedVariables`); `reference.conf` captures them and their new names in `renamed-variables`, so a composition that layers it is judged by what its resolution saw: exported alone, or beside `MFA_TOTP_FACTOR_ENABLED` / `MFA_TOTP_FACTOR_ISSUER` set to a different value, one refuses the boot (`environment-variable-renamed`), naming the new variable and its path; set to the same value as its new name, it boots. Set `MFA_TOTP_FACTOR_ENABLED` or `MFA_TOTP_FACTOR_ISSUER` instead. An empty `mfa.factors` block an older configuration leaves behind, its variables unset, is a key the `mfa` section does not know, and refuses the boot wherever `mfaModule` is installed: delete it.

**The MFA page's old path.** `endpoints.mfa.url` refuses the boot wherever `mfaModule` is installed (`config-path-relocated`), naming `mfa.page.url` and `MFA_PAGE_URL`. Its variable, `ENDPOINTS_MFA_URL`, is bound to no setting and declared renamed on the MFA module; `reference.conf` captures it and `MFA_PAGE_URL` in `renamed-variables`: exported alone, or beside `MFA_PAGE_URL` set to a different value, it refuses the boot (`environment-variable-renamed`); set to the same value, it boots. Set `MFA_PAGE_URL` instead.

**The routes' budget is the limiter's.** `mfa.rateLimit` is removed: every `/session/mfa` POST is limited by the deployment's `rateLimiter` under the prefix `mfa` (`mfa:ip:<ip>`), by its own `limits.mfa` (`redis-rate-limiter.limits.mfa`, `core-rate-limiter-memory.limits.mfa`), or else its `defaultLimit`. A key still set under `mfa.rateLimit` refuses the boot wherever `mfaModule` is installed (`config-path-relocated`), naming each key as removed; an empty `mfa.rateLimit {}` block is a key the `mfa` section does not know, and refuses it too.

**Key ids and rotation.** An entry written without an `id` — as `reference.conf`'s, which `MFA_ENCRYPTION_KEY` feeds — is named by its key's fingerprint: `k` and the first 16 characters of base64url(HMAC-SHA-256(key, `o3co:mfa:key-id`)), which tells nothing of the key. So a key changed in place leaves what the old one sealed `key_unavailable`, naming the old fingerprint — put that key back — never `unreadable`, which no key cures. An entry written with an `id` keeps it: never change its key in place. To rotate, write the ring in a deployment-owned layer: add the new key last as an entry of its own (a new `id`, or none), then move it first, and keep the old key until nothing sealed under it, and no digest naming it, is left. A recovery set's digests are never made again — its data is re-sealed at every use, its digests are not — so a set stays under the key it was made with until it is regenerated, and removing that key makes the set `503`. Opening data sealed under a key that is no longer first logs `mfa_factor_sealed_with_retired_key` (info, the key id) once per key id. Core's envelope seals with a random 96-bit AES-GCM nonce, and a factor's data is re-sealed at every use, so rotate each key well before 2^32 seals under it — the bound NIST SP 800-38D sets for random nonces.

**Refused**, each naming the key and quoting no key or id.

- Before any factory runs (`config-validation-failed`, the key's path with its section's): a key a section does not know, at any level; `mfa.mode` outside `off`, `optional` and `required`; an `mfa.page` that is not a section with a string `url`; a ring that is not a list of `{ id?, key }` entries; a transaction's life outside 60 to 1800 seconds, its attempts outside 2 to 10, recent MFA's window outside 60 to 3600 seconds, a subject's records outside 2 to 100, a lock field that is not a positive whole number, or `mfa.storeTimeoutMs` below 1000; `mfa.enrollment.requireEmailProof` other than `when-mail`, `always` or `never`; a key of `mfa` missing, but the mode and the page; in `mfa-totp-factor`, a parameter out of its range, an algorithm it does not take, an `enabled` that is no switch, or an issuer outside its rule; in `mfa-recovery-code-factor`, a key the section does not know, or a count outside its range; in `mfa-email-factor`, a key the section does not know (a subject line, a body or a send limit among them), or a code's life outside its range; a factor's section missing, because `reference.conf` is not layered; a section written as a value rather than a section of keys.
- By the MFA module's factory, a `RangeError` whose message starts with the key: `mfa.mode` `off` or unset, which a missing `mfa` section reads as; an empty ring or one without `MFA_ENCRYPTION_KEY`; a key that is not canonical base64 of 32 bytes; a duplicate id — a fingerprint that equals a written id among them — or one outside `A-Za-z0-9_-` (1 to 64 characters); one key listed twice, whatever ids it is written under; a lock core's rule refuses; a store timeout whose lease would pass the longest subject lease; `mfa.enrollment.requireEmailProof = "always"` with no mail sender wired, under which nobody could give the proof and so nobody could bind (D20).
- By the TOTP factor's factory: for a factor that is on and has no issuer written, a deployment's issuer — the `oauthTokenSettings` slot's — with no host to default it to (naming `MFA_TOTP_FACTOR_ISSUER`).
- By the email factor's factory (`contribute-factory-failed`): `mfa-email-factor.enabled` true with no module providing `mailSender`, naming the switch, its variable (`MFA_EMAIL_FACTOR_ENABLED`) and the slot — the factor could send no code. Which module provides the slot is the composition's: the message names no sender package.

`mfaConfigSchema` holds each shape and range of the `mfa` section, refusing a key it does not know at every level: the mode, the page (a section with a string `url`, which may be left out), the ring's entries, the transaction's life (60 to 1800 seconds) and attempts (2 to 10), each lock field a positive whole number, recent MFA's window, the first binding's proof, a subject's records and the store timeout. `mfaModule`'s section schema is it with the mode optional, which the module refuses as `off`. Reading the settings makes the rest: the ring's refusals and the sample key's, where the keys are decoded and the environment is known, and core's `checkConfiguredMfaLockoutPolicy` on how the lock's fields relate to each other (`hardLimit` at least 10, above `threshold` and at most 100, `maxSeconds` at least `baseSeconds` and at most a week, every duration within the Date range). The TOTP factor's module alone reads `mfa-totp-factor`; `mfaModule` reads every `mfa` key above and no factor's section, so a composition without the TOTP factor — its factors all another package's — is never refused over TOTP's.

**The development sample key.** [`MFA_DEVELOPMENT_SAMPLE_KEY`](src/config.mts) is a published key a development configuration may put in the ring in place of a key of its own. Everyone holds it, so it is refused — wherever it sits in the ring — when the environment the configuration was selected by is `production` or `staging`, when `NODE_ENV` is either (each read whatever its case and the whitespace around it), and under `core.deployment.mode = "multi"`, which the module reads from core's `deploymentMode` slot and never off the configuration — the rule the Redis federation stores' plaintext mode follows too. The environment reaches the refusal from the composition root (the standalone passes `CONFIG_ENV || NODE_ENV`) as `mfaModule({ environment })`. Where it is accepted, the module says so once at boot: `mfa_development_sample_key_in_use` (warn).

## Installing

Installed is on (the session-admission ADR's D7): a composition that wants no MFA installs none of this package, and an `mfa` section it writes is one no module reads. The standalone template installs it behind a switch of its own, `MFA_MODE` (`mfaMode`), `required` by default: `optional` or `required` installs what follows, with the operator reset, and writes `mfa.mode`, `core.sessionRequirements.expected` (naming `mfa`) and `core.sessionRequirements.secondFactorAuthority = "mfa"` from the switch, and `off` installs none of it ([its README](../../templates/standalone/README.md#multi-factor-authentication)). One that wants it lists `mfaModules({ environment })` — the TOTP factor's module, the recovery-code factor's, the email factor's (off unless switched on, and refusing the boot when it is on with no `mailSender`) and `mfaModule` — with an `MfaFactorStore` and an `MfaTransactionStore` (core's memory modules on one replica, `@o3co/auth-provider-redis`'s on several), the session package's login, its `loginCompletionModule` and its user-session store; sets `mfa.mode` to `optional` or `required`; declares `"mfa"` in `core.sessionRequirements.expected`; and declares `core.sessionRequirements.secondFactorAuthority = "mfa"` beside it, so core refuses the boot unless the requirement registered as `mfa` declares the second-factor authority.

`mfaModule` requires `mfaFactorResolver`, `mfaFactorStore`, `mfaTransactionStore`, `userSessionStore`, `sessionRequirementResolver`, `csrfGuard` (every MFA POST runs it), `loginCompletion` (a verified second factor finishes the login through it: load the session package's `loginCompletionModule` beside `sessionModule`) and `deploymentMode` — core's, filled from `core.deployment.mode`, which the development sample key's refusal reads — and reads `rateLimiter` — what limits its routes — `auditSink` — its absence declared with `core.declaredAbsent = ["auditSink"]` — `subjectRevocation` — the boundary its routes' admission of a signed-in session, and every use of a login's transaction, reads, its absence declared with `oauth.revocation.subject = "unsupported"` — `sessionLifecycleStore` — core's session lifecycle port, which core's session-store modules fill and `sessionLifecycleModule` requires, and which the routes' admission reads after a live record: a session closing or closed is not admitted; core's session lifecycle is required where a user-session store is wired, so the boot is refused without it — `logger`, `mailSender` — where the account-email proof and a factor's codes go — and `userRepository`, for the enrollment witness's write alone (`markMfaEnrolled`). It mounts `mfa-routes` (`MFA_ROUTES_ID`) at `/session/mfa`, after the session middleware (see [The routes](#the-routes)). It claims the `mfa` prefix (`MFA_RATE_LIMIT_PREFIX`) with no budget of its own, and registers its two admission actions (`MFA_ADMISSION_ACTIONS`): `mfa.manage`, graded `credential_change`, which its routes admit an enrollment, a rename, a removal or the lock's release from a signed-in session as, and `mfa.view`, graded `use`, the list of the subject's factors. With no `rateLimiter` wired — its absence declared in `core.declaredAbsent`, as core requires — its routes pass every request through. The boot is refused:

- `mfa.mode = "off"`, or unset, with the module installed: remove the module, or set the mode;
- once every factor has registered, for what a first binding's `hints.enrollable` would have to list, each `cause` carrying a `reason`: an enabled factor — this package's or another's — whose kind core's hint grammar refuses (`^[a-z][a-z0-9_-]{0,63}$`; `MfaFactorKindUnhintableError`, `mfa-factor-kind-unhintable`, naming the kind); more than 16 enabled counting factors, the most a hint list carries (`MfaTooManyFactorsError`, `mfa-too-many-factors`); and `mfa.mode = "required"` with no counting factor enabled, which nobody could meet (`MfaNoCountingFactorError`, `mfa-no-counting-factor`: it names the enabled factors that do not count, and asks for an installed counting factor's `enabled` key — the TOTP factor's, `mfa-totp-factor.enabled` (`MFA_TOTP_FACTOR_ENABLED`), where its module is installed);
- without a `userSessionStore`, a `csrfGuard` or a `loginCompletion`, at the requires-closure, naming the slot;
- without a `sessionLifecycleStore` beside the `userSessionStore` (`contribute-factory-failed`, the message naming both slots): wire core's session lifecycle: a session-store module that fills `sessionLifecycleStore` (`memorySessionStoresModule` or `redisSessionStoresModule`) and `sessionLifecycleModule`;
- for a key ring, a transaction life, attempts, a lock or a first binding's proof the settings refuse (above), for `mfa.enrollment.requireEmailProof = "always"` without a `mailSender` (D20), and without `mfa.page.url`, the page a step-up starts on (`MFA_PAGE_URL`; `reference.conf` ships `/mfa`);
- by core, when the requirement's reach is not what the enabled factors reach, when `mfa` is not declared in `core.sessionRequirements.expected`, when another installed requirement declares the second-factor authority too (`duplicate-second-factor-authority`), or when `core.sessionRequirements.secondFactorAuthority` names `mfa` and the requirement registered under that name does not declare the authority (`second-factor-authority-not-declared`).

**Switching `optional` to `required`.** A live password session of a user who holds no counting factor has no second factor to step up with: at its next action it is asked to log in again, and the login binds the user's first factor (the MFA ADR's F2 amendment).

Whether a second factor can be recorded on a session is admission's to say: core decides it once per admission, over the store's capability and the record's shape, and hands it on as `SessionView.secondFactorRecordable`. The requirement and `POST /session/mfa/step-up` read that answer and nothing else: where it is `false`, the requirement sends the session to log in again where it would step it up, and the step-up of a counting factor answers `401`, opening nothing. A `userSessionStore` without `recordSecondFactor` (core's `supportsSecondFactorUpdate`) is one such case for every session: the module boots, says so once at warn (`mfa_step_up_unsupported`, with the adapter's `kind`), and a binding in a session records nothing on the session. A record whose primary cannot be told, or whose `authentication` or `amr` is not in a shape the types admit, is the other, whatever the store (core's `user-sessions` README says when `recordSecondFactor` answers `null`).

A directory without `markMfaEnrolled` (core's `supportsMfaEnrollmentWitness`), or none, cannot hold the enrollment witness: the module boots and says so once at warn (`mfa_enrollment_witness_unwritable`); D12's defence is then what the Store answers on `authenticate` and on `authenticateByToken`. With `mfa.enrollment.requireEmailProof = "when-mail"` and no `mailSender`, a first binding asks for no proof: said once at warn (`mfa_first_binding_without_email_proof`) — notify account holders of `mfa.factor.enrolled` from the audit events.

Without `subjectRevocation` the subject's own release of its lock can lift the hard hold once every guessable factor is bound again, but can never give the week or the backoff back early — no boundary can be read to show a revocation came after the attack: the module boots and says so once at warn (`mfa_lock_release_unavailable`); such a release is `409` with `reason: "no_revocation_boundary"`.

**The operator reset** is `mfaResetModule`'s, installed beside `mfaModule` where operators reset subjects: it provides `mfaReset`, eagerly — `handle.components.mfaReset.resetMfaForSubject(subject, { requireEmailProof?, federationGrants?, requestedBy? })` — and requires `mfaFactorStore`, `mfaTransactionStore`, `subjectRevocationService` (the oauth package's `subjectRevocationServiceModule`: the reset ends every session and token of the subject's) and `mfaSubjectLeases`, the subject's lease owner `mfaModule` builds from `mfa.storeTimeoutMs` and provides ([`src/factorSet.mts`](src/factorSet.mts)) — authoritative: a composition that overrides it while `mfaModule` is loaded is refused at boot. Every writer holds a lease of the same rules: sixteen `mfa.storeTimeoutMs`, a Store call cut off at one, a write started only with one left; the reset waits up to two such leases for another holder. **The operator reset needs `mfaModule` installed**: under `mfa.mode = "off"` it is not, the reset is unavailable, and a composition that installs `mfaResetModule` without it is refused at boot, naming `mfaSubjectLeases`. It reads `userRepository` for the witness's clear (`markMfaEnrolled(subject, false)`), `mailSender` — `requireEmailProof: true` without one is a `RangeError` — `auditSink` and `logger`, and no section. See [The routes](#the-routes), "The operator reset".

## The `mfa` requirement

Registered as `sessionRequirements.mfa` ([`src/requirement.mts`](src/requirement.mts); the session-admission ADR's D6):

- **The second-factor authority** — the requirement declares it (`secondFactorAuthority`), which is what core weighs, never the name: core lets the authority alone reach and add a second factor's `amr` values and `mfaAt`, holds its completion of a login to a verified second factor, and binds it at boot to `mfaFactorResolver`, `mfaFactorStore` and `mfaTransactionStore`. The name `mfa` is this package's own.

- **Reach** — what a step-up can add to a session: each enabled factor's `amrValues`, and `mfa` when one of them adds it (TOTP: `otp` and `mfa`), read once — at boot, after every factor registered — and kept: core seals that reach and merges with it, and the requirement's own verdicts read it too. The page a step-up starts on is `mfa.page.url`; the one remediation the requirement declares is `mfa.step_up`, the step-up route's.
- **At each use** (`admit`), by the action's grade — the requirement names no action:
  - `use`: under `optional` every session is met. Under `required`, a session a cookie, a code or a link carries is met when its primary is a federation, or when a second factor was verified in it (`mfaAt`); a password session without one is stepped up to the MFA page when its subject may hold a counting factor to step up with — or unmet, when no factor is enabled, and sent to log in again when no second factor can be recorded on the session (`secondFactorRecordable`) — and sent to log in again when it holds none, where the login binds its first factor; a session whose primary cannot be told, or no live session, is sent to log in again.
  - `grants_nothing` — device verification's `device.lookup` and `device.deny`: met on any live session a cookie, a code or a link carries, whatever it is named, so a user refuses a phished device request without a step-up.
  - `credential_change` — an action that changes the ways into the account: the link start (`session.link`), WebAuthn registration (`webauthn.register`), an enrollment, a rename or a removal from the account page (`mfa.manage`). The account page's list (`mfa.view`) is a `use`. A session a cookie, a code or a link carries is held — under `required` on top of the baseline, whose answer comes first, so the grade is never looser than `use`; under `optional` alone — to what the subject's factor records say: a record counts unless an installed factor of its kind declares it does not (recovery codes), so a kind no longer installed is presumed to count, and a store that cannot answer is an outage (`503`).
    - **A subject with a counting factor** needs **recent MFA** ([`isRecentMfa`](src/requirement.mts)): a second factor verified in the session within `mfa.manage.maxAgeSeconds` — the window's edge included, an `mfaAt` up to `DEFAULT_CLOCK_SKEW_MS` ahead of the clock read as now and one further ahead as not recent. Without it the session is stepped up to the MFA page — unmet when no factor is enabled, sent to log in again when no second factor can be recorded on the session (`secondFactorRecordable`).
    - **A subject without one** is making its first binding (D12, D24), a passkey and a linked identity as much as a factor. What the session recorded of its login's `User` (`enrollmentFacts`, the view admission hands the requirement) is read first: a session that recorded nothing is sent to log in again — a fresh login records it, so a store of your own must round-trip it — and so is a password session whose recorded witness says the subject enrolled, or says nothing readable, beside no record that may count — never a first binding, and nothing recorded: the witness it recorded may predate a removal that cleared it, and the password login reads the `User` afresh, where a real loss is `503` and recorded (below). A federated session in that state is `503`, recording `mfa.enrollment_state_inconsistent`, never a first binding: a federated login does not consult the requirement, so nothing else would record the loss. A session whose primary the requirement cannot tell is held on that side. Then the primary must be as recent, by the same rule, or the session is sent to log in again. The primary is read as the session's freshness, core's `authenticationFreshness`: `authTime`, or for a federated login the earlier of that and the upstream's recorded authentication once the federation callback records it (#1084 switch-on), and never recent when the upstream showed no time. A second factor verified in the session does not stand in for it. So a federation whose upstream reports no `auth_time` — GitHub, and Google, whose `auth_time` the Google adapter does not request — sends every first binding through it to log in again, every time, while `core.federations.<name>.callbackMeetsFreshness` is `false` (the default); set it to `true` for such a federation to let the callback count as the primary. Where the upstream is why a primary is not recent, the requirement says so at info (`mfa_first_binding_upstream_not_recent`, `reason` `upstream_unknown` or `upstream_stale`). Then the subject's first-binding mark ([below](#the-routes)): a session established no later than it, plus `DEFAULT_CLOCK_SKEW_MS`, may have recorded `not_enrolled` before the subject enrolled, and is sent to log in again; a mark that cannot be read is `503`. Then the one gate ([below](#the-routes)) over the account's address as recorded and D25's flag: no proof asked is met; a proof asked is met only while one given in that same session through the step-up stands — `mfa.manage.maxAgeSeconds` from when it was given; a store answering an older one, the clock skew allowed, answers none — and stepped up to the MFA page otherwise; a proof nobody can give is stepped up and never met.
    - A session whose primary is neither a password nor a federation, and no live session, are sent to log in again.
    - The window bounds the admission, not what follows it: the link start is admitted, and its callback writes the identity up to the federation transaction's lifetime (10 minutes) later.
    - Hosts' clocks must agree within `DEFAULT_CLOCK_SKEW_MS`: `mfaAt` carries the clock of the replica that recorded it, so a replica whose clock runs ahead stretches recent MFA by its lead.
    - A subject who holds a counting factor and is answered `403 step_up_required` is stepped up on the MFA page: a factor it holds, verified through `POST /session/mfa/step-up` ([below](#the-routes)), records recent MFA on the session.
  - A token is judged on its own `amr` whatever the grade, under `required`, and met under `optional`: a refresh token is judged on what it was issued with, whether or not it names a live session. A federation's is met; one carrying a factor's own second-factor value (`otp`, `hwk`, `swk`, `email`, `recovery` — never `mfa` alone) is met whatever its primary, so a passkey sign-in's `["hwk"]` token keeps refreshing; a password alone is unmet; anything else — no `amr` at all (a token issued before tokens carried one), an unknown value — is sent to log in again.
- **At a password login** (`admitPrimary`), the subject's factor records are listed — a store that cannot answer is `503`, with nothing written. When no record that may count stands (none, or recovery codes alone), the login's `User` must not say the subject enrolled: a witness `true`, or one that is neither `true`, `false` nor absent, records `mfa.enrollment_state_inconsistent` and is `503` under either mode — the factor store was lost, or the Store answers wrongly — never a first binding (D12). Every record that serves interrupts the login for a second factor — every one but a recovery set whose data opened and holds no code left ([`src/factorState.mts`](src/factorState.mts)); a record this deployment cannot use (a retired kind, data that does not open — a TOTP factor whose key left the ring —, a recovery set with a code left) is never read as none. With none that serves — no record, or exhausted or retired sets alone, which stay on record (retired: below the subject's recovery-set floor, the floor read with the records as every judgment over them reads it; one that cannot be read is said at warn, `mfa_recovery_set_floor_unread`, and reads every set as without it) — `optional` establishes the session as before, and `required` interrupts it for a first binding — when every counting factor refuses this user (`enrollable(user)`), the list is empty and each such login is said at warn (`mfa_enrollment_nothing_enrollable`, the kinds alone) — asking the account-email proof first where the gate does (below). A federated login is not asked (the federation callback does not consult admission in this release).

## The login's interruption

A password login the requirement interrupts is answered `403` once the express session is regenerated — left unauthenticated — and the login's MFA transaction opened, bound to the regenerated session (`binding: { kind: "session", id }`, which every later use compares whole); no session is written until the ceremony completes. The body is the closed shape core validates, and the page reads nothing else:

```json
{ "error": "mfa_required", "transaction": "<id>", "expires_in": 600 }
```

```json
{ "error": "mfa_enrollment_required", "transaction": "<id>", "expires_in": 600,
  "hints": { "enrollable": ["totp"], "email_proof": false } }
```

- `transaction` is 32 random bytes, base64url. It is not a bearer: every use compares the session it is bound to with the browser's, so the page keeps the cookie the `403` set. It travels only in request bodies and the `MFA-Transaction` request header — never in a URL.
- `expires_in` is `mfa.transactionTtlSeconds`; the transaction expires then, and the user starts again from the password.
- `mfa_required`: the subject holds a factor; the page asks for it.
- `mfa_enrollment_required` (`required`, no record that serves — none, or recovery sets with no code left — or, from `POST /session/mfa/verify`, a login reopened for a binding, below): `hints.enrollable` lists the counting factors this user may enroll, in registration order; `hints.email_proof` says whether the account-email proof comes first, and the transaction requires exactly what it says (the gate, under [The routes](#the-routes)).
- The login's `403` carries a fresh CSRF token, as a successful login does; a reopened login's, answered by `POST /session/mfa/verify` on the same browser session, does not need one. Core checks the login's body (`checkInterruptionAnswer`); the reopened one is built by this package to the same shape.

## The routes

Mounted at `/session/mfa` ([`src/routes.mts`](src/routes.mts), over the coordinator in [`src/coordinator.mts`](src/coordinator.mts)); the page is the deployment's (the MFA ADR's D6). The routes complete a login's transaction, and an `enroll` one a signed-in session opened — to add a factor, or to give the account-email proof a first binding in that session asks for.

- **Every answer** carries `Cache-Control: no-store`.
- **Every POST** sits behind the deployment's CSRF guard (`csrfGuard`: the session's double-submit token, or a same-origin `Origin` / `Referer`; refused `403 access_denied`), then the flood guard, the deployment's `rateLimiter` per client address under `mfa:ip:<ip>` (`429 rate_limited`; `503` while it is down and its `failMode` is `closed`; none without a limiter), before anything is read. Bodies are JSON or a form, parsed on these paths alone.
- **The transaction id** travels in the body's `transaction_id` or the `MFA-Transaction` header — the header alone on the `GET` — and never in a URL; two that disagree name none. A transaction bound to another browser, missing, malformed, spent, expired, or neither a login's nor an `enroll` one of the signed-in session presenting it — its `sid` and subject — is answered alike, spending nothing: `400 {"error":"invalid_request","error_description":"Unknown or expired MFA transaction"}`.
- **A login begun before a revocation.** Every use of a login's transaction — its read, a challenge, a verification, the account-email proof, an enrollment's start and completion, a login reopened after a recovery code — compares its continuation's `authTime` with the subject's sessions boundary (`subjectRevocation.revokedBefore`, the revocation skew of one second allowed), in whole seconds as token verification compares `auth_time` (core's `claimCoveredByRevocationBoundary`): one at or before it — a revocation, or a password change, since the login began — is `401 {"error":"login_required"}`, spending and binding nothing, and said at info (`mfa_login_revoked`). A boundary that cannot be read, or answers neither a date nor none, is `503` (`mfa_store_unavailable`, `store: "revocation_boundary"`). With no `subjectRevocation` wired, none is read; the step-up reads a session's own transactions alone, never a login's boundary. The boundary is read once per call: a revocation that lands while one call runs can still let that call bind, and the session it makes is dead at its first admission.
- **A signed-in session** is admitted before its transaction is read — to enroll, as `mfa.manage`; to give the proof or read its transaction, through the requirement's `mfa.step_up` remediation, which holds it to a live, unrevoked session alone — and its `User` is the one its cookie holds (`cookieSessionUser`). Not signed in, no longer live, or revoked: `401 {"error":"login_required","error_description":"Log in again"}`; a requirement's or a store's outage: `503`. A login's ceremony runs on a browser session that is not signed in yet, and admits nothing.
- **A factor** is named by `factor_id`, one of the subject's that an installed factor verifies; anything else is `400 {"error":"invalid_request","error_description":"Unknown second factor"}`, spending nothing.
- **An outage** — a store that cannot answer, or answers outside its port's contract (core's `readMfaAttemptReservation`, `readMfaSubjectAttemptReservation`, `isConsumedMfaTransaction`, `isMfaFactorUpdateWritten`), a factor whose data does not open, a factor that throws — is `503 {"error":"temporarily_unavailable","error_description":"MFA temporarily unavailable"}`, logged once at error; never a wrong code, never "no factor", never a verification.

**The subject lock** (D21, [`src/lock.mts`](src/lock.mts)), on a login's verification, under `mfa.lockout`. A proof whose factor is guessable (TOTP) reserves one of the subject's attempts, which counts as a failure until it settles: `success` once the factor was written — ending the consecutive run, refunding nothing of the week; `void` when the proof was right and completed nothing — a transaction another verification consumed, a consume or factor write that failed or lost its compare-and-set — removed as though never made; a failure otherwise, a factor that throws included, so a proof crafted to make a factor throw buys no free guess. A store that cannot reserve is `503`, nothing checked; a settle the store does not take is one `mfa_subject_lock_unsettled` warning, the answer standing and the attempt counted. A hold — the backoff from the `threshold`-th consecutive failure, the weekly budget, the hard limit — answers `429 mfa_locked` with the hold, `Retry-After` in whole seconds rounded up (none for `hard`, which no time and no exempt proof lifts: only a release once every guessable factor is bound again, or the operator reset, below. For `hard`, the attempt that is the hardLimit-th since the last success holds, whatever its outcome: a correct hardLimit-th code still signs in, but guessable proofs stay held), `attempts_remaining` — the refusal spent one of the transaction's — and `usable_kinds`: the exempt kinds the subject holds — installed, not guessable, with at least one record — each once, in code-unit order. It names them and judges none: a recovery set with no code left, one whose key left the ring, or a record whose data does not open is listed, and whether it works shows at its verification (`401` / `503`). That is display; the judgment — what a login asks for, what a step-up offers — is [`src/factorState.mts`](src/factorState.mts)'s, where a set with no code left serves nothing. A proof whose factor is not guessable — a recovery code, a WebAuthn assertion — reserves nothing and passes during every hold; once its factor was written it records an exempt success, ending a consecutive run before the hard hold is fixed, never the hard hold, never the week. The account-email proof is not held and records no exempt success.

**A recovery code** ([`src/recovery/factor.mts`](src/recovery/factor.mts)) is read as the long code is — either case, hyphens anywhere, `O`/`I`/`L` for the digits — and compared with every digest of the set it names; a match is spent by writing the set without it, by compare-and-set. A digest whose key left the ring is `503` before an attempt is spent (`mfa_factor_unreadable`, `state: "key_unavailable"` with the `keyId` to put back), never a code refused: a set's digests stay under the key they were made with, so that key stays in the ring for as long as the set is kept — or the set is regenerated (`POST /session/mfa/recovery-codes`, below). A set carries its generation, and the subject's recovery-set floor in the MFA transaction store retires every set below it: a regeneration, or a first binding by the account-email proof, writes its set one generation past the newest and raises the floor to it. A code of a retired set is refused unchecked as an invalid code (`401 mfa_invalid`), spending no attempt; the floor is read before the attempt and again once the code is spent, so a code spent while a regeneration raised the floor is refused too, its transaction spent. A set written before generations were kept reads as generation 0. A retired set left stored (a sweep that failed) is not offered by a transaction and is listed `retired`: the offer and the list read the floor once, bounded, and only for a subject whose records hold a set — when no set it can read stands at or above it, the records are listed again, since a regeneration writes its new set before it raises the floor; a floor they cannot read is said at warn (`mfa_recovery_set_floor_unread`), the records are listed again and every set reads as without it, so an outage hides no set from the offers or the list — but a recovery code's verification reads the floor itself and is `503` while it cannot, so a subject whose only way in is a recovery code waits the outage out. Routing reads it the same way, so every judgment agrees on what is usable: a retired set, like an exhausted one, gives a step-up nothing to qualify on (`403 mfa_no_qualifying_factor`), and a password login asks for no second factor over it — under `optional` a subject holding nothing else signs in by password. A floor routing cannot read is no floor: the step-up opens, the login asks. A set with no code left is kept, for audit, and refuses every code: no transaction offers it, a login does not ask for it, and a step-up beside nothing else usable is `403 mfa_no_qualifying_factor`; `usable_kinds` still names its kind.

**The email factor** (F5, [`src/email/factor.mts`](src/email/factor.mts)), on with `mfa-email-factor.enabled` and a `mailSender`. It counts, adds `email` — and `mfa` only with `addsMfa`, so an email login alone does not meet `urn:o3co:acr:mfa` unless the deployment says so — and is guessable: its code is held to the subject lock.

- **A login code** is six digits from the CSPRNG, mailed at each challenge to the login's address while it matches the digest the factor recorded (Mail, below), living `codeTtlSeconds`, capped at the transaction's expiry. It is kept only as a keyed digest bound to the transaction and the factor, and stands across wrong attempts until a resend replaces it: an earlier code is then refused. A verification takes the code with the whitespace around it, nothing else.
- **Its enrollment** mails a long code to the account's address — the login's `User`'s at a first binding, the session's cookie `User`'s from the account page — never one a request names; the code lives `codeTtlSeconds` and a resend replaces it. The record keeps only the keyed digest of the address that code went to, as the coordinator kept it at the send: no address, and no hint. Its identity (core's `MfaFactor.identity`) is that digest with its key id: the same digest under the same key is the factor enrolled already, `409 mfa_factor_duplicate` (below) — at the start, before a transaction is opened or a code sent, and at the completion; the same address enrolled under two keys is not seen as one, which `mfa.maxFactorsPerSubject` bounds. A first binding is not affected: it stands only alone. A first binding under `when-mail` with a sender wired mails twice: the account-email proof, then the enrollment code. From the account page, the address is the one the session's `User` held at its sign-in: one the Store changed since gives a factor refused at its first login.
- **A changed address.** A login code goes out only while the Store's address matches the recorded digest; otherwise the factor is `403 mfa_factor_refused` (Mail, below). The stale record stays — listed, refused at each challenge, counted toward `mfa.maxFactorsPerSubject` — until the user removes it (`POST /session/mfa/factors/remove`; the list says `address_changed`) or the operator resets the subject; the user enrolls the new address beside it, with recent MFA.
- **Keys.** At each login the factor records its digest again under the ring's first key, so a retired key leaves its records as they are used. A record unused since its digest's key left the ring is `503` (`mfa_factor_unreadable`, `state: "key_unavailable"`) at its challenge until the key is put back or the factor re-enrolled.
- **While the subject is held.** The challenge does not read the lock: a held subject's code is still mailed, up to the sender's limit (`429 rate_limited`), and is refused where it is verified — `429 mfa_locked`, spending one of the transaction's attempts. How many codes go out during a hold is the sender's limit, which the deployment sets (the runbook, "Mail"); `@o3co/auth-provider-standard`'s SMTP sender has no limit setting, so with it the cap is the relay's quota. The deployment's `rateLimiter` bounds each client address's requests, challenges included — its `limits.mfa`, or else its `defaultLimit` — and with the limiter declared absent, nothing does.

**The login's completion.** The verification's additions — the factor's `amr` values, `mfa` when the factor adds it, and `mfaAt` — go to core's `resumePrimary` with the continuation the transaction carried, and every other requirement not yet done in that login is asked. `establish` is written through the `loginCompletion` slot, the session recording `amr` `["pwd", "otp", "mfa"]` for a TOTP login (`["pwd", "hwk", "mfa"]` or `["pwd", "swk", "mfa"]` for a WebAuthn one, `["pwd", "email"]` for an email one — `mfa` beside it with `addsMfa`) and `authentication.mfaAt`; another requirement's interruption is answered through it too (its ceremony on a regenerated session, its `403` with a fresh CSRF token). A requirement's store that cannot answer is `503` with admission's line; a session store that cannot is `503 {"error":"temporarily_unavailable","error_description":"Session store unavailable"}`, rolled back.

**The first binding** (F3, D24, D25; [`src/enrollment.mts`](src/enrollment.mts)). A login's transaction whose `enrollment` is not `none` binds one counting factor the login's `User` may enroll:

- **Refused, spending nothing:** a transaction that asks for a second factor (`400 {"error":"invalid_request","error_description":"No enrollment is open in this MFA transaction"}`) — so a subject whose only record does not open never binds; a kind that is not a counting factor this user may enroll (`400 … "Unknown second factor kind"`); a completion with no enrollment begun or one expired (`400 … "No enrollment is pending in this MFA transaction"`); a label a page cannot show (`400 … "Invalid label"`); while the account-email proof is owed, `403 {"error":"mfa_email_proof_required"}` — D25's flag is read again at each call, so a flag an operator reset set after the transaction opened makes it owe the proof; once the subject holds a record that may count — another session bound one — `401 login_required`; and, at the start and at the completion, a login the subject's first-binding mark distrusts (below) — `401 login_required` with `Retry-After`, no secret shown. A factor that cannot start its enrollment (the WebAuthn factor for an account whose username is not well-formed text), or cannot say whether the user may enroll it (its `enrollable` throws — at the start, nothing opened, or at the completion, before an attempt is spent), is `503`, once at error (`mfa_factor_enrollment_unavailable`, with its `kind`), and never falls back to another name or reads as an unknown kind.
- **The completion, in order:** the subject's first-binding mark read (a login it distrusts is refused, nothing spent); an attempt reserved (`mfa.maxAttemptsPerTransaction`; the proof of possession is never held to the subject lock); the proof checked by the factor; its data sealed; **the subject's records read under the lease**, and the binding judged on them again — a record that may count beside it is `401 login_required`, nothing written and the transaction kept; **the mark read again under the lease**, which covers one noted since the first read (a login it distrusts is `401 login_required` with `Retry-After`, one that cannot be read `503`, nothing written and the transaction kept with the attempt reserved); **the mark noted** (one that cannot be noted is `503`, the attempt reserved and the transaction kept); **the transaction consumed** — of two completions of one transaction at once one binds, the other is answered as a spent transaction, and no factor is written twice; **the factor written** (`binding`: `email_proof` when the proof was given, else `password`), only while the records stand as the lease read them — when another write landed since (another login of the subject bound one at once past its lease, or a reset ran), it is not written and the answer is `401 login_required`, the transaction spent; D25's flag consumed under the lease where the proof was given; the recovery codes written as one `recovery_code` record, each code only as a keyed digest; the enrollment witness marked; then the login resumes through `resumePrimary`, with the factor's `amr`, `mfa` and `mfaAt`, and is established or answered by another requirement.
- **What stands when a later write fails:** a factor that cannot be written is `503`, the transaction spent; recovery codes that cannot be written, or marked shown (the set is written unshown and marked shown by compare-and-set just before its codes are answered), leave the binding standing and the answer says so — `"recovery_codes_issued": false` in place of `recovery_codes`, one `mfa_recovery_codes_unwritten` line, or `mfa_recovery_codes_conflict` at warn when another write of the subject's factors landed first — so the page can point to regenerating them (`POST /session/mfa/recovery-codes`); the list says `recovery_codes_shown: false` for a set never answered; a witness that cannot be marked is one `mfa_enrollment_witness_unwritten` warning, healed at the next password login that verifies a counting factor. With the recovery-code factor off, the answer carries neither key. The codes are in this answer alone, and at a login the set is marked shown only as that answer is made, once the session is established: when another requirement interrupts the resumed login (its `403` is the answer), core refuses the continuation (`401 login_required`) or the session store is out (`503`), the set is written and left unshown — listed `recovery_codes_shown: false` — and a mark that fails answers the login with `"recovery_codes_issued": false`. The session a first binding establishes records the login's `User` as it was — not enrolled — until the next login.
- **The first-binding mark** ([`src/firstBindingMark.mts`](src/firstBindingMark.mts); D12). A first binding — at a login, after a recovery code, or from the account page — notes the subject's mark in the transaction store (`noteFirstBinding`), dated as it is noted rather than when the request began, once its proof is checked, before its transaction is consumed and its factor written; a verification that marks the witness notes it first, unless the directory cannot write the witness. It stands `max(mfa.manage.maxAgeSeconds, 2 × mfa.transactionTtlSeconds)` plus twice `DEFAULT_CLOCK_SKEW_MS` and one factor-set lease (31 minutes 20 seconds by default) — the lease a write it marks may still be landing in. A session or a login authenticated no later than the mark plus `DEFAULT_CLOCK_SKEW_MS` and one factor-set lease — the lease the marked write may still be landing in — may hold a `User` read before the subject enrolled, so it binds no first factor (one request that stalls longer than `DEFAULT_CLOCK_SKEW_MS` and one factor-set lease between its note and its witness's mark leaves a sign-in of the same subject in that stretch past the mark, since the mark is noted once, and that sign-in binds a first factor only once the factor-store record the request wrote is lost) — at a login's start and completion, at a login reopened after a recovery code, and in a session at admission and at its enrollment's start and completion: `401 login_required`, nothing spent, said at info (`mfa_first_binding_distrusted`); the MFA routes' own answer carries `Retry-After`, the seconds until a fresh sign-in passes the mark on that replica's clock (admission's `401` carries none). A mark that cannot be noted refuses the first binding `503`, nothing written, the transaction kept with the one attempt its proof reserved — the store's port cannot release it, so outages that outlast the attempts end the transaction — and a memory store at its cap, or Redis down, never lets a binding through unmarked; a verification that cannot note it leaves the witness unmarked (`mfa_first_binding_unnoted`, warn), and the login completes. A mark that cannot be read is `503`.
- **The re-login wait.** Any noted mark — a first binding that stands, one refused or failed after its note (a lost race, a factor store that fails at its write), or a login that marked the witness — refuses a first binding to every sign-in no later than it plus `DEFAULT_CLOCK_SKEW_MS` and one factor-set lease: fresh logins too, for 6 minutes 20 seconds at the default `mfa.storeTimeoutMs`, and up to 5 minutes more across replicas whose clocks differ by the skew. Under `required`, a factor-store blip at a first binding therefore keeps that subject from logging in until then; the Store's witness, where it keeps one, answers such a login `503` first (D12). It fails closed by design. Replicas' clocks must agree pairwise within `DEFAULT_CLOCK_SKEW_MS` (run NTP): they date both the sign-ins and the mark.
- **At most one first binding.** Two first bindings of one subject that run at once take the subject's lease one at a time, and the factor store fences each write on the set its lease read. One binds; the other is refused on its read under the lease — `401` at a login, `409 mfa_enrollment_conflict` from the account page, its transaction kept — and audited `mfa.first_binding_conflict`. So whoever holds a user's password — or, for a federated account, its upstream account — can race the owner and be refused, never gain a way in, and the audit shows the race; the remedy is a password change, which is the Store's — or, for a federated account, the upstream account at its identity provider.

**A login reopened for a binding** (F3, D24, D25; [`src/reopen.mts`](src/reopen.mts)). Under `required`, a login's verified proof that does not count — a recovery code — for a subject with no counting factor it can use completes no login. What follows is settled before anything is spent — before the transaction's attempt is reserved, so a refusal or an outage here spends no attempt, never the transaction and never the code: beside a record that may count (one whose data does not open, a kind no longer installed) the binding is `allowed`; otherwise it is a first binding, `required`, for which the login's `User` must not say the subject enrolled (`503`, `mfa.enrollment_state_inconsistent`). The counting factors the user may enroll must be some (none is `503` with `mfa_enrollment_nothing_enrollable`; a factor that cannot say is `503` with `mfa_factor_enrollment_unavailable`). A binding nobody could complete is refused with the code kept — `403 {"error":"mfa_enrollment_required","error_description":"A second factor that counts must be enrolled"}`, naming no transaction: an `allowed` one at `mfa.maxFactorsPerSubject`, a first binding whose factor and codes would pass it (below), or a first binding whose proof the gate (below) asks and nobody can give (`mfa_email_proof_unprovable`). The gate decides the proof over the address fact the sign-in recorded (core's `enrollmentFactsOfContinuation` — the snapshot taken at the password check) and D25's flag; a store that cannot answer the flag is `503`. Then the transaction is consumed and the proof spent, as any verification does (a lost race spends the transaction, never the code; a recovery code is an exempt success; a lost compare-and-set round settles all of this again over the records read after it, and a counting factor the subject can use then completes the login), and a new login transaction is opened over the same continuation, bound to the same browser session, living `mfa.transactionTtlSeconds`: the answer is the login's own `403 mfa_enrollment_required` naming it, with `hints.enrollable` and `hints.email_proof`, so the page takes the transaction from it. That `403` comes from `POST /session/mfa/verify`: the browser session is not regenerated, so it carries no new CSRF token, and its body is built by this package to the shape core's `checkInterruptionAnswer` holds a login's to, not passed through it. An outage opening it is `503` with the proof spent: the user logs in again. `mfa.verified` for a proof that reopens carries `reopened: true`. On the new transaction, which verifies no factor (`400 … "Unknown second factor"`) — it is for the binding, never for spending another code — so a login reopens once, and the new transaction ends within one `mfa.transactionTtlSeconds` of the first one's expiry:

- **`allowed`:** the binding is by `mfa`, asks no account-email proof — D25's flag is a first binding's alone — issues no codes, and is held to `mfa.maxFactorsPerSubject`, as from the account page.
- **`required`:** the first binding above, with the proof the gate asked. Bound by `email_proof`, its recovery codes replace the sets that stood: those are read under the subject's lease, the new set is written one generation past them and the subject's recovery-set floor raised to it — which retires them — then those alone are removed, each fenced on the set the lease read — another write of the subject's factors after that read stops the removals, so a set written by another binding is never removed; a removal that fails, or removals stopped, leave a retired set stored beside the new one, its codes refused, said once at error (`mfa_recovery_codes_unreplaced`), and the audit says `regenerated: true, unreplaced: true`. Bound by `password` — no proof was asked — it keeps the sets that stood, writing its own at their generation and leaving the floor, as every first binding by a sign-in alone does, from the account page too — by `password`, or by `federated` in a session signed in through a federation, which proved no second factor either (D25's amendment; `src/recovery/issue.mts`): the owner's remaining codes stay usable, and the audit says `regenerated: true, unreplaced: true, kept: "password_binding"` (`kept: "federated_binding"` for a binding by `federated`). The account-email proof is only as strong as the mailbox: where the account's address is a mailbox at the same identity provider as its federation, whoever holds the upstream account can usually give the proof too.
- **What a password and one code can do.** Where the gate asks no proof (`requireEmailProof = "never"`, or `when-mail` with no mail sender or no address) and the Store does not keep the witness, whoever holds the password and one recovery code of a user whose counting factor is gone binds the first factor — here, or from the account page under `optional`, where the code completes a login. The owner keeps their remaining codes and still signs in with them — then sees the factor they did not bind — and that factor stands until the owner removes it from the account page (step 12) or an operator removes it. The trail: `mfa.recovery_code.used`, then `mfa.factor.enrolled {purpose: "login", binding: "password"}`, then `mfa.recovery_codes.generated {regenerated: true, binding: "password", kept: "password_binding"}`; notify the account holder of the second and the third. A federated account is in the same place from the account page: whoever holds its upstream account at the identity provider signs in and binds the first factor by `federated` (`kept: "federated_binding"`), the owner's codes kept.

**An enrollment from the account page** (F4; [`src/enrollment.mts`](src/enrollment.mts)). `POST /session/mfa/enrollment {kind}` with no transaction admits the signed-in session as `mfa.manage` — the requirement's `credential_change` rule, [above](#the-mfa-requirement) — and opens an `enroll` transaction bound to the browser session, its `sid` and its subject, living `mfa.transactionTtlSeconds`: `enrollment: "required"` when the subject holds no record that may count, `"allowed"` beside one. `…/complete` admits the session again and compares the transaction's `sid` and subject with it, so a completion in another session, or once the requirement would step it up, binds nothing and spends nothing.

- **Another factor** — the subject holds one that may count — needs recent MFA (else `403 step_up_required`), binds by `mfa`, and is handed the subject's factors of its kind. Nothing beside a record that may count is ever a first binding, and a transaction keeps the binding it was opened for: a first binding's refuses a record that may count found at its completion, and another factor's refuses a subject left with none that may count — each `409 {"error":"mfa_enrollment_conflict"}`, since the session stands and the page starts the enrollment again; so is a first binding dropped because another stood beside it at once.
- **A first counting factor** needs a sign-in within `mfa.manage.maxAgeSeconds` (else `401 login_required`) and the gate's proof where it asks one (else `403 step_up_required`, below); it binds by `email_proof` when the proof was given on its transaction or in the session, else by the sign-in alone — `federated` in a session signed in through a federation (core's `sessionAuthentication`), else `password` — while no record may count — recovery codes alone included — with the one-first-binding check, D25's flag cleared by a proof, the recovery codes and the witness mark as at a login.
- **The limit.** A subject holding `mfa.maxFactorsPerSubject` records is answered `409 {"error":"mfa_factor_limit"}` at the start and at the completion, before an attempt is spent, and again on the records the completion's lease reads, before anything is written. Its writes are fenced on that read (see "The factor store's fence"), so completions made at once cannot together pass the limit: one whose factor's write finds the records changed is refused, its factor never written. Another factor's enrollment counts every record stored, a retired recovery set still stored included. A binding that replaces the recovery sets — a first binding by the account-email proof — and a regeneration count what stands once the replacement completes: no set stored is counted, though each is removed only after the new set is written. A sweep that stops leaves its sets stored, each retired by the floor, so the subject may hold one record past the limit for each set left, until a later regeneration's sweep removes them.
- **The limit at a first binding.** A first binding adds its factor and, with the recovery-code factor on, a set; the sets it replaces (an `email_proof` binding's) do not count, and the sets it keeps (a `password` or `federated` binding's) do. Where that would pass `mfa.maxFactorsPerSubject` it is refused `409 {"error":"mfa_factor_limit"}` before anything is spent — at the start, which counts the fewest records it can come to while the binding is not known, and at the completion, by the binding it makes — and again on the records the completion's lease reads, before anything is written. Its writes are fenced on that read, so bindings made at once cannot together pass the limit: a factor whose write finds the records changed is never written, the binding refused as one the records no longer allow; a set whose write finds them changed is not written, and the binding stands without codes (`recovery_codes_issued: false`, `mfa_recovery_codes_conflict`).
- **A duplicate.** A binding whose factor a record of the subject holds already — a record of its kind that answers the same identity (core's `MfaFactor.identity`: the email factor's address digest under its key, the WebAuthn factor's credential id; a factor without one, as TOTP, has no duplicate) — is `409 {"error":"mfa_factor_duplicate","error_description":"This second factor is already enrolled"}`. At the start and on the records the completion's lease reads, it is answered after a binding the records no longer allow and before the limit. Where the identity is known before the factor begins (the email factor's), the start refuses it, nothing opened, kept or sent. The completion refuses it once the proof was checked — the attempt spent, nothing written, the transaction standing — on the records read before the lease, and again on the records the lease reads, which decides. The completion's read before the lease judges the limit before the proof, spending no attempt, and the duplicate only after it, so there a subject at the limit is answered `409 mfa_factor_limit`. On the lease's read: of two enrollments of one authenticator that complete at once, the later to hold the lease finds the earlier's record and is refused, so one stands, and nothing is removed to settle it. The answer names no record: the caller holds the session, and the factor list shows it. An `identity` that throws is read as none — the record a duplicate of none — said at warn each time it is read (`mfa_factor_identity_unavailable`, its `kind`).
- **What `binding` says.** `password`: bound on a password sign-in alone; `federated`: bound on a federated sign-in alone, at the upstream identity provider; `email_proof`: after the account-email proof; `mfa`: beside a factor, with recent MFA. A login is interrupted for a binding only after a password, so a login's first binding is never `federated`.
- `GET /session/mfa/transaction` lists no factor for an `enroll` transaction: it verifies the account-email proof alone. A body and an `MFA-Transaction` header that name different transactions are `400`, and open none.
- A binding escalates the session it was made in, as a step-up does ([below](#the-step-up-of-a-second-factor)), by the factor's `amr` and the binding's time. The factor and its codes are answered `200` whatever the escalation came to, since the codes are shown once: a renewal that fails at its save signs the browser out; a record that fails leaves a session never escalated before as it was, and signs out one escalated before, whose record keeps the earlier nonce ([below](#the-step-up-of-a-second-factor)); a store that answers the session without the new nonce has the session ended; each failure is logged as at a step-up. A session store without the step-up capability keeps the session as it was.

**The step-up of a first binding** (the MFA ADR's F2 first-binding branch, D24). `POST /session/mfa/step-up` admits the session through the requirement's `mfa.step_up` remediation, then asks the requirement, as `mfa.manage`, what a first binding in it is answered: a witness that says the subject enrolled with no counting record, or a store's outage, is `503`; a sign-in older than `mfa.manage.maxAgeSeconds`, or a session that recorded no facts, `401 login_required`. A subject who holds a record that may count gets the step-up of a second factor (below); another requirement's step-up is answered as that requirement's `403 step_up_required`; under `required`, a password session whose subject holds no counting factor never gets here — it is sent to log in again. Otherwise it answers an `enroll` transaction owing the account-email proof: the one `transaction_id` names, when it is the session's own first binding's and its proof is not met, or a new one. The proof is given on it through `POST /session/mfa/challenge` and `/verify` with `factor_id: "account-email"` (below), mailed to the address the session's login `User` carried; a verified proof is recorded for that session alone (`MfaTransactionStore.recordSessionEmailProof`), standing `mfa.manage.maxAgeSeconds`, and every first binding in the session is admitted on it while it stands. A proof lost with the store is given again. An `enroll` transaction takes the account-email proof alone: any other `factor_id` is `400 … "Unknown second factor"`.

What the page does with a first binding's `403 step_up_required` — from the link start, WebAuthn registration or `POST /session/mfa/enrollment` — and with the step-up's answers is [The MFA page's contract](#the-mfa-pages-contract)'s.

**The gate** ([`src/firstBinding.mts`](src/firstBinding.mts)) is one function for every first binding — a first factor at a login, and, in a session, a first factor, passkey or linked identity — over what each caller hands it: `mfa.enrollment.requireEmailProof`, whether a `mailSender` is wired, the account's address as the session's enrollment facts say it (core's one reading: `none`, `address`, or `unreadable` — present, and not one address `normaliseMailAddress` reads), and D25's flag. `when-mail` asks for the proof when a sender is wired and the account has an address, or one it cannot read; `always` always; `never` never, whatever the address; the flag always. A proof asked for that nobody can give — no sender, no address, an address no proof can be sent to — is asked for and refused (`403`), never skipped, and said at warn at each login or admission that asks it (`mfa_email_proof_unprovable`, with the reason, never the address). At a login the proof is kept on the login's transaction; in a session, for that session alone, `mfa.manage.maxAgeSeconds`.

**The step-up of a second factor** (the MFA ADR's F2; [`src/stepUp.mts`](src/stepUp.mts), and the finish, `createSessionEscalation`, in [`src/escalation.mts`](src/escalation.mts)). For a subject holding a record that may count, `POST /session/mfa/step-up` answers a `step_up` transaction bound to the browser session, its `sid` and its subject, owing no proof, living `mfa.transactionTtlSeconds`: the one `transaction_id` names when it is the session's own `step_up` transaction — answered as it was opened, a newly posted `acr_values` not recorded — else a new one; any other named transaction is `400`. None is opened where admission's view says no second factor can be recorded on the session (`secondFactorRecordable`: a store without `recordSecondFactor`, or a record not in a shape one can be recorded on; `401 login_required`, a session already holding recent MFA included), or when the subject holds no factor of an installed kind whose data opens (`403 {"error":"mfa_no_qualifying_factor","error_description":"No second factor of this account can be used for a step-up"}`: only a kind no longer installed, say, or only a TOTP whose key left the ring). A session that already holds recent MFA may step up again, for a fresh `mfaAt`.

- **What is offered.** Every factor the subject can use — of an installed kind, its data opening, a recovery set with a code left — listed by `GET /session/mfa/transaction` with `purpose: "step_up"` — a recovery code included: it adds `recovery` and `mfa`, and under `required` it is accepted beside no counting factor that can be used, opening no binding. `acr_values`, a string the body may carry, is read strictly — space-delimited, at most 16 values of at most 256 characters, anything else recording none — and kept on the transaction as a hint only: it chooses no factor here, and `/authorize` decides on the browser's return whether what was added meets it (D17).
- **The verification** is a login's: `POST /session/mfa/challenge` and `/verify` with the factor's id, the transaction's attempts, the subject lock (its audit says `purpose: "step_up"`), the compare-and-set rounds, and an exempt factor's success dated by the verification's time, as `mfaAt` is. An email factor's code is a login code, mailed to the address the session's `User` carried at its sign-in and compared with the digest the factor recorded. This package reads no directory: where the account's address has since changed in the Store, a login refuses the old one (the digest no longer matches), while a step-up mails the address the session signed in with until the user signs in again; a stale email factor is step 12's to manage. A counting factor verified in a session whose recorded witness does not say enrolled — none recorded included — notes the first-binding mark, then marks the witness, as at a login. A `step_up` transaction takes neither the account-email proof nor an enrollment (`400`).
- **The finish** runs behind the session's admission, which compared the cookie session's renewal nonce with the record's. What the verification adds is held first to the `mfa` requirement's sealed reach (one outside it is `500`, nothing renewed). Then the express session id is renewed with a fresh renewal nonce (`loginCompletion.renewSession`; an answer without one is the cookie store's outage), then the second factor is recorded on the `UserSession` (`recordSecondFactor`: the factor's `amr`, `mfa` when it adds it, `mfaAt`, the new nonce, expecting the one admission compared) — once, never retried, since a retry after a write that landed would expect the old nonce and undo it. The store's answer must be this session's record (its `sid`, subject and dates). Once recorded with the new nonce: `200 {"step_up":"verified", "recovery_codes_remaining"?}` with a fresh CSRF token. Otherwise:

| What happened | Answer | Logged |
| --- | --- | --- |
| What the verification adds is outside the `mfa` requirement's reach | `500 server_error`, nothing renewed or recorded | error `mfa_escalation_invalid` |
| The renewal failed, or answered no renewal nonce | `503`, nothing recorded: at its save the browser is signed out; at its regeneration, or without a nonce, the old cookie session stands, not stepped up | error `mfa_store_unavailable` (`store: "cookie_session"`, `step: "regenerate"`, `"save"` or `"renewSession"`) |
| The record is gone, another completion from the same cookie session was recorded first, or the record predates how a session was established | `401 login_required`, the renewed cookie session left as it is: at its next admission it is `not_live`, or below the step-up's level | info `mfa_escalation_not_recorded` |
| The store answered the session without the new nonce | `500 server_error` "The session could not be secured: sign in again": the escalation would stand bound to no cookie session, so the session is ended (`UserSessionStore.delete`) and every cookie of it refused; a removal that fails is the store's outage, logged too | error `mfa_escalation_unbound` (and `mfa_store_unavailable` `user_session` `delete` when the removal fails) |
| The store refused the event (`RangeError`) | `500 server_error` | error `mfa_escalation_invalid` |
| Any other failure, or an answer that is not this session's record | `503`: the renewed cookie session stands, not stepped up | error `mfa_store_unavailable` (`store: "user_session"`, `step: "recordSecondFactor"`) |

- **What a renewal orphans.** Records bound to the old express id: a consent `/authorize` parked, a federation-grant browser binding, the session's other open MFA transactions; other tabs holding the old cookie go `not_live`. A `POST /session/logout` from the old cookie ends only that cookie session once the escalation is recorded; one whose read of the record ran before the record landed deletes the record, ending the renewed session too — availability only: the user signs in again. The `/authorize` re-authentication ask survives, keyed in the session store under its own prefix. An authorization code carries the `amr` decided at `/authorize`, per code: a user's own code minted just before their own step-up stays `pwd`-only, and the page's return to `/authorize` mints a fresh one.
- **A record that fails after a renewal.** The cookie session then holds a nonce the record does not. A session never escalated before stays as it was, below the step-up's level, and is answered `401` at its next step-up, which expects that nonce; one escalated before keeps the earlier nonce on its record, so it is `not_live` at once. Either way the user signs in again. Reading the expected nonce from the record admission read ([#940](https://github.com/o3co/auth.provider/issues/940)) removes it.

**Managing factors** (F4; [`src/management.mts`](src/management.mts)). The account page lists, renames and removes the signed-in subject's records; a session that is not admitted is answered as at an enrollment (`401 login_required`, `403 step_up_required`).

- **The list** is admitted as `mfa.view`, a `use`: under `optional` any live session of the subject can list — one signed in by password alone, before any first binding, included — and under `required` the baseline. Each record's `state` is [`src/factorState.mts`](src/factorState.mts)'s — `usable`, `unreadable` (its data does not open, or a digest it holds names a key the ring no longer holds — said at error, `mfa_factor_unreadable` with the `keyId` to put back), `not_installed`, `exhausted` (a recovery set whose codes are all spent), `retired` (a recovery set below the subject's recovery-set floor: replaced by a newer one and left stored, its codes refused — removed by the next regeneration, or from the list) — or `address_changed`, an email factor whose recorded digest is not the address of the session's login `User`; one with no readable digest, or beside a `User` with no address, is `unreadable`. A date a record holds that is not a valid date is left out; one that is no date at all is `503`. A session begun before the account's address changed holds the old address: it lists, and a step-up's email code is mailed, against that address until the user signs in again.
- **A recovery set** in the list says how many codes it has left (`recovery_codes_remaining`) and whether its codes were ever answered (`recovery_codes_shown`): `false` for a set whose answer never went out — a page points the user to regenerating it.
- **A regeneration**, `POST /session/mfa/recovery-codes`, needs recent MFA (`mfa.manage`) and a record that may count — a subject without one, whom `mfa.manage` admits on a recent primary, is `409 mfa_enrollment_required`, since codes never stand alone. Under the lease it reads the subject's first-binding mark: a session signed in no later than it plus `DEFAULT_CLOCK_SKEW_MS` — one admitted on a recent primary while no factor stood, the owner binding one since; or the session that just bound the first factor, which got codes with it — is `401 login_required` with `Retry-After`, said at info (`mfa_first_binding_distrusted`) — widened by one lease past the skew, since the owner's factor may land up to a lease after its mark and a sign-in in that stretch on a clock up to the skew ahead must not pass. Every mark distrusts the same way, so the `401` also meets, until the sign-in is later than the mark plus `DEFAULT_CLOCK_SKEW_MS` and a lease (6 minutes 20 seconds by default): the session whose login reconciled the witness, a session signed in before a binding that stepped up after it, and a fresh MFA login on another device within the skew; a step-up in a session whose witness is not `enrolled` notes the mark again at that moment, and so arms the `401` again. A request that reached its lease longer after it began than a mark can be relied on — its lifetime less the skew and a lease — is `409 mfa_request_stale`: a mark noted meanwhile may have lapsed. It is held to `mfa.maxFactorsPerSubject` as a binding's codes are: a subject at the limit holding no set is `409 mfa_factor_limit`; replacing a set at the limit stays allowed. It runs whole under the subject's lease, as a removal does: the records read, the floor read, the new set written (`binding: "mfa"`) one generation past the floor and every set it can read, the floor raised to it, every set that stood removed — those it cannot read included — and the set marked shown just before its codes are answered. Every write of the set is fenced on the records the lease read: when another write of the subject's factors landed since — a writer past its own lease — the new set is not written, the floor is not raised, and its codes are never answered, `409 mfa_recovery_codes_conflict` (warn, `mfa_recovery_codes_conflict`); one landing after the new set stops the removals, every set left retired by the floor and said as `unreplaced`, and the next regeneration removes it. A floor that cannot be raised removes the new set and keeps the old codes (`503`); a mark that fails answers no codes (`503`, `mfa_recovery_codes_unwritten`), the set left unshown and every set that stood retired, so the user regenerates again. Audited `mfa.recovery_codes.generated` (`binding: "mfa"`, `by: "user"`, `regenerated`, and `unreplaced: true` when a retired set is left stored — its codes verify nothing). Codes marked shown are answered even when the lease ended before its release, said at error (`mfa_subject_lease_overrun`, `route: "recovery-codes"`).
- **A rename** writes the label (1 to 64 characters a page can show as they are) by compare-and-set at the version read, the record's data and last use as read; a verification or another rename landing in between is `409`, and the page reads the list again.
- **A removal** needs recent MFA (`mfa.manage`), and runs whole in [`src/factorSet.mts`](src/factorSet.mts). Under `required` the subject keeps a usable counting factor: removing an installed counting factor is `409 mfa_last_factor` when no other usable one stands — a record of a kind no longer installed, one whose data does not open, or an email factor whose address changed does not stand in for it; a recovery set and a retired kind are always removed. A store that fails after it removed the record is read again, and a record gone is a removal. It is audited `mfa.factor.removed` (`kind`, `factorId`, `binding`, `by: "user"`). The records are then read again — unreadable, said at warn (`mfa_factor_removal_unread`), those read before less the removed one decide — and once none that may count stands (`mayCount`: a kind no longer installed counts), the enrollment witness is cleared (`markMfaEnrolled(subject, false)`), after the removal (D12). A clear that fails is said at warn (`mfa_enrollment_witness_uncleared`) and the removal stands: the witness then says enrolled beside no counting record, so the subject's next password login is `503` (`mfa.enrollment_state_inconsistent`) until the Store's flag is cleared — fail-closed. Sessions are not ended: a password session whose login recorded the subject enrolled is sent to log in again for its next first binding — an enrollment, a rename, a removal, a link or a passkey — and the fresh login reads the cleared witness; a federated one is answered `503` there, recorded, until it signs in again.
- **One write at a time.** A removal and a verification's witness mark run under the subject's lease in the MFA transaction store ([`src/factorSet.mts`](src/factorSet.mts), the one place the lease and the subject's generation are used), held to the generation read before the session was admitted — or, for a mark, before the proof was checked; a ceremony that writes later carries its own from its begin. Two removals, or a removal and a mark, run one after the other: under `required` one of two removals of the last two counting factors is `409 mfa_last_factor`. Another write in the way is waited for up to about three quarters of a second, then `409 mfa_factors_busy` with `Retry-After` in the whole seconds its lease has left; a recovery or a reset that moved the generation since the request was admitted, or a write of the subject's factors that landed after the removal read them (see "The factor store's fence"), is `409 mfa_factors_changed`, nothing removed. A transaction store that cannot read the generation, give the lease or take it back within one `mfa.storeTimeoutMs` is `503`.
- **The lease's time.** The lease stands sixteen `mfa.storeTimeoutMs` — the most Store calls one writer makes under it (`FACTOR_SET_STORE_CALLS`, fourteen: a first binding by the account-email proof in a session makes thirteen over two standing recovery sets — a login's twelve, its set marked shown by its answer, past the lease; a regeneration makes six and one per standing set; each set beyond three at a binding, or eight at a regeneration, adds a removal the lease's time cuts off when it runs short — every set that stood is then already retired by the floor, the new set is left unshown, and the answer is `503`, to be tried again; the operator reset makes eight, a removal five, a mark four), the acquire, and one to spare — at least a second; a timeout whose lease would pass the longest subject lease (600 s) refuses the boot, and a test holds every writer to the count. From the acquire the write keeps a monotonic deadline: a read under the lease is given up when it would leave less than one `mfa.storeTimeoutMs`, and a write starts only with at least that much left. Given up before any write, the removal is `409 mfa_factors_busy` and a mark writes nothing; after a removal was written, the witness is not cleared and the removal is an overrun. A release that finds the lease gone is an overrun too, said at error (`mfa_subject_lease_overrun`) whatever the removal came to, a removal it made audited and answered `409 mfa_factors_changed`; a mark is answered unwritten, warned as one, and the next verification marks again.
- **A mark reads first.** Under the lease a mark reads the records: none that may count writes nothing (the witness is in step), none readable writes nothing and is warned; else it marks, reads again, and clears the witness again when a write outside the lease left none — a clear that fails, or a read again that fails, is warned.
- **The factor store's fence.** Every write of a subject's factor set under the lease — a removal, a binding's factor, a recovery set and the removal of the sets it replaces — is conditional on the set as the lease read it, right after the acquire: the factor store applies it only while no other write of the set landed since (`createIf` and `removeIf` at the set's store generation, held by [`src/factorSet.mts`](src/factorSet.mts) alone), and each write moves the generation the next is held to. So a write that stalls past its lease — a store slower than `mfa.storeTimeoutMs`, an evicted lease — and arrives after another writer's is refused, never applied, and never tried again: two removals cannot both pass `mfa_last_factor`, two first bindings cannot both stand, completions made at once cannot together pass `mfa.maxFactorsPerSubject`, and nothing read before a reset lands after it. A rename, and a verification's write of a factor's own data, are a record's update, fenced by its `version`, not by the set.
- **What the lease cannot do.** It is logical, and the directory and the MFA transaction store take unconditional writes: a witness mark or clear that stalls past its lease can leave the witness true beside no counting factor — the next password login is `503` until an operator resets the subject, fail-closed — and a transaction-store write that was not answered within its bound can land later. A binding's consume of D25's flag names its lease, and the store checks the lease in the same step, so a consume that lands after the lease ended clears nothing, not the flag a later reset set. Its line, `mfa_subject_lease_overrun` with `route: "enrollment"`, is the operator's sign to run the reset again. The operator reset's removal of every record is unconditional — the reset always wins — so a reset whose removal stalls past its lease still removes a factor bound after the reset began: its report says `overran`; run it again, and the user binds again. A conditional write that timed out is unknown: it lands if the set is still as it was read when it arrives. An acquire whose answer is lost after the store took it leaves the lease held for its time: the port names its own token, so the caller cannot claim it. Set `mfa.storeTimeoutMs` to at least every store's own per-call timeout; a store with none is not bounded at all.
- **An enrollment** runs under the lease too: the subject's generation is read where it begins — before the session's admission, or at a login's begin — carried in the sealed pending enrollment, and its completion's writes (the first-binding mark, the transaction's consumption, the factor, the recovery codes, the witness) run whole under the lease acquired at it, each held to the lease's time. Every write of it, the transaction store's included, goes through what the lease hands it. A reset or a recovery since it began is answered as a binding the records no longer allow, nothing written; another write in the way past the wait, or too little of the lease left before the first write, is `409 mfa_factors_busy`, nothing written and the transaction standing — the attempt the completion reserved before its proof was checked counts, as any completion's does; a completion that runs out of the lease after a write — the transaction spent — answers what it wrote, said as an overrun (`mfa_subject_lease_overrun`), never busy. Before any write, the binding is judged again on the records its lease read — a first binding beside a record that may count, another beside none, the limit — and every write after is fenced on them: a factor whose write finds them changed, another writer where a store's lease admits both (an evicted lease), is not written, and the binding is answered as one the records no longer allow, the transaction spent.

**The lock's release** ([`src/lockRecovery.mts`](src/lockRecovery.mts), [`src/lockRelease.mts`](src/lockRelease.mts)). No revocation and no password change clears the subject lock (D21); a factor that is not guessable — a recovery code, a passkey — authorizes the subject's own release.

- **The authorization** is minted when such a factor verifies, for the session it verified in: at a login once its session is established, and at a step-up once its session is escalated — so a user who signs in with a recovery code spends that one code. It lasts `mfa.manage.maxAgeSeconds` from the verification (its longest, 3600 s, is core's `MFA_RECOVERY_AUTHORIZATION_MAX_MS`), and a newer one in the session replaces it. A guessable factor (TOTP, the email factor), or a kind not installed, mints nothing. One the store cannot record is said at warn (`mfa_lock_recovery_unauthorized`), the answer standing.
- **The release**, `POST /session/mfa/lock/release`, is admitted as `mfa.manage`. It reads the subjects' sessions boundary (`revokedBefore`), then, under the subject's lease, reads the subject's records and hands the store the earliest creation time of those of any kind but an installed exempt one — a record whose data does not open included, and one of a kind not installed, which may be installed again (remove it from the account page) — and the store judges the rest in one step: the authorization standing in this session; for the week and the backoff, a boundary later than the attack's first counted failure by more than five minutes (`DEFAULT_CLOCK_SKEW_MS`); for the hard hold, every guessable record bound after the answer's `rebind_after` — the hold's time plus `DEFAULT_CLOCK_SKEW_MS`, as the store judges it. Applied, it is audited `mfa.lock.recovered` (`operation: "recover"`, the `generation`, what it `cleared`) and said at info (`mfa_lock_released`, or `mfa_lock_release_held` while the hard hold stands); a refusal is said at info (`mfa_lock_release_refused`, `reason`). `rebind_after` is in no log line: it shows roughly when the latest failed attempt was, which is the account holder's to see. A bound the store answers that no date can hold is `503`, never an answer without it; the release may already have applied by then, so a retry answers `already_applied` — what it came to. An authorization already applied answers what it came to, applying nothing more.
- **The order the page states**, and what it shows of each answer and of `rebind_after`, are [The MFA page's contract](#the-mfa-pages-contract)'s.
- **Sign-out-everywhere.** A host that lets a session that has not passed its second factor sign out everywhere hands whoever holds only the password the boundary the release asks for: the victim's next release then gives the week back with the password unchanged. Such a host asks the second factor for it.
- **What does not hold the lease.** A login that has not passed its second factor takes no lease of the subject's: its codes reserve attempts and nothing more, and a first binding at a login is open only where no record may count. So a password holder cannot keep the victim's release, or the reset, waiting.

**The operator reset** ([`src/reset.mts`](src/reset.mts), `mfaResetModule`): `resetMfaForSubject(subject, { requireEmailProof?, federationGrants?, requestedBy? })`, after the operator confirmed the account holder out of band — the reset is the account-takeover path if they did not. A subject that is not a non-empty string, a `federationGrants` other than `revoke` or `keep`, a `requestedBy` that is not 1 to 256 characters, or `requireEmailProof: true` with no mail sender is a `RangeError`, nothing done; an account with no address cannot give the proof either, and the provider cannot read the account by subject: check it in the Store first. Then, in order: every session and token of the subject's ended (`revokeAllForSubject`, the federation grants as asked and as policy allows) — a revocation that throws or is not complete stops it there; then, under one lease of the subject's, waited for up to two of its leases and never gone on without, each write started only with a Store call's time of the lease left: D25's flag when asked — set under the lease, so a binding that held it cannot clear it — the reset's own authorization, the lock state reset whole by it (the hard hold and every authorization included, the generation moved, so a write begun before stops at its commit; an authorization the store answers applied before is no reset), every record removed (`removeAllForSubject`: one sealed under a retired key, of a kind not installed, or a recovery-code set alike), and the witness cleared; then D25's flag set again, the last write under the lease, so a binding's consume of it that timed out and landed during the reset does not leave it cleared; then every session and token ended again, so a login made with a factor before its removal ends too. It answers a report — `complete` (both revocations complete, the lease held throughout), `stoppedAt` when a step did not complete (`sessions`, `lease`, `email_proof`, `lock`, `factors`, `witness`), `overran` when its lease ended before its release, both sessions' reports (`sessions`, `sessionsAgain`), the `removed` kinds and count once the removal succeeded, the `generation`, the `witness` (`cleared`, or `unwritable` where the directory cannot write it) — and is run again until complete. It emits one `mfa.reset` and no `mfa.lock.recovered`, and mails nothing: a deployment notifies the account holder from the audit.

**The account-email proof** ([`src/proof.mts`](src/proof.mts)): `factor_id: "account-email"` on a transaction that owes it — a login's, or an `enroll` one the step-up answered — (`400 … "Unknown second factor"` on any other).

- `POST /session/mfa/challenge` mails a long code — 16 Crockford base32 characters, 80 bits — and answers `200 {"sent_to":"a***@example.com", "expires_in":<s>}`, audited `mfa.challenge.sent` with `kind: "account-email"`. It goes to the address the login's `User` carried — at a login, the password check's answer; in a session, the `User` the session's cookie holds — never a later read of the Store, which has no read by id, so the address is at most the transaction's life old, or the sign-in's in a session, which the step-up holds within `mfa.manage.maxAgeSeconds`. The code lives ten minutes, capped at the transaction's expiry; a resend replaces it. No sender, or no address: `403 {"error":"mfa_email_proof_unavailable"}`.
- `POST /session/mfa/verify` takes the code as it was shown, in either case, with or without hyphens: `200 {"email_proof":"verified"}`, audited `mfa.verified`. It spends the transaction's attempts — five wrong codes end the transaction — and never the subject lock. The code stands across attempts until it is replaced. On an `enroll` transaction a right code also records the proof for its session; a store that cannot record it is `503`, and the proof is given again.

**Mail** ([`src/mail.mts`](src/mail.mts)): a factor's login code, an email factor's enrollment code and the account-email proof go through `sendMfaMail` — the account's address compared with the digest a factor recorded before anything is written, the pending state kept with the digest of the address the code goes to and handed back to the verification, then the sender handed the purpose, the subject, that address, the code and its expiry, and its answer read through `mailSendOutcome` alone. A factor whose recorded address no longer matches the login's, or that holds none it can read, is `403 {"error":"mfa_factor_refused"}`, audited `mfa.email_address_mismatch` with the subject and the kind — nothing sent, nothing kept. The sender's limit is `429 {"error":"rate_limited"}`; its outage, or no sender wired, is `503` with one `mfa_mail_unavailable` line. Either clears the pending code; the transaction stands.

**Audit** (the MFA ADR's D28), each with `subject`, `ip`, `userAgent`, and `kind` and `purpose` in its details: `mfa.challenge.sent`; `mfa.verified`; `mfa.verify.failure`, with `reason` — `invalid`, `expired`, `replayed`, `malformed`, `sign_count_regression` or `exhausted` — and `factorId` when the factor names the factor the refusal concerns (the WebAuthn factor's `sign_count_regression`): the record id of one of the subject's factors of that kind, which the coordinator checks, else left out; `mfa.email_address_mismatch`; `mfa.locked`, with `hold`, for every proof the subject lock refused, and `mfa.locked.first`, with `hold` and the refused factor's `binding`, for the refusal that begins an episode (the first since an attempt was let through) — the one a deployment notifies the account holder of; `mfa.recovery_code.used`, with `remaining`, beside `mfa.verified` (with `reopened: true` when the code reopened the login for a binding); `mfa.factor.enrolled`, with `binding` (`password`, `federated`, `email_proof`, or `mfa` beside another factor) and `by: "user"`, `purpose` `login` at a login and `enroll` from the account page; at a step-up, a factor's `mfa.challenge.sent`, `mfa.verified`, `mfa.verify.failure`, `mfa.locked` and `mfa.recovery_code.used` say `purpose: "step_up"`, and no other event is added — `mfa.verified` is the verification, recorded before the session is escalated, as at a login before the session is established; whether the escalation landed is in the `mfa_escalation_*` and `mfa_store_unavailable` lines; `mfa.recovery_codes.generated`, once the answer carrying its codes is sent — so a login's `mfa.factor.enrolled` with no `generated` after it means its set was written and never shown (bound by `email_proof`, the sets that stood are retired; the list says `recovery_codes_shown: false`) or not written (`mfa_recovery_codes_unwritten`) — with `binding` — `mfa` for a regeneration from the account page, which carries no `purpose` — `by: "user"` and `regenerated` — `true` when a set stood, or may have — and `unreplaced: true` when an older set is still stored beside the new one: kept and usable (`kept: "password_binding"` or `"federated_binding"`: a first binding by a sign-in alone never replaces a set), or retired and not removed, its codes verifying nothing; `mfa.first_binding_conflict`, with `kind` alone — a first binding its checks before the subject's lease let through, refused under the lease by the factor another login of the subject bound at once, which may be a password holder racing the owner: its own never written, its transaction kept, answered as any first binding the records no longer allow; `mfa.factor.removed`, with `kind`, `factorId`, `binding` and `by: "user"` alone, for a removal from the account page; `mfa.lock.recovered`, with `operation: "recover"`, the `generation` and what it `cleared` (`week`, `run`, `hard`), for a release applied; and the operator reset's `mfa.reset` — with `by: "operator"`, the `kinds` and `count` removed (once the removal succeeded), `requireEmailProof`, `sessions` and `sessionsAgain` (each revocation complete), `complete` and `requestedBy` when given, and with neither `ip` nor `userAgent`: no request is behind it. The requirement records `mfa.enrollment_state_inconsistent`, with `witness` — `purpose: "login"` at a login, and `purpose: "session"` with the admitted `action` at a first binding in a session — and so does a verification that would reopen a login for a first binding, with `purpose: "login"`. None carries an address or a code.

**Logs** never carry the transaction id, a proof, a code, an address, a secret or a factor's data: `mfa_store_unavailable` (error: `route` — `step-up`, `factors` and `recovery-codes` among them — `sid` at a session's escalation, `store` — `mfa_transaction`, `mfa_factor`, `revocation_boundary` (`step: "revokedBefore"`, a login's transaction held to its subject's sessions boundary), `user_session`, `cookie_session` or an interrupting requirement's name — `step`, the error's projection; a session's proof's read and write are `sessionEmailProofAt` and `recordSessionEmailProof`, the first-binding mark's `firstBindingAt` and `noteFirstBinding`, a session's escalation's `cookie_session` `regenerate`, `save` and `renewSession` (a renewal answered without a nonce) and `user_session` `recordSecondFactor` and `delete`), `mfa_escalation_unbound` (error: `route`, `sub` — a store that dropped the renewal nonce; the session is ended), `mfa_escalation_invalid` (error: `route`, `sub`, and the error's projection for a store's `RangeError` — what a verification adds outside the requirement's reach, or an event the store refused), `mfa_escalation_not_recorded` (info: `route`, `sub`), `mfa_factor_unreadable` (error: `route` — `factors` for a listed record whose key left the ring — `kind`, `factorId`, `state` — `unreadable`, `key_unavailable` with the `keyId` to put back, `verification`, `challenge` when a pending challenge's kept state does not open, with the `keyId` when that key is the one missing, or `enrollment` when a first binding's pending enrollment does not open or its factor threw completing it), `mfa_factor_challenge_unavailable` (error: `kind`, `factorId`), `mfa_factor_enrollment_unavailable` (error: `kind`; `route: "verify"` when a factor's `enrollable` threw while a login was being reopened for a binding, `route: "enrollment"` when it threw at an enrollment's start or completion), `mfa_factor_identity_unavailable` (warn: `kind` — a factor's `identity` threw; the record is judged a duplicate of none) — a factor's own failure, here and in `mfa_factor_unreadable`'s `verification` and `enrollment`, by its `name` and `code` alone, never its text, `mfa_mail_unavailable` (error: `route`, `purpose`, `kind`, `reason` — `outage` or `no_sender` — `cleared`, and the sender's failure by its `name`, `code` and `status` alone, never its text), `mfa_mail_refused_at_limit` (warn: `route`, `purpose`, `kind`, `cleared`), `mfa_email_proof_unprovable` (warn: `sub`, `reason` — `no_sender`, `no_address` or `unreadable_address`; the next login heals both), `mfa_login_revoked` (info: `sub`, `route` — a login's transaction past its subject's sessions boundary, answered `401`), `mfa_first_binding_distrusted` (info: `sub`, and `route` — or `action`, from a session's admission — a first binding the first-binding mark refused, answered `401`), `mfa_first_binding_upstream_not_recent` (info: `sub`, `action`, `reason` — `upstream_unknown` or `upstream_stale` — a federated session's first binding sent to log in again because its upstream, not its callback, is not recent), `mfa_subject_lock_unsettled` (warn: `sub`, `kind`, `step` — `settleSubjectAttempt` or `noteExemptSuccess` — `outcome`, the error's projection; ## The MFA page's contract

The Provider renders no page (the MFA ADR's D6 and O11): it answers JSON under `/session/mfa`, and sends a browser to the deployment's MFA page, `mfa.page.url`, when a step-up is asked. The login page's second step, the MFA page and the account page are the deployment's — one page or several — and each keeps the rules below, every one with the route or answer it relies on. What each route answers in full is [The routes](#the-routes)'s; this is what a page does with it.

**Where the page is served.** The page runs on the Provider's origin, within the session cookie's reach: script that runs there acts as the signed-in user, so a cross-site scripting hole in it is an account takeover.

- **On the Provider's origin.** The session cookie is host-only (`__Host-auth.session` by default, `session-store.name`), and every transaction is bound to the browser session that opened it, so only a page on the Provider's origin speaks for that session. Core holds `mfa.page.url` to the issuer's origin at boot (`checkStepUpPage`, [`packages/core/src/session-admission/requirement.mts`](../core/src/session-admission/requirement.mts)), and `/authorize` sends a browser to no step-up page off it.
- **Its own headers.** `Content-Security-Policy` with `frame-ancestors 'none'`, so no other site frames it over a code, a TOTP secret or recovery codes, and a strict `script-src 'self'`: no third-party script — analytics, session replay, error reporting that captures request bodies or URLs — runs beside them. `Cache-Control: no-store`, as every `/session/mfa` answer carries ([`src/routes.mts`](src/routes.mts)), so no cache keeps what it shows. `Referrer-Policy: no-referrer` (or `same-origin`): its URL carries `redirect_to`, the `/authorize` request with its `reauth_ask` id.
- **Server strings as text, never HTML.** A factor's `label` — up to 64 characters that may hold `<` and `>`, set by whoever binds the factor, a password holder included where a first binding by password is open — its `hint`, and `sent_to` are rendered as text.
- **The TOTP QR code drawn in the page.** `otpauth_uri` holds the secret: the page draws its QR code itself and never sends the URI to an image or QR service.
- **Nothing in browser storage.** A code, a secret, a transaction id or a recovery code lives in the page's memory alone, never in `localStorage` or `sessionStorage`.

**Every POST** passes the deployment's CSRF guard (`csrfGuard`, [`packages/session/src/csrf.mts`](../session/src/csrf.mts)) before anything is read, by either arm:

- **The origin arm.** A browser sends `Origin` on a POST, so a `fetch` from the page on the Provider's origin passes on it alone — the arm that usually applies. A foreign `Origin` is refused, token or not.
- **The double-submit arm**, for a request without a same-origin `Origin` or `Referer`. `GET /session/csrf` sets the token's cookie and answers `{"csrf_token","cookie_name","header_name","body_field","expires_in"}`; the page sends the cookie's current value — the cookie `cookie_name` names, readable by script — in the header `header_name` names (`x-csrf-token`) or the form field `body_field` names (`csrf_token`). An answer that sets a new token replaces the cookie, and a value that no longer matches it is refused, so the page reads the cookie again after each such answer rather than keeping a value: the login's `403`, a `200` that completes a login, `{"step_up":"verified"}`, and a session's `POST /session/mfa/enrollment/complete` `200` whose escalation renewed the session ([`src/escalation.mts`](src/escalation.mts)).
- A refusal is `403 access_denied`, nothing read. Bodies are JSON or a form. Past the limiter's budget for `mfa`, `429 {"error":"rate_limited"}`, with `Retry-After` when the limiter says when.

**The transaction.** The page keeps the id a `403` or the step-up answered in memory, and sends it in the body's `transaction_id` or the `MFA-Transaction` header — the header alone on `GET /session/mfa/transaction` — never in a URL, which no route reads. It is not a bearer: it works only in the browser session it is bound to, so the page keeps the cookie the answer set. `400 invalid_request` has several causes, which the page tells apart by `error_description`:

- `"Unknown or expired MFA transaction"` — missing, malformed, spent, expired, another browser's, or two that disagree: the user starts again — from the password at a login, from `POST /session/mfa/step-up` in a session.
- `"Unknown second factor"` — a `factor_id` that is none of the subject's that an installed factor verifies, or any factor on a transaction that verifies none (an `enroll` one, a login reopened for a binding): nothing spent; the page reads the transaction again and offers what it lists.
- The enrollment's own, below.

`401 {"error":"login_required"}` sends the user to the login page.

**Where the page goes next: `redirect_to`.**

- The page has a `redirect_to` only on its own URL: no `/session/mfa` answer carries one. `/authorize` sets it when it sends a browser to step up — the authorization request on the Provider's origin, built on the configured issuer and never on the request's host, carrying its `reauth_ask`, with `acr_values` beside it on the page's URL when the request asked an acr (`stepUpTrip`, [`packages/oauth/src/routes/authorizeAsk.mts`](../oauth/src/routes/authorizeAsk.mts)); the federation-grants connect flow sets it to its connect URL, marked as stepped up. Core reserves the name: `mfa.page.url` may not carry it.
- **The page follows `redirect_to` only when it is on the Provider's origin** — parsed as a URL, its origin the Provider's — and lands on a page of its own otherwise.
- The login page continues where the login was going: `POST /session/login` held its `redirect_to` to `session.redirectAllowlist`, by exact match, and once the second factor is answered `200 {"message":"Logged in successfully"}` the page navigates there.
- **A step-up another page is asked for.** A route called from a signed-in session — `POST /session/mfa/enrollment`, `/recovery-codes`, `/factors/rename`, `/factors/remove`, `/lock/release`, the link start, WebAuthn registration, device verification — may answer `403 {"error":"step_up_required","error_description":…,"requirement":"<name>","page":"<href>"}`. `requirement` names the requirement that asks, and `page` is that requirement's registered page (its `page.href`): `mfa` and the MFA page, or another installed requirement and its own page — so the page reads `requirement` rather than assuming the MFA page. `page` carries no return parameter, since the page that was answered knows where it returns to: it sends the browser to `page`, naming itself in `redirect_to`, and starts its action again on the way back.

**Codes.**

- **A TOTP code and an email factor's login code:** `autocomplete="one-time-code"` and `inputmode="numeric"`. A TOTP code is sent as its digits alone — 6 to 8, as the factor was enrolled with (`mfa-totp-factor.digits`) — with no space in or around it, which the factor does not read ([`src/totp/factor.mts`](src/totp/factor.mts)); an email login code is six digits, whitespace around it read ([`src/codes.mts`](src/codes.mts)).
- **A long code** — a recovery code, the account-email proof's code, an email factor's enrollment code — is 16 Crockford base32 characters, shown `XXXX-XXXX-XXXX-XXXX`, and meant to be pasted: `autocomplete="one-time-code"`, in a text input, since it holds letters. The page takes it pasted with or without hyphens or spaces, and sends it with the spaces inside it removed: the verifier reads either case, hyphens anywhere, whitespace around it, and `O`, `I`, `L` as `0`, `1`, `1` — not whitespace inside it ([`src/codes.mts`](src/codes.mts)).
- **A mailed code** — an email factor's login code at its challenge, its enrollment code at the enrollment's start, the account-email proof's at its challenge — is answered `sent_to`, the address masked (`a***@example.com`; absent when the address does not mask), and `expires_in`, the code's life in seconds — at an enrollment's start, the time left to complete it. A code sent again replaces the earlier one. The mail's refusals: `403 {"error":"mfa_factor_refused"}` at a challenge — the email factor's recorded address is not the account's, or the account has none: the page offers another factor; `429 {"error":"rate_limited","error_description":"Too many codes sent: try again later"}` — the mail sender's limit, the flood guard's code, told apart by its description and carrying no `Retry-After`; `503` — the mail could not be sent. Either of the last two clears the code; the transaction stands.
- A proof refused is `401 {"error":"mfa_invalid","error_description":"Second factor not accepted","attempts_remaining":<n>}`: the page shows the attempts left; at `0` the transaction is over, and the user starts again.

**The lock.** A guessable proof — a TOTP code, an email login code — that the subject lock holds is answered by `POST /session/mfa/verify` `429 {"error":"mfa_locked","error_description":…,"hold":"backoff"|"weekly"|"hard","usable_kinds":[…],"attempts_remaining":<n>}`, unchecked; it still spends one of the transaction's attempts ([`src/lock.mts`](src/lock.mts)).

- **The page shows the factors that still work.** `usable_kinds` names every installed kind whose factor is not guessable (`guessable: false`) that the subject holds, each once: with the bundled factors `recovery_code` and `webauthn`, and any such factor a deployment contributes. It names them and judges none (a spent set is named), so the page offers the factors of those kinds that `GET /session/mfa/transaction` lists, and their verification says whether one works.
- **`backoff` and `weekly`** carry `Retry-After`, in whole seconds: the page shows when a code may be tried again, beside the other factors.
- **`hard`** carries no `Retry-After` and no time: no wait lifts it. The page shows no time, and says: make an exempt proof — with the bundled factors, a recovery code or a passkey — rebind, then release (below).

**Releasing the lock** (`POST /session/mfa/lock/release`, [`src/lockRelease.mts`](src/lockRelease.mts)). A proof of an exempt factor — any installed kind whose factor declares `guessable: false`; with the bundled factors, a recovery code or a passkey — verified in a session, at its login or at a step-up, authorizes a release in that session for `mfa.manage.maxAgeSeconds`; a guessable one (TOTP, an email code) authorizes none ([`src/lockRecovery.mts`](src/lockRecovery.mts)). The page states the order up front, so one code is spent. Steps 1 and 3 count only from five minutes (`DEFAULT_CLOCK_SKEW_MS`) after the lock began, and the page has no instant to show before the release answers one, so it says so:

1. Change the password, and revoke the subject's sessions, which the release asks for. For a password account, the Store's password change does both: it calls `revokeAllForSubject`. For a federated account, the user secures the upstream account at its identity provider — which revokes nothing here — and signs out everywhere, through the host's sign-out-everywhere, which must itself ask the second factor (the lock's release, "Sign-out-everywhere", under [The routes](#the-routes)). The revocation counts only when it is more than five minutes after the attack's first counted failure: made more than five minutes after the first `429 mfa_locked`, it does.
2. Sign in with an exempt factor.
3. While the hard hold stands, rebind: replace every record that is not of an installed exempt kind — a TOTP or an email factor, one whose data does not open, and one of a kind no longer installed, a passkey's included where the WebAuthn factor no longer is — by enrolling the new one (`POST /session/mfa/enrollment`), then removing the old (`POST /session/mfa/factors/remove`). A factor counts only when it is created more than five minutes after the hard hold began: made more than five minutes after the first `429` that said `hard`, it does.
4. Release.

While the hard hold stands, rebind first, then release: a release before the rebind answers `held` and spends the session's authorization, so another exempt proof is made before the next release. Each answer is the page's to show:

- `200 {"lock":"released"}`: the hard hold, if one stood, is lifted. The week and the backoff are given back only where a revocation counted, so they may still stand: the page still handles a later `429 mfa_locked`.
- `200 {"lock":"held","hold":"hard","description":…,"rebind_after":"<ISO 8601>"}` — never "released": the week may be given back, but guessable factors stay held. The page tells the user to replace them after `rebind_after`, make an exempt proof again (`POST /session/mfa/step-up`), then release.
- `403 {"error":"mfa_exempt_proof_required"}`: no authorization stands in this session — make an exempt proof, then release.
- `409 {"error":"mfa_lock_release_refused","reason":"not_revoked_since"}`: no revocation counted — none since the attack began, or one too close to it. The page asks the user to change the password again (or sign out everywhere again), sign in with an exempt factor, then release. Any revocation of the subject's sessions meets it, so the release does not prove a password was changed.
- `409 {"error":"mfa_lock_release_refused","reason":"no_revocation_boundary"}`: this deployment cannot give the week back early. While the hard hold stands it carries `rebind_after`, and a rebind alone lifts the hold: rebind after it, then release — or ask for a reset.
- `409 {"error":"mfa_factors_busy"}` with `Retry-After`: try again then. `403 step_up_required`: recent MFA has lapsed — step up first. `401 login_required`: the session is gone — a revocation ends it — so the user signs in again. `503`: an outage; a retry is safe, and answers what the release came to.

**`rebind_after`** is the one instant the page shows, and it has it only from the release's `held` and `409` answers, after an exempt proof: a login's `429 mfa_locked` and the release's `403 mfa_exempt_proof_required` carry none. Wherever an answer carries it, the page shows it and says that a factor whose `created_at` (`GET /session/mfa/factors`) is not after it does not count — replace it again after that instant — and that a factor listed without `created_at` does not count either: remove it. A factor bound within five minutes of the hard hold is one of those. The page computes nothing: the server is the only source of the instant.

**Enrolling** ([`src/enrollment.mts`](src/enrollment.mts)).

- **At a login,** `403 {"error":"mfa_enrollment_required","transaction":"<id>","expires_in":<s>,"hints":{"enrollable":[…],"email_proof":<bool>}}` asks the page to bind a factor of a kind `hints.enrollable` lists. It comes from `POST /session/login`, or from `POST /session/mfa/verify` when a recovery code reopens the login for a binding — naming a new transaction, which the page switches to, and setting no new CSRF token. With `hints.email_proof` the account-email proof comes first — `POST /session/mfa/challenge` and `/verify` with `factor_id: "account-email"`, answered `200 {"email_proof":"verified"}` — and until it is given an enrollment is `403 {"error":"mfa_email_proof_required"}`. Then `POST /session/mfa/enrollment {transaction_id, kind}` and `POST /session/mfa/enrollment/complete {transaction_id, proof, label?}`. One from `/verify` that names no transaction is a binding nobody could complete: the page has nothing to bind on, and the code was not spent.
- **From the account page,** `POST /session/mfa/enrollment {kind}` opens a transaction of its own and answers it, `"transaction"` and `"expires_in"`, beside the factor's answer.
- **TOTP's answer** is `{secret, otpauth_uri, algorithm, digits, period}`: the page draws `otpauth_uri` as a QR code itself — the Provider renders no image — shows `secret` for manual entry, and offers the URI as a link for an authenticator on the same device.
- **What else the page handles:**
  - `400 invalid_request`, by `error_description`: `"Unknown second factor kind"` — a kind not on offer: the page offers what `hints.enrollable` lists; `"No enrollment is open in this MFA transaction"` — the transaction asks for a second factor, not a binding: the page reads it again; `"No enrollment is pending in this MFA transaction"` — none was begun, or it expired: the page begins again; `"Invalid label"` — 1 to 64 characters, none that breaks or reorders a line. Each spends nothing.
  - `409 {"error":"mfa_factor_duplicate"}`: the subject holds this factor already — at the start nothing was opened or sent; at the completion the attempt is spent and nothing written. The page shows the factor list.
  - `409 {"error":"mfa_factor_limit"}`: the subject holds `mfa.maxFactorsPerSubject` records; the page sends the user to remove one.
  - `409 {"error":"mfa_enrollment_conflict"}`, from the account page: the subject's factors changed while it enrolled, and the session stands — the page starts the enrollment again.
  - `401 {"error":"login_required"}` at a login: the records no longer allow the binding — another sign-in bound a factor, or a recovery or a reset ran — so the user signs in again.
  - `401 {"error":"login_required"}` with `Retry-After`, at a login or in a session: the subject's first-binding mark distrusts this sign-in — the user signs in again once that time has passed.
  - `409 {"error":"mfa_factors_busy"}` with `Retry-After`: another change holds the subject's factors, the transaction standing — complete it again then.
  - `403 step_up_required`, from the account page: the subject holds a counting factor and has no recent MFA — step up first.
  - `503`: an outage; at the completion the transaction may be spent, and the user begins again.
- **Recovery codes are shown once.** A first counting factor's completion answers `recovery_codes` (`["XXXX-XXXX-XXXX-XXXX", …]`), as `POST /session/mfa/recovery-codes` does; no route answers them again. The page shows them once, asks the user to keep them, and keeps none itself. `"recovery_codes_issued": false` in their place, or `recovery_codes_shown: false` on a set in the factor list, is a set never answered: the page points to regenerating them.
- **Regenerating recovery codes** (`POST /session/mfa/recovery-codes {}`) retires every set that stood: the page warns first that the codes the user holds stop working. `200 {"recovery_codes":[…]}`, shown once; `403 step_up_required` — step up first; `409 {"error":"mfa_enrollment_required"}` — no factor that may count stands, so codes are not issued alone: bind one first; `401 login_required` with `Retry-After`, as above; `409 {"error":"mfa_factor_limit"}`; `409 {"error":"mfa_request_stale"}` and `409 {"error":"mfa_recovery_codes_conflict"}` — nothing written: try again; `409 mfa_factors_busy` with `Retry-After`, and `409 mfa_factors_changed`; `400 … "Recovery codes are not issued here"` while the recovery-code factor is off; `503` — no codes answered, and the sets that stood may already be retired: regenerate again.

**The step-up** ([`src/stepUp.mts`](src/stepUp.mts)). The MFA page calls `POST /session/mfa/step-up` — with `{"acr_values": …}` as its URL carries them, a hint the step-up records and chooses no factor by:

- `200 {"transaction":"<id>","expires_in":<s>,"email_proof":false}`: the subject holds a factor that may count. The page lists its factors (`GET /session/mfa/transaction`), challenges and verifies one on the transaction, and on `200 {"step_up":"verified"}` — with a fresh CSRF token — follows `redirect_to`.
- `200 {…,"email_proof":true}`: a first binding owes the account-email proof. The page gives it on the transaction (`factor_id: "account-email"`), then returns to the page that asked, which starts the binding again. A proof nobody can give is refused at the challenge, `403 {"error":"mfa_email_proof_unavailable"}`: the account's address must be fixed in the Store.
- `403 {"error":"mfa_no_qualifying_factor"}`: none of the subject's factors can be used; an operator resets the account (`resetMfaForSubject`).
- `401 login_required`: no second factor can be recorded on this session; the user signs in again.
- The verification is a login's — the transaction's attempts, the lock and its `429` — and the finish's own answers are in [The routes](#the-routes) ("The step-up of a second factor").

### A worked example

As `src/__tests__/routes.verify.test.mts` and `routes.lockRelease.test.mts` drive the routes. `>` is what the page sends, `<` what it is answered. Every `/session/mfa` answer carries `Cache-Control: no-store`.

## The TOTP factor

`mfaTotpFactorModule` ([`src/totp/module.mts`](src/totp/module.mts)) contributes the factor ([`src/totp/factor.mts`](src/totp/factor.mts)), built from its section, `mfa-totp-factor`, and the deployment's issuer, which it requires from the `oauthTokenSettings` slot (the oauth module's; a composition without it provides the slot itself): it reads nothing of the whole configuration. Each factor's module is switched by its section's `enabled` (`section.isEnabled`): off, the module registers nothing, so the kind is absent from `mfaFactorResolver` and free for another module to contribute ([`factorSwitches.test.mts`](src/__tests__/factorSwitches.test.mts)). It holds no state and reads no key.

- A verification adds `otp`, and `mfa` beside it (D14). The factor counts as MFA, and its six-to-eight-digit proof is guessable, so the subject lock applies to it (D21).
- A code is accepted at the steps `T - window` to `T + window`, and only when its step is after the factor's `lastUsedStep` — the same code twice, or an older code once a newer one was accepted, is refused as `replayed` (RFC 6238 §5.2). There is no drift resynchronisation (D22). HOTP and TOTP are pinned by RFC 4226 Appendix D's and RFC 6238 Appendix B's vectors.
- Each factor keeps the algorithm, digits and period it was enrolled with, so changing them in the configuration never breaks an enrollment; the window applies to every verification.
- Enrolling hands out a secret of the algorithm's output length (20, 32 or 64 bytes) in RFC 4648 base32 without padding, and the `otpauth://totp/<issuer>:<account>?secret=…&issuer=…&algorithm=…&digits=…&period=…` URI authenticator apps read, the account being the Store's username as it is — so where the username is an address, the label shows it, to the account's owner alone, in this answer and in the owner's authenticator app; an account without a well-formed username is refused, quoting nothing. The pending enrollment keeps the secret and its parameters alone, never the URI or an address; nothing the provider keeps — a factor's data, a pending state, an audit event, a log line — carries the address. The page renders it as a QR code (D6). The proof of possession binds the factor at the step it matched.
