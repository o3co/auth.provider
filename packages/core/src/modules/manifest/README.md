# modules/manifest

Last updated: 2026-09-29

## Responsibility

The vocabulary a module is written in: `defineModule`, `ModuleSpec` / `Module`, `ComponentMap` / `ComponentKey`, `ProviderDeps` / `Provider`, `ContributesMap` with one factory type per contribution kind (and `FederationTypeContribution` / `FederationInstance`, what a federation package declares it handles, authored with `defineFederationType`), the `RouteContribution` family, `ComponentLifecycle`, `ReplicaSafetyDeclaration`, `AbsencePolicy`, `ModuleSection` (a module's own configuration section) with `SectionSchema` / `SectionDeps`, and the synthetic-key set with its resolver projections.

Which mechanism a new policy is written on — a contribution that adds behaviour, a slot that fills a port, a contribution kind that changes a core decision, or, outside this vocabulary, a capability an adapter opts into — is chosen by the four axes in [AGENTS.md](../../../../../AGENTS.md#extension-surface-four-axes).

It decides nothing at runtime. `defineModule` returns its argument unchanged; every check on a manifest — uniqueness, closure, collisions, pairing, declared absence, replica safety — is a stage-1 row in [`../../boot/`](../../boot/README.md), and so is the parse of a module's section. It owns no slot's value type either: `ComponentMap` is an empty interface that the directory owning a value augments (`../../repositories/ClientRepository.mts` for `clientRepository`, `../../boot/types.mts` for `config` / `pathResolver` / the two registrars, `synthetic-keys.mts` for the resolvers).

It is separate from `boot/` so that a module is written against the vocabulary without the planner: this directory is its own package subpath (`./modules/manifest`) and is re-exported from the package root, which is where every package that authors a manifest imports it from, and the dependency runs one way — `boot/` imports it and it imports nothing of `boot/`.

## Public contract

- [`index.mts`](./index.mts) — the `@o3co/auth-provider-core/modules/manifest` subpath (`package.json#exports`); the root barrel re-exports the same names.
- One file per concept, named for it: `defineModule` is [`define-module.mts`](./define-module.mts), the contribution kinds [`contributes-map.mts`](./contributes-map.mts), the synthetic keys [`synthetic-keys.mts`](./synthetic-keys.mts), and so on.
- Package README: [Module System](../../../README.md#module-system).

## Inputs and outputs

- A manifest is consumer-authored data. `defineModule` neither validates nor freezes it; `readonly` at the type level is the contract, and boot freezes only its own projections.
- `ProviderDeps<R, O>`: a required key is `NonNullable<ComponentMap[K]>` because boot's requires-closure check guarantees it is present before any factory runs; an optional key may be `undefined`.
- Every factory in `provides`, `contributes` and `overrides` receives the module's one typed deps object; there is no per-contribution declaration.
- A module's own configuration section ([#728](https://github.com/o3co/auth.provider/issues/728)) is the manifest's `section` ([`module-section.mts`](./module-section.mts)): `schema`, the Zod schema of the one section the module owns; `reference`, the package's `config/reference.conf` as a `file:` URL; `at`, the dot-separated path of non-empty keys the section sits at until it moves under the module's name (unset, the top-level key named exactly as the module is, not split on dots); `relocatedFrom`, the paths it moved from — a list of old paths moved whole as the section, or a map from each old path to its path inside the section (`""` for the section itself) for keys renamed as they moved. Boot parses the value at `at` with the schema, for every installed module, and hands the result to every factory as `deps.section`, typed as the schema's output: one deeply frozen object, plain data copied apart from the `config` slot, a value that is not plain data (a `URL`, a `Buffer`) as the schema made it. A module that declares no section has no `section` key, and reading it does not compile. A configuration that still sets a key at or under an old path of a loaded module refuses boot (`config-path-relocated`), naming the key's new path and the environment variable that binds it — or, for a map entry to `null`, that the key was removed; an empty object at an old path sets nothing. A relocation of a switch that decides whether a module is loaded (an adapter selection, `federations.<name>.enabled`) is declared by a module that is always loaded, since the module it would load may never be. That bridge is removed at the first major release — the relocated-paths drift test fails the cut that forgets. `reference` is a declaration boot does not act on yet: it does not layer the references.
- The section is read from the configuration after core's schema parsed it — the object the `config` slot holds — so a module moved onto `deps.section` sees what it read from `config`. Under a parent core's schema declares, core strips the keys it does not declare and coerces the ones it does, and a `configSchema` still composed with it can inject defaults: keep the module's `configSchema`, or core's mirror of the section, until the loader parses each section on its own.
- `section` is not a slot. A module that declares a section and also requires or optionally reads a component named `section` refuses boot (`reserved-component-key`), because its deps would carry both under one name; a component named `section` is otherwise an ordinary slot — provided, read by a module without a section, bootstrapped or overridden. `ProviderDeps<R, O, S>` adds it beside the slots when `S`, the schema's type, is given; `defineModule` infers `S` from `section.schema` (`never` without one), and a call that writes its type arguments names it as the third. `ModuleSpec`'s own default for `S` is the widest schema, `SectionSchema`, whose deps read `section: never`: that is the erased `Module`, so `ModuleSpec<ComponentKey, ComponentKey>` is still `Module` and a sectioned manifest is assignable to it like any other.
- `configSchema` is to be deprecated once the loader layers each package's `reference.conf`. Until then it composes with core's schema into the one parse of the whole configuration, as before.
- Name-keyed kinds (`grants`, `federations`, `tokenExchangeValidators`, `mfaFactors`, `sessionRequirements`, `rateLimitBudgets`, `federationTypes`) collide by name; list-shaped kinds (`auditHooks`, `routes`, `grantPolicyHooks`, `grantMiddleware`, `tokenBindingMechanisms`, `discoveryMetadata`) accumulate. Boot enforces the policy in its stage-1 rows `per-kind-contribute-duplicates` and `route-collisions`.
- `rateLimitBudgets` ([#728](https://github.com/o3co/auth.provider/issues/728)) is keyed by the prefix a limiter key carries before its first `:`: a module contributes the budget of each prefix it owns — the default `{ limit, windowSeconds }` it reads from its own settings, as numbers already parsed (its own coercing schema, or `requireUsableConfiguredRateLimitSpec`; an environment variable's string is refused), or `null` when those settings switch it off, which leaves keys under the prefix to the limiter's `defaultLimit`, not unlimited — and boot composes them into one view, the synthetic key `rateLimitBudgetResolver`, that a limiter reads at request time. Two modules contributing one prefix is `duplicate-contribute`; a prefix that is empty or holds `:` is `contribution-malformed` at stage 1; a host may not supply the collector (`contribution-kind-guarded`). A budget's `limit` and `windowSeconds` are read once, and the copy that was validated is what registers. No limiter reads the view yet; the bundled ones still seed their limits with `resolveSeededLimitSpecs`.
- `federationTypes` ([#728](https://github.com/o3co/auth.provider/issues/728)) is keyed by the `type` an entry of the `federations` configuration names: a federation package declares the schema of such an entry and the factory that builds a provider from one entry and its name (`FederationTypeContribution<Deps, E>`, the factory given `FederationInstance<E>`). Author one with `defineFederationType<Deps>()({ entrySchema, factory })`, which infers `E` from the schema and types the factory's entry with it; written inline without it, `E` is `unknown` and nothing ties an annotated entry to the schema. Boot reads a declaration's schema and factory once, at stage 1, and registers those. The map's owner strips its own keys (`enabled`, `type`, `trustUpstreamAmr`) before it parses an entry, so a strict schema names only the type's keys. Two packages claiming one type is `duplicate-contribute`; a declaration that is not an object with a Zod `entrySchema` and a `factory` is `contribution-malformed` at stage 1; a host may not supply the collector. The container of either kind must be a record — an array, a function or `null` in its place is `contribution-malformed`. Not dispatched yet: no entry is parsed and no factory runs until the federations section moves under core. A `federations` entry stays the bare factory, name-keyed by the federation's name.
- Every contribution value type is the contract it will be read as, so registration and use share one type. That includes `FederationProvider` ([`../../federations/types.mts`](../../federations/types.mts)) and `ExchangeTokenValidator` ([`../../token-exchange/validator.mts`](../../token-exchange/validator.mts)), whose contracts are in core because boot collects them and core imports no sibling package: the type a contribution is registered with is the type its consumer reads. A factory may answer with the value or a promise of it (`Contributed<T>`) — `applyContributions` awaits it.
- `AbsencePolicy` is data — a config path, the one value that counts as the declaration, and an operator-facing hint. Boot's `declared-absence` row compares it with `===`.

## Dependencies

- Depends on, all type-only: `audit/`, `mfa/`, `policy/`, `grants/`, `federations/`, `token-exchange/` and `session-admission/` (the contribution value types, and the branded resolver type), `discovery/` (the `discoveryMetadata` value type), `middleware/` (the `tokenBindingMechanisms` value type), `ratelimit/` (the `rateLimitBudgets` value type, `RateLimitSpec`), `express`, `zod`. Nothing from `boot/` and no implementation.
- Depended on by `boot/`, by every bundled `…Module` in core (directly or through `../index.mts`), by `discovery/`, `device-authorization/` and `grants/` for types, and by every downstream package that authors a manifest.
- Direction: `boot` → `manifest`, never the reverse. This directory must not import `boot/`, an adapter package, or `testing/`.

## Failure and lifecycle

Nothing here fails at runtime. A manifest violation is a `BootError` from stage 1 — a sectioned module reading a `section` slot (`reserved-component-key`), a malformed `at` (`module-section-path-invalid`), and a malformed `rateLimitBudgets` prefix or `federationTypes` declaration (`contribution-malformed`) among them — and so is a section its schema refuses, or cannot answer for synchronously (`config-validation-failed`, naming the operator's path); a `ComponentLifecycle.cleanup` runs at `AppHandle.dispose()` in reverse-topological order with errors aggregated (boot README). A `grantMiddleware`, `tokenBindingMechanisms`, `mfaFactors` or `rateLimitBudgets` factory that returns `null` means "disabled by config": the first two are skipped at composition, an `mfaFactors` kind is claimed and absent from `mfaFactorResolver` ([`../../mfa/__tests__/factorResolver.test.mts`](../../mfa/__tests__/factorResolver.test.mts)), and a `rateLimitBudgets` prefix is claimed and absent from `rateLimitBudgetResolver` — [`../../boot/__tests__/grant-middleware.integration.test.mts`](../../boot/__tests__/grant-middleware.integration.test.mts), [`../../boot/__tests__/token-binding-mechanisms.integration.test.mts`](../../boot/__tests__/token-binding-mechanisms.integration.test.mts).
