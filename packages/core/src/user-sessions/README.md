# user-sessions

Last updated: 2026-10-05

## Responsibility

The provider-side record of an authenticated user, keyed two ways. Sid-keyed: `UserSessionStore` (the session aggregate), `SessionRPRegistry` (relying parties for logout fan-out), `SessionFamilyIndex` (refresh-token families to revoke), `SessionFederationIndex` (upstream IdPs linked to the session). Subject-keyed: `SubjectSessionIndex` (which sessions a subject holds) and `SubjectRevocation` — the not-before boundary for issued tokens, which carries a second, independent boundary for federation grants (`SupportsSessionsOnlyRevocation`). With them: the in-process adapters, `memorySessionStoresModule`, the `AdapterFactory` aliases, the retention arithmetic, subject-wide revocation — `revokeAllForSubject`, `cascadeSubjectSessions`, `createSubjectRevocationService` — and the one reading of how a session was established and what this provider vouches for in it (`sessionAuthentication`, `vouchedAmr`, and `requirementSession`, the requirement rule's input; the MFA ADR's D9), with what each login path records, whether a federation's upstream IdP's `amr` counts (D13), and what a verified second factor makes of a session — the step-up capability's computation, which both bundled stores write. The session lifecycle — one record per sid that fences joining a session against closing it (`SessionLifecycleStore`, `active` → `closing` → `closed`) — is in [`lifecycle/`](./lifecycle/), described here; its one writer, the service, is [`../session-lifecycle/`](../README.md) (`SessionLifecycle`, its module and the relying-party notifier contract), which nothing installs yet; session admission reads a record's state to refuse a session closing. A session also records what its login's `User` said for a first binding (`enrollmentFacts`: the MFA enrollment witness and what its address is — none, one the provider reads, or one it cannot (`mailAddress`: `none`, `address`, `unreadable`), the MFA ADR's D12 and D24), and this directory holds the rule for what a store may record of it.

State ownership: these stores hold the session state; the browser cookie session is `packages/session`'s; the ordered per-session teardown (`cascadeLogout`) is `packages/oauth`'s and is injected as `CascadeSession`, because core cannot import it; the lifecycle service in `../session-lifecycle/` runs the same teardown itself, through core's ports. The Redis adapters are `packages/redis`. The two-boundary design (D13) is recorded in the ADR [2026-09-17-federation-grants-offline-delegation.md](../../docs/adr/2026-09-17-federation-grants-offline-delegation.md); this README does not restate it.

It is separate because these stores are read by `oauth` (logout, userinfo, the refresh grant), `session`, `redis` and `federation-grants`. The sid-keyed stores end with the session; the subject-keyed revocation boundary deliberately outlives it — for as long as the longest grant, refresh token, access token or session it covers ([`retention.mts`](./retention.mts)) — because a store that expired the boundary with the session would let revoked tokens and grants come back. Subject-wide revocation lives here too, because the subject boundary is the one it stamps; it reaches into [`../federation-grants/`](../federation-grants/README.md) for the grant lifetime ceiling and to end a subject's grants, so the two directories depend on each other at run time — recorded in [the directory map](../README.md#where-a-boundary-is-a-judgement-call).

## Public contract

- [`types.mts`](./types.mts) — the six store interfaces, `UserSession` / `UserSessionClaims` / `RegisteredRP` / `SessionAuthentication` / `SessionEnrollmentFacts`, the step-up capability `SupportsSecondFactorUpdate` with `SecondFactorEvent` and its guard `supportsSecondFactorUpdate`, the session-end capability `SupportsSessionEnd` of `SessionFamilyIndex` and its guard `supportsSessionEnd`, `SUBJECT_REVOCATION_ABSENCE_POLICY`, `supportsSessionsOnlyRevocation`, the factory aliases, and the six optional `ComponentMap` slots.
- The in-process adapters are [`memory/`](./memory/), one per store over two private primitives (a sid-keyed hash and a sorted set); `memorySessionStoresModule` is [`modules/memory.mts`](./modules/memory.mts) and the factory aliases are [`factory.mts`](./factory.mts). `memory/` and `modules/` are described here rather than given a README of their own.
- Subject-wide revocation is `revokeAllForSubject`, `cascadeSubjectSessions` and `createSubjectRevocationService`, each in the file of its name; the retention horizon is [`retention.mts`](./retention.mts).
- How a session was established (`UserSession.authentication`, a `SessionAuthentication`) and what it vouches for are read by `sessionAuthentication` and `vouchedAmr` in [`authentication.mts`](./authentication.mts), and by nothing else (an `authentication` in a shape the types do not admit reads as one that cannot be told: no primary, nothing vouched for; a stored `amr` in such a shape vouches for nothing, and a pre-upgrade one names no primary unless it is an array that holds `fed`): every consumer that asks how a user authenticated asks them, and builds the requirement rule's input with `requirementSession`, never from the record's own `amr` or `authentication` — `designVocabulary.drift.test.mts` fails a read of either field — by shape, whatever the receiver is called — anywhere but those readers, the rule and the two bundled stores, beyond the counted reads it lists that are not a session's. The same file holds what each login path records (`passwordSessionAuthentication`, `federatedSessionAuthentication`), the reading of `core.federations.<name>.trustUpstreamAmr` (`federationTrustsUpstreamAmr`) that the federation callback and `oauth`'s `acr` drop share, `sessionAfterSecondFactor` / `checkSecondFactorEvent`, which `recordSecondFactor` writes, with `canRecordSecondFactor`, whether it records anything on a session, and `recordableSessionAuthentication`, whose answer `create` records.
- What a session's `enrollmentFacts` may hold is read by `readEnrollmentFacts` and `recordableEnrollmentFacts` in [`enrollmentFacts.mts`](./enrollmentFacts.mts): both bundled stores record the latter's answer, and admission hands a requirement the former's. The facts are derived from the login's `User` by `session-admission/`'s primary builders, never here.
- The session lifecycle is [`lifecycle/`](./lifecycle/), described here rather than by a README of its own: the port `SessionLifecycleStore`, its record and vocabulary, the `sessionLifecycleStore` slot, the one reading of every answer a store gives and of a caller's input, and the in-process store. The service that calls it lives in `../session-lifecycle/`. Its contract lives in [`lifecycle/types.mts`](./lifecycle/types.mts); its design is the ADR [2026-10-05-session-lifecycle.md](../../docs/adr/2026-10-05-session-lifecycle.md).
- Package README: [Session stores and federation tokens](../../README.md#session-stores-and-federation-tokens).

## Inputs and outputs

- A `UserSession` is immutable after `create`, except for what a second factor verified in it adds: the store is `create` / `get` / `delete`, and a store with the step-up capability adds `recordSecondFactor`, which changes `amr` and `authentication` and nothing else — never `authTime`, never the session's lifetime. `delete(sid)` is the invalidation primitive; the orchestrator calls it last, so a failed sibling cleanup leaves the session retryable.
- Every index write takes the session's `expiresAt`, and the adapter syncs storage TTL to it. Expiry is a `Date` on the store interfaces and epoch-ms in the private primitives; the conversion is explicit at the boundary.
- `listFederations` returns insertion order — load-bearing for the post-logout redirect.
- A family index with `SupportsSessionEnd` keeps a session's "ended" mark until the session's `expiresAt` plus the clock-skew allowance (`DEFAULT_CLOCK_SKEW_MS`), writes it even when the end comes after `expiresAt`, and `removeBySid` leaves it. For an `endSession` and an `addFamilyIdUnlessEnded` on one sid, the end lists the family or the add answers `"ended"`; a refused add's family may stay unlisted until `expiresAt`, and its caller issues nothing for it. That holds while the store keeps its reads and writes linearizable and serves reads from the primary, for operations inside the session's life on every clock involved; an add that finds `expiresAt` passed answers `"ended"`. The memory index runs each call with no `await`, so what it writes and what it reads are one step.
- A `registerRP` that has resolved is in every `listRPs` on that sid that starts after it: a logout lists the RPs after it ends the session, and a code exchange registers its RP before it joins the session. A registry that reads from a replica, is eventually consistent, or can lose a write it acknowledged can miss an RP's logout.
- A session says how it was established in `authentication`, and its `amr` holds only what this provider vouches for: the federation callback records an untrusted IdP's values in `authentication.upstreamAmr`, a trusted one's (`core.federations.<name>.trustUpstreamAmr = true`) beside `fed`. A session written before the key existed (`authentication: undefined`) is split as it is read: `fed` makes the primary a federation and every other value an untrusted upstream one, so it vouches for `fed` alone — whatever that federation's switch says now, since the session does not name it; else `pwd` makes it a password login, whose values are all this provider's; else its primary is unknown (`undefined`), and such a session logs in again: under `mfa.mode = "required"` the requirement rule re-authenticates it; under `optional` a request's `acr_values` can still name a step-up target for it, and the MFA ADR's step-5 amendment obliges `/authorize` (build-order step 13), when it would ask a step-up of such a session, to send it to the login page instead. No such session has a second factor on record. It is never read as more trusted than it was written.
- `create` refuses, with a `RangeError` and nothing recorded, an `authentication` that `SessionAuthentication` does not admit — not an object, a `primary` that is not a non-empty string, a `federation` or `upstreamAmr` of the wrong type — and an `mfaAt` that is not a `Date` at or after the epoch, or is further ahead of the store's clock than the clock skew tolerated between hosts (`DEFAULT_CLOCK_SKEW_MS`, `jwt/`): both bundled stores record what core's `recordableSessionAuthentication` answers — a copy, its `mfaAt` no later than the store's clock — never their own input. `authTime` is held to the same rule: `create` refuses one that is not a `Date` at or after the epoch or is further ahead of the store's clock than `DEFAULT_CLOCK_SKEW_MS`, and both bundled stores record what `recordableAuthTime` answers, no later than the store's clock.
- `enrollmentFacts` is one of the session's two optional keys: a witness `MfaEnrollmentWitness` admits and an address fact `MailAddressFact` admits (`none`, `address`, `unreadable`), never the address. `create` refuses anything else with a `RangeError`, nothing recorded, and records a copy of those two fields alone; a session created without them reads back with the key left out, and so does one a store written before the key holds. A session without them recorded nothing, and a reader decides what that means: the MFA ADR's D12 has the `mfa` requirement send it to log in before a first binding. `recordSecondFactor` keeps them as they were.
- `recordSecondFactor` keeps what the session vouches for and adds to it: `amr` becomes what the session vouches for followed by the factor's values, each once; `mfaAt` the later of the two, each no later than the recording store's clock — monotonic on that clock, so nothing recorded is still to come, and a step-up repairs an `mfaAt` a replica whose clock ran ahead wrote. A pre-upgrade session is split first, so a pre-upgrade `["hwk", "fed"]` plus TOTP becomes `["fed", "otp", "mfa"]` with `upstreamAmr` `["hwk"]`. It answers `null`, and writes nothing, for a session that is gone, and whenever `canRecordSecondFactor` is false: its primary cannot be told, or its `authentication` or `amr` is not in a shape the types admit. Session admission asks `canRecordSecondFactor`, beside the store's capability, once per admission and hands the answer on in its view (`SessionView.secondFactorRecordable`): where it picks the second-factor authority to step a session up for `acr_values` it answers a new login (`reauthenticate`) instead, and a requirement is handed the same answer to decide its own step-up on. An event with no values, an empty one, `pwd` or `fed`, only `mfa`, or a time that is not a date at or after the epoch or is further ahead of the store's clock than `DEFAULT_CLOCK_SKEW_MS` is a `RangeError` before anything is read — the caller's fault, never the store's outage, which is any other rejection. An event's `renewalNonce` (`renewalNonce.mts`: 128 bits, base64url, one spelling) is recorded as `UserSession.renewalNonce` in the same write, replacing an earlier one; an event without one leaves it, and one that is not a nonce is a `RangeError`. A store reads the two nonces once, through `readRenewalNonces`, and compares and records what it answered. The event is recorded only while the session's nonce is its `expectedRenewalNonce` — absent matching absent, `expectsRenewalNonce` — judged in the same atomic step as the write; otherwise `null` and nothing written, so of two completions started from one cookie session only the first is recorded. It is the session's other optional key: admission refuses every cookie session but the one holding it (the MFA ADR's D27), so a store with the capability round-trips it, as both bundled stores do. The memory store writes the fields with no `await` between read and write; the Redis store's compare-and-set is `@o3co/auth-provider-redis`'s.
- The watermark is compared inclusively against a token's `iat`. `revokeBefore` advances both boundaries; `revokeSessionsBefore` only the sessions one; neither ever moves a boundary backwards. Neither records a `before` later than the store's clock plus `DEFAULT_CLOCK_SKEW_MS`: it is clamped to that, read in the same atomic step as the write, and said at warn (`subject_revocation_boundary_clamped`) where the store has a logger, never refused — a refusal would leave every token already issued alive. One behind the store's clock is recorded as given. Every adapter reads its arguments as `checkSubjectRevocationInstant` does (a `Date` with a finite time, else a `RangeError`) and bounds by the rule `clampSubjectRevocationBoundary` states: a store whose clock is read in-process calls it, and one whose clock is a server's clamps in its own atomic step there, and may use it to tell `clamped` from the `now` the server answers. A clamped boundary comes from a replica outside the tolerance, and what it minted past the clamp is not covered; the warn line is the signal. The `expiresAt` of a stamp is the caller's, sized by `resolveSubjectRevocationHorizonMs` from the token lifetimes of the `oauthTokenSettings` a caller holds, or the configuration's when it holds none, and from the session lifetime of the `sessionCookiePolicy` it must hold — each held to its key's rule, a `RangeError` naming the member otherwise, and a missing `sessionCookiePolicy` a `RangeError` naming the slot; the memory adapter raises it to `SUBJECT_REVOCATION_MIN_RETENTION_MS` whenever the grants boundary advances.
- A lifecycle record's state only moves forward. A join lands only while the record is active and the session's `expiresAt` is after the store's clock, and never once a close has committed: the state check and the write are one atomic step, and the closing commit keeps the participants as its snapshot. A repeated close answers the saved close at the current generation, writing nothing. A completion applies only at the generation read, checked before the item. The whole record lapses at one retention: `expiresAt` plus `DEFAULT_CLOCK_SKEW_MS`, and from the closing commit the later of that and the commit plus the request's `retainMs`. The memory store runs each member with no `await`, and when full refuses rather than evicts.
- `revokeAllForSubject` and the service report backend outcomes rather than throw them: `unavailable` is a composition gap, `failures` are backend outages, and `complete` is the one field a caller checks. What they refuse, they refuse before the first write: a `RangeError` for an invalid `revokeGrantsConsentedSince`, and at construction a `RangeError` for a non-positive watermark TTL and a `TypeError` for allowing keep on an adapter that cannot stamp the sessions-only boundary. A caller may ask for its federation grants to be kept (`SubjectRevocationRequest.federationGrants: "keep"`); whether that is honoured is operator policy (`federation-grants.allowKeepOnSubjectRevocation`, default `false`), a refused keep is carried out as a full revocation, and the report says both what was asked and what happened.

## Dependencies

- Depends on: `single-use/` (`usableMaxEntries`, the lifecycle memory store's caps),  `federation-grants/` (revocation, the grant lifetime and the store types — for subject-wide revocation and retention), `config/` and `jwt/` (the configuration's lifetimes the retention horizon falls back to, the clock skew, and the skew tolerated in a verification time, `DEFAULT_CLOCK_SKEW_MS`), `token-settings/` and `browser-session/` (`OAuthTokenSettings` and `SessionCookiePolicy`, type-only: the lifetimes the retention horizon reads from the slots a caller holds), `errors/` (`describeValue`, how a refused lifetime is named), `grants/` (the `amr` values `pwd`, `fed` and `mfa`, for reading and recording a session's primary and a factor's event), `session-admission/` (`RequirementSession`, the input a session requirement is asked about, type-only), `repositories/` (`MfaEnrollmentWitness`, type-only: the witness values the enrollment facts hold), `modules/manifest/` (the module), `adapters/`, `logging/` (the logger type, and `loggableError` for the revocation helpers' failure lines).
- Depended on by: `session-admission/` (the D9 readers and what each login path records, and the session types), `grants/` (`UserSessionClaims`, type-only), `jwt/` (type-only), `boot/` (replica safety), `federation-grants/` (the capability guard in `types.mts`), the root barrel; downstream `packages/oauth` (logout cascade, userinfo, the wired revocation service), `session`, `redis`, `federation-grants`, and `mfa` (the step-up capability's guard).
- `federation-grants/` reaches this directory only through `types.mts`, and no import cycle crosses the two directories. Must never import `boot/`, `middleware/`, `routes/`, `packages/oauth` (the cascade is injected), or `testing/`.

## Failure and lifecycle

- Store methods reject on a backend failure; the revocation helpers convert every such rejection into a reported failure and never throw (`cascadeSubjectSessions` in particular), because their callers have already written something they cannot undo.
- The memory adapters GC lazily on read and write, hold no timers and need no disposal. They are single-replica: the module is refused under `core.deployment.mode = "multi"`.
- No cancellation or deadlines; a subject cascade is sequential by design.
