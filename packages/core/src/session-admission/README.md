# session-admission

Last updated: 2026-09-29

## Responsibility

The one decision that an authenticated browser session — or the primary authentication about to become one — may proceed with an action ([the session-admission ADR](../../docs/adr/2026-09-28-session-admission.md)). Every consumer of a session (`/authorize`, consent, the session-bound grants, the refresh grant, device verification, the federation-grants browser half, the link flow, WebAuthn registration) asks it with its own slots and a claim this directory built. The password login asks it before anything is written, a requirement that interrupted a login asks it again when its ceremony completes, and the federation callback is given its establishment without asking. An extension that changes what "logged in" means — MFA first — is a session requirement, contributed under the `sessionRequirements` kind. It reaches every consumer through the synthetic key `sessionRequirementResolver`, never through a consumer's manifest.

It owns the decision and its vocabulary: the reading of each carrier a session is claimed by, the actions and their grades, the steps and the merge of their verdicts, the requirement contract and what registration holds a requirement to, the establishment half (the primary, the continuation a requirement persists, the interruption's validated answer, the capability to establish), and the provider's `acr` vocabulary.

It does not own a protocol: what a consumer answers for an outcome — a redirect, an RFC 6749 error, a `403` — is the consumer's. How a requirement decides is the requirement's; the MFA requirement is `packages/mfa`'s. Writing a session is `packages/session`'s. Reading the subject-revocation boundary against an instant is `federation-grants/`'s helper, which this directory calls. The registration pass that runs its rules at boot is `boot/`'s.

It is a directory of its own so that the consumers cannot disagree on what a live session is, and so that a second extension touches this port's contributors and nothing else.

## Public contract

- The entry point is [`admit.mts`](./admit.mts): the decision for a session and for a login, and the builders of the claims it reads.
- The contract is [`requirement.mts`](./requirement.mts): what a consumer passes and is answered, what a requirement is, is asked and answers, the bundled actions, and the rules a requirement is registered under.
- The tail of a login as a contract is [`login-completion.mts`](./login-completion.mts): the `loginCompletion` slot (#728) a requirement's completion finishes a login through — the session package's `establishSession` and `answerInterruption`, with the stores, the session's lifetime and the CSRF mechanism left to the provider. Its contract suite and recording double are on the testing entry, beside the other slots' (`../testing/slots/`).
- The testing entry, [`testing/`](./testing/), is published on `@o3co/auth-provider-core/testing`: the resolver a consumer built by hand takes in a test, the contract suite every requirement runs, and the MFA table's merge rows.
- What the package exports from here is listed, with where each name is defined, in the package README's [Session admission](../../README.md#session-admission).

## Dependencies

- Imports values from `user-sessions/` (how a session was established, what it vouches for, and what each login path records), `federation-grants/` (the subject-revocation boundary reading, kept there because moving it here would close a value cycle through `user-sessions/`), `grants/` (the `amr` values and their composition), `jwt/` (the revocation skew), `audit/`, `errors/` (the RFC 6749 error-code grammar) and `logging/`. The testing entry takes `mfa.mode`'s type from `mfa/`, type-only.
- Imported by `boot/` (the resolver's builder, the registration and the reach seal), `mfa/` (the continuation check an MFA transaction is held to), `user-sessions/` and `modules/manifest/` (types only), the root barrel and the testing entry. A consumer package reaches it through the package entry alone.
- Never imports `boot/`, and nothing outside core but Express's request and response types, which the login completion's call carries.

## Invariants

- **One decision point.** No shipped source outside this directory reads a session record (`get(` on a `UserSessionStore`), reads the subject-revocation boundary (`revokedBefore(`), selects an `acr`, or builds a claim literal. The exceptions are the token side's reads the ADR's D9 leaves where they are and `verifyJwt`, each pinned to its file and count with a reason — [`../__tests__/sessionAdmissionCallers.drift.test.mts`](../__tests__/sessionAdmissionCallers.drift.test.mts).
- **Claims are built here alone.** A claim comes from this directory's builders — one reading of each carrier: the cookie, a code record's first read and its revalidation, a link transaction, a verified token. A claim, a resolver, a primary, an establishment and an interruption are branded at the type level and checked at runtime through module-private sets. An object shaped like one, or a copy of one, is refused with a `RangeError` before anything is read, as is a bundled action passed as anything but its `ADMISSION_ACTIONS` entry itself — [`__tests__/admit.test.mts`](./__tests__/admit.test.mts), [`__tests__/primary.test.mts`](./__tests__/primary.test.mts).
- **Every step fails closed.** A store or a requirement that throws, or a requirement that answers something that is not a verdict, is `unavailable` and never a verdict. It names the store admission reads itself (`user_session`, `revocation_boundary`) or the requirement, and is logged once at error as `session_admission_unavailable` with `store`, `action` and `loggableError`'s projection — never the `sid`. A cookie claim without a subject is `not_live` (`no_subject`) before any store is read. A record that is gone, has no `sub`, has an `authTime` or `expiresAt` that is not a valid date, or is past its `expiresAt` is `not_live` (`gone`). A claim's subject that is not the record's is `not_live`, logged at warn and audited as `session.admission.subject_mismatch`. The subject-revocation boundary is read against a live record, and never for a token carrier, whose boundary `verifyJwt` reads — [`__tests__/admit.test.mts`](./__tests__/admit.test.mts).
- **A requirement is never asked about a dead session**, and only for an action graded `use` or `credential_change`: in registration order, with a view of the record, the subject (the record's when one was read, else the claim's) and the D9 reading — for a token carrier, the token's own `amr`. The first verdict that is not `met` wins. A `step_up` carries that requirement's registered page, and is `unmet` from a requirement that registered none and `reauthenticate` over no live session. A `remediation` action that is not one core issued to a requirement registered with the resolver is treated as `credential_change`, the strictest grade, and said once per name — [`__tests__/admit.test.mts`](./__tests__/admit.test.mts).
- **The `acr` is selected here alone**, over what the session vouches for (the D9 reading), never over the record's own `amr` — [`../__tests__/designVocabulary.drift.test.mts`](../__tests__/designVocabulary.drift.test.mts), [`../__tests__/sessionAdmissionCallers.drift.test.mts`](../__tests__/sessionAdmissionCallers.drift.test.mts).
- **A requirement's name** is RFC 6749's error-code characters — printable ASCII without `"` or `\`, at least one — the only ones a `step_up` is sent in on the wire. It is never one of the names admission gives its own stores' outages (`user_session`, `revocation_boundary`), so the store an `unavailable` admission names tells a store's outage from a requirement's. Registration refuses both at boot — [`__tests__/requirement.test.mts`](./__tests__/requirement.test.mts), [`../boot/__tests__/session-requirements.test.mts`](../boot/__tests__/session-requirements.test.mts).
- **Core describes every admission outage.** `describeAdmissionOutage(store)` is the one text a client is given: each of admission's own stores by name, anything else as a requirement's outage, never by the requirement's name. Every bundled consumer answers an `unavailable` admission with it, so none reports a requirement's outage as the session store's — [`__tests__/requirement.test.mts`](./__tests__/requirement.test.mts).
- **A requirement is registered as a copy**, each field read once. Its remediations are its own routes, `<name>.<route>`, each once, and never a name in `ADMISSION_ACTIONS`. Core issues one branded remediation action per route to the contributing module alone, by the object its factory returned; the copy the resolver answers carries none. Its hint keys follow core's grammar, none of them a name core reserves — [`__tests__/requirement.test.mts`](./__tests__/requirement.test.mts), [`../boot/__tests__/session-requirements.test.mts`](../boot/__tests__/session-requirements.test.mts).
- **The step-up page is resolved once, at registration, on the issuer** it is validated against — at boot, `oauth.jwt.issuer`. A path must stay on the issuer's origin once a browser resolves it (`//host`, `/\host`, an encoded backslash and a control character are refused); an absolute URL must be on the issuer's origin; `params` are strings and never `redirect_to`, the consumer's return parameter. A path page with nothing to resolve it on is refused. The registered page carries its `href` — one absolute URL, the params on the query, no return parameter — and a `step_up` admission carries that page: every consumer answers or navigates from `href` and none resolves the page itself — [`__tests__/requirement.test.mts`](./__tests__/requirement.test.mts).
- **The reach is sealed once, and one requirement reaches.** A requirement's `reach` is not read at registration, since it may fill as the same pass registers the factors. It is read once, at the end of boot's stage 4, held to the reach rules and sealed on the copy as a frozen snapshot. The resolver, the `acr` drop and admission read that snapshot, and a contributor's mutable `Set` changes nothing after boot. The rules: no primary's marker; a second-factor value under the name `mfa` alone; a page for a reach that is not empty (a page may stand with an empty reach); and, in this release, an empty reach under any name but `mfa`, since only the MFA requirement adds vouched values to a session. The rules have one home, which boot, `resolverForTests` and the contract suite all run; only `resolverForTests`'s `allowAnyReach`, for tests of admission's own mechanics, lifts them — [`__tests__/requirement.test.mts`](./__tests__/requirement.test.mts), [`../boot/__tests__/session-requirements.test.mts`](../boot/__tests__/session-requirements.test.mts).
- **A login is established from what core built.** A password login's primary is built by `passwordPrimary` alone and records `pwd`. A completion adds a second-factor value or an `mfaAt` under the name `mfa` alone, and under that name it must be a verified second factor, whether presented to `resumePrimary` or read back from a continuation — so a completion that verified nothing never establishes a password-only session. A persisted continuation is read back through its check. `resumePrimary` asks, in order, every requirement with `admitPrimary` not already done in that login. An interruption is opened with the session id and the continuation core built, and its answer is held to the closed body and core's hint grammar before the route sees it — [`__tests__/primary.test.mts`](./__tests__/primary.test.mts), [`__tests__/primary.check.test.mts`](./__tests__/primary.check.test.mts).
- **The resumption's callers are guarded.** Outside this directory, a call of `resumePrimary(` or `continuationOf(` is kept to `packages/mfa/src`: in this repository only the MFA package completes an interruption. A second in-tree requirement that interrupts a login widens the guard in the pull request that adds it; `tools/composition`'s fixture requirements are not scanned. Beside them, `establishWithoutAsking(` is kept to the federation callback and `recordSecondFactor(` to the two bundled session stores and `packages/mfa` — [`../__tests__/sessionAdmissionCallers.drift.test.mts`](../__tests__/sessionAdmissionCallers.drift.test.mts).
- **The merge rows are MFA's table, in one list.** The merge is the MFA ADR's step-4 table under the ADR's D2 mapping, with no row lost. Its rows are one list on the testing entry. Core's merge test runs them against a stand-in written to the MFA requirement's table, and the MFA package runs them against the requirement it registers — its `mfa.mode = "off"` rows against admission with no requirement registered, which is what an MFA-off composition is. They are the MFA requirement's rows: another requirement is held to the contract suite, not to them — [`__tests__/admit.merge.test.mts`](./__tests__/admit.merge.test.mts), and `packages/mfa`'s `requirement.merge.test.mts`.
- **A login's tail is reached through a slot, never an import.** A requirement's completion finishes a login through `loginCompletion`, which the session module is to provide: each of its two calls refuses what core did not build before the session is touched, every outage leaves the browser not signed in, and an interruption's `403` carries a fresh CSRF token. The suite a provider runs holds it to that — [`__tests__/loginCompletion.test.mts`](./__tests__/loginCompletion.test.mts).
- **The contract suite fails each way a requirement can break the contract** — [`__tests__/contract.test.mts`](./__tests__/contract.test.mts).
