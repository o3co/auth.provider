# session-admission

Last updated: 2026-10-05

## Responsibility

The one decision that an authenticated browser session — or the primary authentication about to become one — may proceed with an action ([the session-admission ADR](../../docs/adr/2026-09-28-session-admission.md)). Every consumer of a session (`/authorize`, consent, the session-bound grants, the refresh grant, device verification, the federation-grants browser half, the link flow, WebAuthn registration) asks it with its own slots and a claim this directory built. The password login asks it before anything is written, a requirement that interrupted a login asks it again when its ceremony completes, and the federation callback is given its establishment without asking. An extension that changes what "logged in" means — MFA first — is a session requirement, contributed under the `sessionRequirements` kind. It reaches every consumer through the synthetic key `sessionRequirementResolver`, never through a consumer's manifest.

It owns the decision and its vocabulary: the reading of each carrier a session is claimed by, the grades and what an action a consumer registers may be named and graded, the steps and the merge of their verdicts, the requirement contract and what registration holds a requirement to, the establishment half (the primary, the continuation a requirement persists, the interruption's validated answer, the capability to establish), and the provider's `acr` vocabulary.

It does not own a protocol: what a consumer answers for an outcome — a redirect, an RFC 6749 error, a `403` — is the consumer's. How a requirement decides is the requirement's; the MFA requirement is `packages/mfa`'s. Writing a session is `packages/session`'s; the contract a requirement's completion finishes a login through, and a step-up renews a signed-in session's id through, the `loginCompletion` slot, is declared here, beside the establishment it consumes, and the session package's login-completion module provides it. Reading the subject-revocation boundary against an instant is `federation-grants/`'s helper, which this directory calls. The registration pass that runs its rules at boot is `boot/`'s.

It is a directory of its own so that the consumers cannot disagree on what a live session is, and so that a second extension touches this port's contributors and nothing else.

## Public contract

- The entry point is [`admit.mts`](./admit.mts): the decision for a session and for a login, and the builders of the claims it reads.
- The contract is [`requirement.mts`](./requirement.mts): what a consumer passes and is answered, what a requirement is, is asked and answers, and the rules a requirement is registered under.
- The actions are [`actions.mts`](./actions.mts): the grades, a closed list core owns, and what a consumer registers for each action it admits under `contributes.admissionActions`.
- The testing entry, [`testing/`](./testing/), is published on `@o3co/auth-provider-core/testing`: the resolver a consumer built by hand takes in a test, the contract suite every requirement runs, and the second-factor authority's merge rows.
- What the package exports from here is listed, with where each name is defined, in the package README's [Session admission](../../README.md#session-admission).

## Dependencies

- Imports values from `user-sessions/` (how a session was established, what it vouches for, what each login path records, and what a session's enrollment facts may hold), `repositories/` (`readMfaEnrollmentWitness`, the one reading of the witness; `readPlainFields`, the by-name plain-data copy a login's declared claims go through) and `mail/` (`normaliseMailAddress`, the one spelling of an address), which the primary builders derive a session's enrollment facts with, `federation-grants/` (the subject-revocation boundary reading, kept there because moving it here would close a value cycle through `user-sessions/`), `grants/` (the `amr` values and their composition), `jwt/` (the revocation skew), `audit/`, `errors/` (the RFC 6749 error-code grammar) and `logging/`. The testing entry imports nothing from `mfa/`: its merge rows spell the MFA module's modes themselves.
- Imported by `boot/` (the resolver's builder, the registration of requirements and of actions, and the reach seal), `mfa/` (the continuation check an MFA transaction is held to), `user-sessions/` and `modules/manifest/` (types only), the root barrel and the testing entry. A consumer package reaches it through the package entry alone.
- Never imports `boot/`, and nothing outside core but Express's request and response types, which the login completion's call carries.

## Invariants

- **One decision point.** No shipped source outside this directory reads a session record (`get(` on a `UserSessionStore`), reads the subject-revocation boundary (`revokedBefore(`), selects an `acr`, or builds a claim literal. The exceptions are the token side's reads the ADR's D9 leaves where they are and `verifyJwt`, each pinned to its file and count with a reason — [`../__tests__/sessionAdmissionCallers.drift.test.mts`](../__tests__/sessionAdmissionCallers.drift.test.mts).
- **Claims are built here alone.** A claim comes from this directory's builders — one reading of each carrier: the cookie, a code record's first read and its revalidation, a link transaction, a verified token. A claim, a resolver, a primary, an establishment and an interruption are branded at the type level and checked at runtime through module-private sets. An object shaped like one, or a copy of one, is refused with a `RangeError` before anything is read — [`__tests__/admit.test.mts`](./__tests__/admit.test.mts), [`__tests__/primary.test.mts`](./__tests__/primary.test.mts).
- **Every step fails closed.** A store or a requirement that throws, or a requirement that answers something that is not a verdict, is `unavailable` and never a verdict. That covers reading a store off `deps`: each is read once, in the guarded step that uses it, and that reading serves every later step, so a getter that throws is that store's `unavailable`, never an escaped rejection. A requirement's answer is copied inside its own guarded step, so a getter on it that throws is that requirement's `unavailable`. The audit sink is read off `deps` only to audit a subject mismatch; a getter on it that throws fails as that audit, and the answer stands. It names the store admission reads itself (`user_session`, `session_lifecycle`, `revocation_boundary`) or the requirement, and is logged once at error as `session_admission_unavailable` with `store`, `action` and `loggableError`'s projection — never the `sid`. The one exception is `cookieRenewedAway`, which is not an admission: it rejects with the session store's own error, and its caller handles that rejection. A cookie claim without a subject is `not_live` (`no_subject`) before any store is read. A record that is gone, has no `sub`, has an `authTime` or `expiresAt` that is not a valid date, or is past its `expiresAt` is `not_live` (`gone`). After the subject and the renewal nonce, where the consumer hands its `sessionLifecycleStore`, the session's lifecycle record is read through core's reader: one closing or closed is `not_live` (`closing`), from the closing commit on, at the first reading and at the last; no record for the sid, or no store handed, reads as before; a store that throws, answers outside the port's types, or holds a record of another subject is `unavailable` (`session_lifecycle`) — [`__tests__/admit.lifecycle.test.mts`](./__tests__/admit.lifecycle.test.mts). A claim's subject that is not the record's is `not_live`, logged at warn and audited as `session.admission.subject_mismatch`. The subject-revocation boundary is read against a live record, and never for a token carrier, whose boundary `verifyJwt` reads — [`__tests__/admit.test.mts`](./__tests__/admit.test.mts).
- **The decision ends on a fresh reading.** Once a requirement was asked about a live record, admission reads the record and the subject-revocation boundary again — steps 1 to 4, on a fresh clock reading, with the claim's subject held to the first reading's — whatever the requirements and the merge answered, and nothing is awaited after that reading. An answer it gives (`revoked`, `not_live`, `unavailable` for its stores) is the admission's; otherwise the merge's answer stands, with the first reading's session and view. A requirement that throws answers `unavailable` at once, with no second reading. No requirement registered, a `remediation`, no store, and a token carrier without a `sid` add no read; a token carrier's second reading reads the record alone — [`__tests__/admit.freshness.test.mts`](./__tests__/admit.freshness.test.mts).
- **An action is its consumer's registration.** Core names no consumer's action. A consumer registers each action it admits under `contributes.admissionActions`, keyed by a name of two lower-case identifiers joined by a dot, with one of the grades — `use`, `grants_nothing` or `credential_change`; `remediation` is a requirement's alone. A request passes the action's name, and admission hands the requirements the grade it registered: the caller never states one, and the request's object arm is typed `IssuedRemediationAction`. A name nothing registers, and any action object but a remediation core issued to one of the resolver's requirements (a literal, a copy, or one issued to another composition's or another boot's), is refused with a `RangeError` before anything is read; a consumer built at the end of boot refuses an admitted action nothing registers where it is built (`checkResolver(requirements, factory, admits)`), and a grant, built earlier, at the call. A grade is self-declared, and `grants_nothing` exempts an admission a record carries from the MFA requirement's baseline — a token carrier is judged on the token's own `amr` whatever the grade: boot says every registered action with its grade and the module that registered it (`admission_actions_registered`), which is where an operator sees who declared each. Every log line names the action — [`__tests__/actions.test.mts`](./__tests__/actions.test.mts), [`__tests__/admit.test.mts`](./__tests__/admit.test.mts), [`../boot/__tests__/admission-actions.test.mts`](../boot/__tests__/admission-actions.test.mts).
- **A requirement decides by grade and never by an action's name.** Its table is exhaustive over `ADMISSION_GRADES`, the closed list core owns; the contract suite asks it about every grade but `remediation`.
- **A session's enrollment facts are core's derivation.** Every primary a builder makes — `passwordPrimary`, `establishWithoutAsking`, a continuation's rehydration — carries `enrollmentFacts` derived from the snapshot of its `user`: the witness as `readMfaEnrollmentWitness` reads it, and what `user.email` is — `none` when it is absent, `null` or empty, `address` when `normaliseMailAddress` reads one address, `unreadable` otherwise — never the address. The snapshot (`readUserSnapshot`, beside `User` in `repositories/`) reads exactly the fields `User` declares, each by name, once, however the object holds it — an accessor, a prototype, a non-enumerable property — and copies arrays and plain objects inside by name; nothing else of the `user` is read or carried. A login refuses a `user` that is not an object, an `id` that is not a non-empty string or not the primary's subject, and a declared field holding what JSON does not hold as it is, which left out would read the witness as not enrolled; a getter that throws is let through as it threw. Facts a caller hands in are not read, and a continuation carries none: the requirement holding one reads them with `enrollmentFactsOfContinuation`, the same derivation its rehydration runs. A requirement's view carries a frozen copy of a record's facts when they are what the type admits, and none otherwise — [`__tests__/enrollmentFacts.test.mts`](./__tests__/enrollmentFacts.test.mts).
- **A login's claims are read once, declared claims strictly and custom claims as their JSON form.** The claims envelope a primary carries — what the session record's `claims` will hold — is read by [`login-claims.mts`](./login-claims.mts) (`readLoginClaims`). Each claim `UserSessionClaims` declares (`email`, `emailVerified`, `name`, `picture`, `groups`) is read by name, once, however the object holds it, through the same plain-data copy as the user's snapshot (`readPlainFields`, beside `User` in `repositories/`) — a list by index into a plain array with nothing else of it, so a `groups` that is an ORM's list, a Proxy or an Array subclass logs in as a plain string array — and must be of its declared type: `null` or any other value is refused, and a getter that throws is let through as it threw. Each custom claim (each other own enumerable key) is read once and stored as its JSON form, `JSON.stringify` parsed back: a `Date` as its ISO string, an object with `toJSON` as what it answers, NaN as `null`; one whose JSON form is nothing (`undefined`, a function) is left out, as JSON does; one whose JSON form cannot be taken (a bigint, a cycle, a `toJSON` or a getter that throws) is dropped and the login goes on, with `login_claim_dropped` (warn, the key and the reason, never the value) said by `admitPrimary` and `resumePrimary` through their logger and by `establishWithoutAsking` through the one it is handed. Claims that are not an object are refused — [`__tests__/claims.test.mts`](./__tests__/claims.test.mts).
- **The cookie session's user is answered only for its admitted subject.** `cookieSessionUser(req, subject)` answers the user an authenticated cookie session holds, read back as a login reads one (`readUserSnapshot`: the declared fields, frozen at every depth), when the copy's `id` is `subject`, and `undefined` otherwise — a user the snapshot refuses included — [`__tests__/admit.test.mts`](./__tests__/admit.test.mts).
- **A requirement is never asked about a dead session**, and never for a `remediation`: in registration order, with a view of the record, the subject (the record's when one was read, else the claim's) and the D9 reading — for a token carrier, the token's own `amr`. The first verdict that is not `met` wins. A `step_up` carries that requirement's registered page, and is `unmet` from a requirement that registered none and `reauthenticate` over no live session. Each requirement is handed the one action object, frozen, so none changes the grade the next reads — [`__tests__/admit.test.mts`](./__tests__/admit.test.mts).
- **The `acr` is selected here alone**, over what the session vouches for (the D9 reading), never over the record's own `amr` — [`../__tests__/designVocabulary.drift.test.mts`](../__tests__/designVocabulary.drift.test.mts), [`../__tests__/sessionAdmissionCallers.drift.test.mts`](../__tests__/sessionAdmissionCallers.drift.test.mts).
- **A step-up through the authority is never offered for `acr_values` onto a session that cannot record it.** In the met + step_up row, when only a step-up through the second-factor authority could finish a requested `acr`, and the session's store has no `recordSecondFactor` (`supportsSecondFactorUpdate`) or no second factor can be recorded on its record (`canRecordSecondFactor` answers `false`, one of the conditions `recordSecondFactor` answers `null` on; [`../user-sessions/README.md`](../user-sessions/README.md) defines it), admission answers `reauthenticate` (`requirement: "acr"`): a new login can carry the factor. Those two conditions are what is checked, decided once per admission as the record is read into the view (`SessionView.secondFactorRecordable`, below) and read there by the row. Stepping up through another requirement whose own reach finishes the entry is for a later release: in this release only the second-factor authority may reach, so when it is passed over the answer is `reauthenticate` (`acr`). An entry no single trip can finish stays `unmet` (`acr`), and a requirement's own `step_up` verdict is its to answer; its view carries the same answer for it to use — [`__tests__/admit.merge.test.mts`](./__tests__/admit.merge.test.mts).
- **The code exchange is judged on the live record.** An authorization code's carrier is judged at the exchange on the session record as it is then, while the tokens carry the `amr` `/authorize` vouched for. A session requirement must not hold `oauth.code_exchange` stricter than `oauth.authorize` — both are graded `use`, so only by the action's name or the carrier: a step-up that lands between the two would open an exchange the requirement meant to refuse. The bundled MFA requirement answers the two alike.
- **A requirement's name** is RFC 6749's error-code characters — printable ASCII without `"` or `\`, at least one — the only ones a `step_up` is sent in on the wire. It is never one of the names admission gives its own stores' outages (`user_session`, `revocation_boundary`, `session_lifecycle`), so the store an `unavailable` admission names tells a store's outage from a requirement's. Registration refuses both at boot — [`__tests__/requirement.test.mts`](./__tests__/requirement.test.mts), [`../boot/__tests__/session-requirements.test.mts`](../boot/__tests__/session-requirements.test.mts).
- **Core describes every admission outage.** `describeAdmissionOutage(store)` is the one text a client is given: each of admission's own stores by name, anything else as a requirement's outage, never by the requirement's name. Every bundled consumer answers an `unavailable` admission with it, so none reports a requirement's outage as the session store's — [`__tests__/requirement.test.mts`](./__tests__/requirement.test.mts).
- **A requirement is registered as a copy**, each field read once. Its remediations are its own routes, `<name>.<route>`, each once, and never a registered action's name — refused where both are known, at the end of boot's stage 4 and by `resolverForTests`. Core issues one branded remediation action per route to the contributing module alone, by the object its factory returned; the copy the resolver answers carries none. Its hint keys follow core's grammar, none of them a name core reserves — [`__tests__/requirement.test.mts`](./__tests__/requirement.test.mts), [`../boot/__tests__/session-requirements.test.mts`](../boot/__tests__/session-requirements.test.mts).
- **The step-up page is resolved once, at registration, on the issuer** it is validated against — at boot, `oauth.jwt.issuer`. A path must stay on the issuer's origin once a browser resolves it (`//host`, `/\host`, an encoded backslash and a control character are refused); an absolute URL must be on the issuer's origin; `params` are strings and never `redirect_to`, the consumer's return parameter. A path page with nothing to resolve it on is refused. The registered page carries its `href` — one absolute URL, the params on the query, no return parameter — and a `step_up` admission carries that page: every consumer answers or navigates from `href` and none resolves the page itself — [`__tests__/requirement.test.mts`](./__tests__/requirement.test.mts).
- **The reach is sealed once, and one requirement reaches.** A requirement's `reach` is not read at registration, since it may fill as the same pass registers the factors. It is read once, at the end of boot's stage 4, held to the reach rules and sealed on the copy as a frozen snapshot. The resolver, the `acr` drop and admission read that snapshot, and a contributor's mutable `Set` changes nothing after boot. The rules: no primary's marker; a second-factor value from the second-factor authority alone; a page for a reach that is not empty (a page may stand with an empty reach); and, in this release, an empty reach for any requirement that does not declare the authority, since only the authority adds vouched values to a session. The rules have one home, which boot, `resolverForTests` and the contract suite all run; only `resolverForTests`'s `allowAnyReach`, for tests of admission's own mechanics, lifts them — [`__tests__/requirement.test.mts`](./__tests__/requirement.test.mts), [`../boot/__tests__/session-requirements.test.mts`](../boot/__tests__/session-requirements.test.mts).
- **The second-factor authority is declared, never named.** A requirement declares in its contract that it is the second-factor authority (`secondFactorAuthority`), read once at registration; no rule here weighs a requirement's name. The authority alone may reach a second-factor value and add one or an `mfaAt`, and at most one registered requirement declares it: a second refuses the boot (`duplicate-second-factor-authority`, naming each with its module), and `resolverForTests` refuses it. Boot binds the authority to core's MFA ports: its module requires `mfaFactorResolver`, `mfaFactorStore` and `mfaTransactionStore`, its reach is what the installed factors reach, and it declares its own `<name>.step_up`, the route its step-up is recorded by. The boot line `session_requirements_registered` says each requirement's declaration. A requirement that does not declare it — one named `mfa` included — is bound to none of this and held to what every other requirement is, and the contract suite holds a fixture to never declaring it — [`__tests__/requirement.test.mts`](./__tests__/requirement.test.mts), [`__tests__/primary.test.mts`](./__tests__/primary.test.mts), [`../boot/__tests__/session-requirements.test.mts`](../boot/__tests__/session-requirements.test.mts).
- **A login is established from what core built.** A password login's primary is built by `passwordPrimary` alone and records `pwd`. A completion adds a second-factor value or an `mfaAt` only from the second-factor authority, and the authority's must be a verified second factor, whether presented to `resumePrimary` or read back from a continuation — so a completion that verified nothing never establishes a password-only session. `resumePrimary` holds each completion, the one presented and each read back, to its requirement's declaration as registered. A persisted continuation is read back through its check, which holds what any completion keeps: a second factor, whoever adds it, a verified one, added by one entry at most. That check does not know which requirement declares the authority, so it accepts an entry under the authority's name that added nothing, and a verified second factor under a name that does not declare it; `resumePrimary`, the one check that knows the registration, refuses both before composing. `resumePrimary` asks, in order, every requirement with `admitPrimary` not already done in that login. An interruption is opened with the session id and the continuation core built, and its answer is held to the closed body and core's hint grammar before the route sees it — [`__tests__/primary.test.mts`](./__tests__/primary.test.mts), [`__tests__/primary.check.test.mts`](./__tests__/primary.check.test.mts).
- **The resumption's callers are guarded.** Outside this directory, a call of `resumePrimary(` or `continuationOf(` is kept to `packages/mfa/src`: in this repository only the MFA package completes an interruption. A second in-tree requirement that interrupts a login widens the guard in the pull request that adds it; `tools/composition`'s fixture requirements are not scanned. Beside them, `establishWithoutAsking(` is kept to the federation callback and `recordSecondFactor(` to the two bundled session stores and `packages/mfa` — [`../__tests__/sessionAdmissionCallers.drift.test.mts`](../__tests__/sessionAdmissionCallers.drift.test.mts).
- **The merge rows are the second-factor authority's table, in one list.** The merge is the MFA ADR's step-4 table under the ADR's D2 mapping, with no row lost. Its rows are one list on the testing entry. A row may say its session store cannot record a second factor (`storeRecords: false`): whoever runs the rows runs each over a store that honours it — with the step-up capability unless the row says so — and `mergeSessionStore(row)` builds such a store. `mergeAdmission` maps a row onto the admission of the registered requirement it is given, throwing unless that requirement declares the authority. It is always handed the store the admission ran over — `mergeSessionStore(row)`, or `undefined` for a row with no session, or a composition without a store — and builds the view's `secondFactorRecordable` over that store. Core's merge test runs them against a stand-in written to the MFA requirement's table under a name that is not `mfa`, registered as boot registers it, and the MFA package runs them against the requirement it registers — its `mfa.mode = "off"` rows against admission with no requirement registered, which is what an MFA-off composition is. They are the authority's rows: another requirement is held to the contract suite, not to them — [`__tests__/admit.merge.test.mts`](./__tests__/admit.merge.test.mts), and `packages/mfa`'s `requirement.merge.test.mts`.
- **A login's tail is reached through a slot, never an import.** A requirement's completion finishes a login through `loginCompletion`, which the session package's login-completion module provides: each of its two login calls refuses what core did not build before the session is touched, every outage leaves the browser not signed in, and an interruption's `403` carries a fresh CSRF token. Its `renewSession` moves a signed-in session to a regenerated id with `isAuthenticated`, `user` and `sid` as they were, a fresh renewal nonce it answers and no other field, saved, writing no session record; a session not signed in stays so; a `regenerate` or `save` that fails, or a request with no express session, is reported once, saves nothing and drops the request's cookie session, and the caller records nothing on it. Renewal orphans what is bound to the old id: a consent `/authorize` parked, a federation-grant browser binding, the session's other open MFA transactions. The suite a provider runs holds it to that — [`__tests__/loginCompletion.test.mts`](./__tests__/loginCompletion.test.mts).
- **An escalated session is live only for the cookie session it was renewed to.** For a cookie claim, a record that carries a renewal nonce (`UserSession.renewalNonce`, recorded with the escalation) the cookie session does not hold — another, none, or a value in another shape — is `not_live` (`renewed`), after the subject check and before the revocation boundary: an old express id a request in flight saved back after the renewal names the same `sid` and is refused. The record's nonce is read once, and a value that is not a nonce binds it to no cookie session, whatever the cookie session holds. A record without a nonce is read as before. `cookieRenewedAway(store, claim)` answers the same question for a route that acts on the record without admitting the session — the session package's logout — through the one record read admission makes. Token, code and link claims are not compared: they carry no cookie session, so an authorization code or a link transaction minted from the session before a step-up still names its `sid`. What the step-up adds does not reach an authorization code's tokens: the code carries the `amr` `/authorize` vouched for, which the oauth package's `authorization_code` grant stamps instead of the record's. A link transaction is judged against the live record, and its start already passes `credential_change` — [`__tests__/renewalNonce.admission.test.mts`](./__tests__/renewalNonce.admission.test.mts), the session package's `renewSession.test.mts` over express-session, and the oauth package's `authorizationCode.amr.test.mts`.
- **A consumer reads the session's facts from admission's view, never off the record.** An admitted admission carries `view` — the `SessionView` admission reads the record into once (`viewOf`), `null` without a record — and a `step_up` one its view. Each requirement is handed a copy with Dates of its own, and its own frozen reading of the authentication (`requirementSession`, called afresh), so nothing a requirement does to its input reaches the next requirement, the merge or the consumer, and it holds the four fields, the enrollment facts and whether a second factor can be recorded on the session, never the `User` or its address — [`__tests__/admissionView.test.mts`](./__tests__/admissionView.test.mts).
- **Whether a second factor can be recorded on the session is decided once, in the view, and handed on.** `SessionView.secondFactorRecordable` is `true` when the store admission read the record from has the step-up capability (`supportsSecondFactorUpdate`) and `canRecordSecondFactor` is true of the record ([`../user-sessions/README.md`](../user-sessions/README.md)); `readLiveSession` reads the store's capability once per reading, over a live record and never without one, in the same guarded step as the record — a store that throws on that read is `unavailable` (`user_session`), never a verdict — and `viewOf` decides the field from it and `canRecordSecondFactor`, the one place it is decided. Every requirement's copy carries it, so a requirement that steps a session up through a second factor can choose `step_up` or `reauthenticate` on it without reading the store or the record's shape. The admitted and `step_up` admissions carry it, so a route that opens a step-up ceremony itself can refuse one that could not be recorded. The merge's met + step_up row reads it there too. Without a record the view is `null`, and a `step_up` over no session is already `reauthenticate` (step 5). It is required in the type: admission always sets it, and a view built by hand sets it too. A token carrier whose record was read is answered from the record, never from the token's `amr` — [`__tests__/admissionView.test.mts`](./__tests__/admissionView.test.mts).
- **The contract suite fails each way a requirement can break the contract** — [`__tests__/contract.test.mts`](./__tests__/contract.test.mts).
