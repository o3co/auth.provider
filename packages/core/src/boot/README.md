# boot

Last updated: 2026-10-03

## Responsibility

The engine behind `createApp`: six stages in a fixed order — `validateManifests` → `planBoot` → `materializeComponents` → `applyContributions` → `freezeWorld` → `assembleApp` — that turn a list of manifests, the host's bootstrap components and the raw configuration into a frozen component world, a mounted Express router and an `AppHandle`. It owns manifest validation, the dependency graph and init order, provider activation, routing contributions to their collectors, the dispatch of `core.federations` entries to the federation types that handle them, freezing, route mount order, the middleware core mounts itself (protected-resource binding always; CORS only when there are origins to let read; the composed `tokenBindingMw` only when a mechanism was contributed), the discovery route's mounting, disposal, the four bootstrap slots (`config`, `pathResolver`, `lifecycleRegistrar`, `readinessRegistrar`), and the `deploymentMode` slot, which it fills from the configuration.

It owns no protocol behaviour: no grant, no route handler, no token. Provider-specific stage-1 checks — the session-requirement kind guard, federation / redirect-policy pairing, federation stores wiring, the federation entries every enabled `core.federations` entry needs a handler for, declared absence, grant-policy issuer, replica safety — are rows of boot's registry, not code in the directories they concern: boot is the one place that sees every manifest and the parsed config together, and a registry row cannot be skipped by a module that forgot to call it. That is why this is a directory of its own, and why no product code but the barrel and `testing/` imports it.

One wiring rule is not a row: `requireFederationGrantSubjectRevocation` ([`../federation-grants/revocationWiring.mts`](../federation-grants/revocationWiring.mts)) is called by the factories that need it — the route contributions of `packages/federation-grants` and the subject revocation service provider in `packages/oauth` — so its refusal reaches boot as a factory failure (`contribute-factory-failed` or `provides-factory-failed`, with the rule's error as its `cause`) rather than as a stage-1 violation.

## Public contract

- The entry point is `createApp(options)` in [`create-app.mts`](./create-app.mts), re-exported by [`../app.mts`](../app.mts) and the root barrel.
- The contract types — `CreateAppOptions`, `AppHandle`, `BootError` with its `BootErrorReason` / `BootStage` unions and one `*Details` type per reason, the collector contracts, and the `ComponentMap` augmentation for the bootstrap slots — are in [`types.mts`](./types.mts).
- The stage-1 check registry (`STAGE_ONE_PRE_CONFIG_CHECKS`, `STAGE_ONE_POST_CONFIG_CHECKS`, exported and frozen) is in [`validate-manifests.mts`](./validate-manifests.mts); the replica-safety check and `replicaUnsafeReason` are in [`replica-safety.mts`](./replica-safety.mts).
- [`index.mts`](./index.mts) is the internal barrel; the root `index.mts` chooses the public subset. Package README: [App Factory](../../README.md#app-factory).

## Inputs and outputs

- `modules` are consumer code, taken as the erased `Module` type; boot validates their structure, never their behaviour. `bootstrapComponents` are host-owned and pre-seeded; `overrideComponents` replace a module's provider (the factory is skipped and the value's lifecycle stays the consumer's) — except a key a loaded module names `authoritative`, which stage 1 refuses to see substituted (#728); neither map may carry `__proto__` as its own key, which names no component (`reserved-component-key`); `contributionKinds` supplies collectors for consumer-defined kinds only — never for `sessionRequirements` or `mfaFactors`, which stage 1 refuses to see replaced.
- Stage 1 parses `bootstrapComponents.config` — the configuration the composition root resolved, unparsed, less the captures of renamed variables (`renamed-variables`) — once ([#728](https://github.com/o3co/auth.provider/issues/728)): with core's transitional base (core's sections and every section it mirrors for another package, each optional), laid over what was written so no key is stripped, then with each module's `configSchema` over the base's output, laid over the same way (a key a parse holds as `undefined` is removed; two modules' outputs that disagree at a key are refused, naming both); every refused value is one `config-validation-failed` naming each operator path — the base's alone when the base refuses. The same refusal names every reserved key of the configuration as written, at any depth, whatever the schemas make of it: a key named after an `Object.prototype` member (`__proto__`, `constructor`, `toString`, …), or `prototype` — a schema would drop `__proto__` unread, and a lookup by any of the others may find an inherited member. The check walks the own data properties of plain objects and lists, which is everything a parsed HOCON file holds; a getter in a configuration built in code is read by the parse, not by the check, and a shared object is named under every path that reaches it. The result, with each section written back (below), is substituted into `bootstrapComponents.config` for every later stage and every post-config check. A top-level section no loaded module owns — not core's base, a `configSchema`'s top-level key or a section's first key — is kept and named once to the logger (`config_sections_ignored`, warn, `sections`) — the bootstrapped one, where the replica-safety warning goes too; with none wired, stage 1 warns nowhere. While core's schema mirrors other packages' sections, a mirrored section counts as owned, loaded module or not, so none is named. A section that sets nothing — empty, or holding only empty sections, by the walk the relocation refusal reads a configuration with (`pathsSetBy`) — is not named (a `reference.conf` leaves one when its variables are unset).
- Then, before any post-config check, stage 1 parses each module's own section ([#728](https://github.com/o3co/auth.provider/issues/728)): for every manifest in `modules` that declares `section` — one whose provider an override replaces included — the value at `section.at` (the module's name when unset), read key by key as own properties, is taken out of that composed config and parsed with `section.schema`, and the result, deeply frozen (plain data copied, anything else as the schema made it), is set as `deps.section` on the deps object of every factory of the module — `provides` at stage 3, `contributes` and `overrides` at stage 4. Every section is read before any is written back; then each result is laid over what is at its path in the config slot (a key it does not hold is kept, one it holds as `undefined` removed), outer sections first, so a section inside another module's lands inside it, and a section whose result is `undefined` removes what is written there; a path a scalar, list or instance stands in the way of is refused there (`config-validation-failed`). `section.reference` is not read; `section.relocatedFrom` is read before the parse (below).
- Then stage 1 reads each module's switch, `section.isEnabled`, with the section it parsed: a module it answers `false` for is switched off, and from there on is its name and its section alone — the post-config rows, which hold every manifest and wiring check (provides, requires, contributions, routes, overrides, lifecycle, declared absence, replica safety), and every later stage see nothing it would register, and none of its factories runs. Only what the parse relies on runs before it, over every module: the manifests, unique names, section paths, and the refusal of old paths and renamed variables. A switch that throws or answers anything but a boolean is `config-validation-failed`, naming the section's path.
- Output: an `Object.freeze`d `AppHandle` whose `components` map is frozen, whose `routes` are in final mount order, and whose `readinessProbes` are what builders registered.
- Mutation stops at stage 5: the component map is frozen and every collector with a `freeze()` is sealed; `register` afterwards throws.

## Dependencies

- Boot imports from every layer below it: `modules/` and `modules/manifest/` (the vocabulary and `SYNTHETIC_COMPONENT_KEYS`), `config/` (`TransitionalConfigSchema` and the overlay), `deployment/` (`deploymentModeOf`, the one reading of `core.deployment.mode`), `federations/` (`federationsOf` and the rules it keeps for a `core.federations` entry: the keys core owns, the name rule, what enabled means), `grants/` (the `GrantRegistry` behind the `grants` collector), `middleware/` (the middleware it mounts), `discovery/` (the planner hooks), `audit/` (`createAuditFanOut`, what the `auditSink` slot holds when `auditHooks` are contributed), `repositories/` (`validatedClientRepository`, what the `clientRepository` slot holds), `net/`, `adapters/`, `readiness/` and `logging/`; to read their replica-safety declarations it imports every directory that bundles a `memory…Module`. `express` is an optional peer: `create-app.mts` imports it with `await import("express")` for the router, and `assemble-app.mts` always requires it with `createRequire` for the `express()` factory `listen()` needs — and for the router when none was passed in.
- Imported by, outside `__tests__/`: `../app.mts`, `../index.mts`, `../testing/`. No other product code in core depends on boot; packages reach it only through `createApp`.
- Boot → `discovery/` runs one way. [`assemble-app.mts`](./assemble-app.mts) hands [`planDiscoveryDocument`](../discovery/planRoute.mts) values — the issuer, and readers for the signing algorithms and the `discoveryMetadata` contributions, so each is read only when planning needs it — never its world, and converts an `outcome: "invalid"` result into a `BootError`. The planner returns a document that failed to validate as a value rather than throwing it, so boot has no `try` around it or around `discoveryRouteFor`: whatever host-supplied code throws there (the key store's algorithm, a contribution's `providerRoot`, the router factory) arrives as itself, unconverted.
- Must never import an adapter package or `testing/`.

- Every `modules` entry is a manifest: a function — a module factory listed without being called, which `Module`'s type accepts because a function has a `name` — is refused as `module-factory-not-called` by the first stage-1 row, before any other row reads it — [`validate-manifests.test.mts`](./__tests__/validate-manifests.test.mts).

- A module's section is parsed at stage 1, from the composed config (coerced where core's schema coerces, with every key no schema declares kept), handed to all of its factories as one deeply frozen `deps.section`, and written back at its path, outer sections first — [`composed-parse.test.mts`](./__tests__/composed-parse.test.mts), with the composed parse itself, the refusals naming operator paths and `config_sections_ignored`; a value its schema refuses — or a schema that throws instead of answering, as an async refinement does — is `config-validation-failed` before the post-config rows and any factory run, every refused section in one error, each issue's path the operator's (the section's path in front) and `details.modules` naming each refused module with that path as `schemaPath`; a module without a section gets no `section` key; the row `reserved-component-keys` refuses a module that declares a section and requires or optionally reads a component named `section` (`reserved-component-key`) — any other `section` component boots — and `module-section-paths` an `at` with an empty key or that is not a string, named by its type, and a path two modules' sections are read at, refusing the later one (`module-section-path-invalid`) — [`module-section.test.mts`](./__tests__/module-section.test.mts).

- A configuration handed to `createApp` that still sets a key at or under a path a loaded module's section moved from (`section.relocatedFrom`, a list of old paths moved whole or a map from each to its path inside the section) is refused by the pre-config row `relocated-config-paths` with `config-path-relocated`, before the configuration is parsed: every such key, in module order, with its module, its old and new dot paths and, for a value, the environment variable bound to the new path; a composition not loading the module boots. `module-section-paths` refuses a `relocatedFrom` that is neither form (a list, every index present, or a plain map — not a Date, a Map or a class instance), has an empty key, names a path that is, or holds, a loaded module's section, or overlaps an old path another loaded module claims — the later module refused, both named (`module-section-path-invalid`) — [`relocated-paths.test.mts`](./__tests__/relocated-paths.test.mts). Core's own section declares its relocations and renames the same way (`CORE_RELOCATIONS`, `validateManifests`' `core`), read by these rows as module "core". The pre-config row `renamed-environment-variables` then judges each variable a loaded module or core declares renamed (`section.renamedVariables`) by what the resolution captured of it in the configuration's reserved `renamed-variables` section (each name `null` unset, the raw string set, as the declaring package's `reference.conf` captures it), and refuses boot with `environment-variable-renamed` (`state`) while the old name is set (the empty string included) and the new name is unset or set to a different string, while a removed key's variable is set, or when a name is not captured: every such variable, in module and declaration order, with its new name and the path that name is bound to, and no value; the two set to the same string boot. ## Failure and lifecycle

- A refused boot is a `BootError` with `reason`, `stage` and typed `details`; `cause` is set for the `*-factory-failed` reasons and for `discovery-document-invalid`, which carries the `DiscoveryDocumentError` it wraps ([`discovery-aggregation.integration.test.mts`](./__tests__/discovery-aggregation.integration.test.mts)).
- A `BootError`'s message names the error behind it by `loggableError`'s rules — its name and message on one line, nothing of a SyntaxError's or a YAMLException's text, a Redis reply's echoed arguments cut, only the kind of a thrown value that is not an Error — never by `String(...)` of it, and without a log field's 256-character cap, so a refusal's advice is kept whole (`failure-summary.mts`); the error itself is the `cause`. Printed (`util.inspect`, Node's unhandled-rejection printer), a `BootError` shows its `cause`, `details.originalError` and cleanup errors by their `loggableError` projection, never whole. A boot failure is printed whole to the log it ends in, and a parser's error quotes its input — [`factory-failure-message.test.mts`](./__tests__/factory-failure-message.test.mts). A required dependency missing at stage 3 or 4 is a plain `Error` — an invariant an earlier stage should have caught, not an operator problem.
- Partial rollback: a stage-3 failure runs the cleanups already recorded, in reverse, collecting cleanup errors into `details.cleanupErrors` — [`materialize-components.test.mts`](./__tests__/materialize-components.test.mts); `LifecycleRegistrar` cleanups drain when any later stage fails — [`create-app.test.mts`](./__tests__/create-app.test.mts).
- `dispose()` is single-shot. It runs `lifecycle.cleanup` in reverse-topological order, falls back to `Symbol.asyncDispose` for module-provided values that declared none — never for override or bootstrap values — and drains the `LifecycleRegistrar` in LIFO order; every error is aggregated into one `AggregateError` — [`assemble-app.test.mts`](./__tests__/assemble-app.test.mts), [`integration.test.mts`](./__tests__/integration.test.mts).
- `dispose()` waits for every cleanup and bounds none. A cleanup's `tailMs` is the least time a host that bounds `dispose()` must allow the whole of `dispose()` for that cleanup's work to settle, the cleanups around it included; `AppHandle.cleanupAllowanceMs` is the longest registered, read when asked, `undefined` when none declared one. Hosts take the longest, so tails do not add. A tail that is not a whole number of milliseconds from 1 to 2147483647 throws a `RangeError` after its cleanup is registered, so the drain after the boot it fails still runs the cleanup — [`assemble-app.test.mts`](./__tests__/assemble-app.test.mts), [`create-app.test.mts`](./__tests__/create-app.test.mts), [`AdapterFactory.test.mts`](../adapters/__tests__/AdapterFactory.test.mts).
- A `LifecycleRegistrar` cleanup that throws is logged once, at error, object-first as `adapter_lifecycle_cleanup_failed` with `phase` (`dispose` or `boot_failure`), its `cleanupIndex` and the `loggableError` projection, and the drain goes on — also when the logger itself throws, so a failed boot still rethrows the error that failed it. At `dispose()` the line goes to the `logger` component; when boot failed, to the logger the composition root handed in (bootstrap or override); either way to `consoleLogger` when there is none — [`create-app.test.mts`](./__tests__/create-app.test.mts), [`AdapterFactory.test.mts`](../adapters/__tests__/AdapterFactory.test.mts).
- No cancellation and no deadline: `CreateAppOptions` carries no signal, so a factory that never settles keeps `createApp` pending. Documented, not tested.
